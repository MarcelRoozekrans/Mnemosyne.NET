# Docs completeness Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Three new docsite pages, an overview with the package map, a variants vision with a 1.0 / post-1.0 split, and a host guide for Daedalus and Thalos, plus the links that make them reachable.

**Architecture:** Documentation only. Each page is written against the source and the existing guides, links to them instead of repeating them, and is checked by the docsite build. No package, sample or API change.

**Tech Stack:** Docusaurus (`npm run build`), Markdown with Mermaid.

**Spec:** `docs/superpowers/specs/2026-11-06-phase-4.5-docs-completeness-design.md`

## Global Constraints

- Docs only. A wrong or missing API found while writing is filed as an issue, not changed here.
- Front matter is `title` and `sidebar_position`. The sidebar is autogenerated from the folders. The site uses `onBrokenLinks: 'throw'` and `onBrokenAnchors: 'throw'`, so every link and anchor must resolve.
- Name only types, properties and packages that exist in `src/` today. The post-1.0 part of the variants page names no interface.
- Run the `anti-slop` skill on every page before its commit. Style follows the existing pages: concrete first, behaviour next, limits last.
- Daedalus and Thalos statements come from those repos' public READMEs (`gh repo view MarcelRoozekrans/Thalos.NET`, `gh api repos/MarcelRoozekrans/Daedalus.NET/readme`). Anything not confirmed there is dropped or phrased as "see the host's repository". Daedalus.NET has no description; if its README is empty, say less.
- Commits: conventional, free scopes, no Claude signature, no nested parentheses in a message body. Work on `docs/phase-4.5-docs-completeness`; push with an explicit `branch:branch` refspec, because `push.default` is `upstream`.
- Phases 4.2 and 4.4 are built first: the pages use `LineageId` and link `docs/concepts/compatibility.md`.

## Review Focus

- The variants page must keep the 1.0 and post-1.0 parts visibly apart, and the post-1.0 part must promise no name (Task 2).
- Every claim about the Thalos adapter must trace to its README, not to memory (Task 3).
- The overview's package table and flow diagram must match the real package names and the real call order (Task 1).
