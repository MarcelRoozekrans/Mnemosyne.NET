# Phase 3.7 Integration Docs and Samples Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** Three integration guides on the docsite and two offline, self-checking, CI-gated samples (chat pipeline, Agent Framework), so milestone 3's "Docs and samples cover every integration" holds.

**Architecture:** Two new console samples under `samples/`, in the shape of the existing two (compose file, README, self-check that exits 1). They share a scripted `IChatClient` and a capture watcher in `samples/Shared`, both unit-tested in `tests/Mnemosyne.NET.Tests/Samples`. Guides live in `docs/guides` and quote only what a sample checks. No package changes.

**Tech Stack:** .NET 10, xUnit v3, Microsoft.Extensions.AI, Microsoft.Agents.AI 1.24.0, AI.Sentinel 4.2.0 (all versions from central package management), PostgreSQL 17 + pgvector, Docusaurus.

**Spec:** `docs/superpowers/specs/2026-11-05-phase-3.7-integration-docs-samples-design.md`

## Global Constraints

- `TreatWarningsAsErrors` is on; samples build under `samples/Directory.Build.props` (`IsPackable` false). No version attributes in csproj files: `Directory.Packages.props` pins them.
- No public API change in any package. A needed change is filed as an issue and dropped from this phase.
- Samples need no key and no model: Docker plus the .NET 10 SDK only. Each has its own database (256 dimensions), reads `MNEMOSYNE_SAMPLE_PG`, and erases its scope in a `finally`.
- A self-check mismatch prints `FAILED: ...` to stderr and exits 1; the run is capped at 2 minutes. Never wait with a fixed sleep.
- Compose ports must not collide with 5432 (store-and-recall) and 5433 (evaluation): chat pipeline uses 5434, Agent Framework uses 5435.
- Guide front matter is `title` and `sidebar_position` (existing guides use 1 to 6): chat-pipeline 7, capture-and-review 8, agent-framework 9. The docsite uses `onBrokenLinks: 'throw'` and `onBrokenAnchors: 'throw'`.
- Prose follows the repository's style; run the `anti-slop` skill on every page and README before its commit.
- Commits: conventional, free scopes, no Claude signature, no nested parentheses in a message body. Work on `feat/phase-3.7-integration-docs-samples`; push with an explicit `branch:branch` refspec (`push.default` is `upstream`).
- The repo refuses `dotnet test --filter`: build first, then run the test exe with `-class <FQN>`.

## Review Focus

- A blocked or skipped capture leaves nothing for a poll to see, so the sample must learn that the capture finished from telemetry, not from the store (Task 2, Task 3).
- The credit card number must be one AI.Sentinel's PII detector rates Critical (a Luhn-valid number); a made-up number would store, and the sample would pass its block check only by accident (Task 3).
- The blocked question's tool shape must differ from the approved one, or an unblocked capture would be an execution of the recalled Reasonlet and look the same as a block (Task 3).
- A sample must fail loudly if the background capture never reports, instead of hanging: the watcher times out with a clear message (Task 2).
- The agent sample must prove the provider put the recalled procedure in the run's instructions, not that some text was sent (Task 4).

### Task 1: ScriptedChatClient

**Files:**

**Interfaces:**
- Produces, in namespace `Mnemosyne.Samples`:
  - `public sealed record ScriptedToolCall(string Name, IReadOnlyDictionary<string, object?> Arguments);`
  - `public sealed class ScriptedChatClient : IChatClient` with constructor `ScriptedChatClient(IReadOnlyList<ScriptedToolCall> toolCalls, string answer)`.
  - `IReadOnlyList<IReadOnlyList<ChatMessage>> Requests` (messages of every call, copied at call time), `IReadOnlyList<ChatOptions?> Options`, and `string SystemText(int call)`: the text of the call's system messages and its `ChatOptions.Instructions`, joined by a newline, empty when there are none.
- Behaviour: when the last message of a call is not a tool result (`FunctionResultContent`), reply with one assistant message holding a `FunctionCallContent` per scripted call (call ids `call-1`, `call-2`, ...; empty list means no tool calls and the answer straight away); otherwise reply with `answer`. Streaming replays the same reply as updates. A cancelled token throws `OperationCanceledException`. Dispose does nothing. Document in the class remarks that it is not a model and what a host registers instead.

  - `ARequestEndingInAToolResultGetsTheAnswer`: a last message with a `FunctionResultContent` gives a reply whose `Text` equals the answer and that has no function calls.
  - `NoScriptedCallsAnswersAtOnce`.
  - `RequestsAreCopiedWhenTheCallIsMade`: mutate the caller's list after the call; `Requests[0]` is unchanged.
  - `SystemTextJoinsSystemMessagesAndInstructions`: a system message `"A"` plus `Instructions = "B"` gives `"A\nB"`; neither gives `""`.
  - `StreamingReplaysTheSameReply` (collect updates, `ToChatResponse()`, compare text and calls).
  - `ACancelledTokenThrows`.

### Task 2: CaptureRunWatcher

**Files:**
- Create: `samples/Shared/CaptureRunWatcher.cs`
- Test: `tests/Mnemosyne.NET.Tests/Samples/CaptureRunWatcherTests.cs` (link the file in the test csproj)

**Interfaces:**
- Produces, in namespace `Mnemosyne.Samples`: `public sealed class CaptureRunWatcher : IDisposable` with
  - constructor `CaptureRunWatcher()`: starts a `MeterListener` on the meter named by `MnemosyneTelemetry.MeterName` (`"Mnemosyne.NET"`, in `Mnemosyne.NET.Abstractions`) for the instrument `mnemosyne.capture.runs`, reading the `mnemosyne.outcome` tag of each measurement;
  - `Task<string> NextOutcomeAsync(TimeSpan timeout, CancellationToken ct)`: completes with the outcome tag of the next finished capture run, in arrival order; throws `TimeoutException` with the message `No capture finished within <timeout>.` on timeout.
- Why: a blocked, skipped or execution-only capture changes nothing a store poll could wait for. The counter is emitted when a background capture finishes, whatever its outcome, so it is the completion signal. The outcome values are the strings in `src/Mnemosyne.NET/CaptureTelemetry.cs` and `RecallTelemetry.ErrorName` (`new_reasonlet`, `new_version`, `execution_only`, `skipped`, error codes such as `Blocked`).

- [x] **Step 1: Write the failing tests.** The counter is internal to the core, so drive the real queue: build a small provider (`AddMnemosyne` with the in-memory fakes the tests already use in `tests/Mnemosyne.NET.Tests/Core/Fakes.cs`, plus `AddReasonletCapture`), hand one `ReasonletCaptureRun` to `IReasonletCaptureSink`, and assert:
  - `ReportsTheOutcomeOfAFinishedCapture` (a valid tool-calling run gives `new_reasonlet`);
  - `ReportsABlockedCaptureByItsErrorName` (register a guard that always blocks; outcome is `Blocked`);
  - `ReturnsOutcomesInArrivalOrder` (two runs, two calls);
  - `TimesOutWhenNothingFinishes` (`NextOutcomeAsync(TimeSpan.FromMilliseconds(50), ct)` throws `TimeoutException`).
  Copy the construction of `ReasonletCaptureRun` from `tests/Mnemosyne.NET.Tests/Chat` or `AgentFramework` capture tests rather than inventing one.
- [x] **Step 2: Run to see the failure.** `dotnet build tests/Mnemosyne.NET.Tests -c Release`. Expected: build error, type not defined.
- [x] **Step 3: Implement** `CaptureRunWatcher`. Queue outcomes in a `Channel<string>` fed from the listener callback; a listener on a shared static meter also sees other tests' captures, so the test class must not run in parallel with other capture tests (use a collection attribute the existing telemetry tests already use; find it with `grep -rn "Collection(" tests/Mnemosyne.NET.Tests`).
