# Phase 4.2 Design — Versioning and lineage API

**Date:** 2026-11-06
**Phase:** 4.2
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)
**Status:** approved 2026-11-06

## Goal

Settle the versioning and lineage API so variant selection in milestone 5 is an addition and not a break: a recall says which lineage each match belongs to, and the types a selector builds can grow.

## Why

A recall returns sibling versions as unrelated matches. `ReasonletDefinition` has a `ParentId` and a `1.k` label, but nothing names the lineage, so a variant selector would have to walk `ParentId` through store reads on every recall. The types on the selector path, `ReasonletCandidate`, `ReasonletMatch` and `ReasonletEvidence`, are positional, so adding a member after 1.0 changes a constructor and breaks binary compatibility. Both gaps must close before the freeze in 4.4.

## Approaches considered

| Approach | Trade-off | Chosen |
|---|---|---|
| **Lineage id plus proof.** `LineageId` on candidate and match, labels documented as opaque, a test-only variant selector proves the seam. | Smallest API change that makes the grouping possible; no new facade method. | **Yes**, by the user |
| Lineage id plus a lineage read (`GetLineageAsync`) on the facade and store. | Serves review UIs and variant tooling, but adds interface members before anything needs them. | No |
| Docs and test only. | M5 would do store reads per recall. | No |

| Where the id comes from | Trade-off | Chosen |
|---|---|---|
| **Computed at search.** The search walks up `parent_id` per candidate. | No schema change; a link cut by an erase is correct at once. Cost is lineage depth times the search limit. | **Yes**, by the user |
| Stored `lineage_id` column. | Cheaper reads, but a backfill migration and a subtree rewrite on every erase. | No |

| Extensibility | Chosen |
|---|---|
| **Convert `ReasonletCandidate`, `ReasonletMatch` and `ReasonletEvidence` to init-only records now.** | **Yes**, by the user |
| Leave all positional records to the 4.4 review. | No |

## Approach

**Lineage id.** A lineage is a root Reasonlet and every version below it. `LineageId` is the id of the root, reached by following `ParentId` upward within the scope. For a root it is the Reasonlet's own id; for a version whose parent was erased, the link is cut, so the version is its own root. `ReasonletCandidate` and `ReasonletMatch` each get `required ReasonletId LineageId`. `ReasonletDefinition` is unchanged: it holds stored facts, and the lineage is derived. `ReasonletSelector` copies the candidate's `LineageId` onto the match.

**Search query.** `ReasonletRepository.SearchAsync` stays as it is, so the HNSW index still serves the nearest-neighbour select. A new `ReasonletRepository.ResolveLineageRootsAsync(scope, ids)` takes the candidate ids and, in the same transaction and one round trip, walks up `parent_id` for each with a recursive CTE like `WalkUpAsync`, answering a row of start id and root id, the root being the row with no parent. `SearchCoreAsync` calls it once when the search returned rows and maps each root onto its candidate. The cost is lineage depth times the search limit; the plan measures it with a deep lineage in an integration test.

**Init-only records.** `ReasonletCandidate` and `ReasonletMatch` become `sealed record` types with `required` init properties and a `Validate()`, as `ReasonletDefinition` is. `ReasonletEvidence` becomes a `readonly record struct` with `required` init properties. Every construction site in `src`, tests, the AOT smoke program and docs moves to object initialisers.

**Labels are opaque.** The docs say a version label is for display and ordering inside one lineage: callers must not parse it. The store keeps generating `1.k`. The Concepts page `versions.md` states this and defines `LineageId`.

**Proof.** A test-only `LineageVariantSelector : IReasonletSelector` in `tests/Mnemosyne.NET.Tests` decorates `ReasonletSelector`, groups the ranked candidates by `LineageId` and returns one match per lineage, chosen by a deterministic rule. It uses only public types. It shows that variant selection needs no further change to the abstractions: if writing it needs a new member, 4.2 adds that member.

**Telemetry.** The recall span and the `FindProcedure` function output carry the lineage id next to the Reasonlet id, so the audit trail of which Reasonlet influenced an answer names its lineage. Check `RecallTelemetry` and `FindProcedureFunction` for the cleanest place; this is an addition to tags and JSON, covered by their tests.

## Tests

- Unit: `Validate()` for the three converted types; `ReasonletSelector` copies `LineageId`; the test-only `LineageVariantSelector` picks one match per lineage and keeps a root and an unrelated Reasonlet apart.
- Integration (PostgreSQL): a root, two siblings and a grandchild all report the root's id; a version whose parent was erased reports its own id; a deleted-and-recreated parent does not leak across scopes; the search still honours `limit` and the intent filter.
- Regression: the AOT smoke program builds and runs with the new initialisers; the four samples still pass in CI.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The walk-up slows the search | Slower recall | A second query after the index scan, so the index is untouched; a deep-lineage integration test; 4.3 benchmarks recall latency |
| A cycle in `parent_id` makes the walk run forever | Hang | Use `UNION` as `WalkUpAsync` does, so a repeated link ends the walk |
| Converting records breaks callers outside this repo | Thalos or Daedalus adapters fail to build | Pre-1.0 and announced in the release notes with a `BREAKING CHANGE` footer; the Thalos and Daedalus adapter PRs are checked for constructions of these types before the commit lands |
| A test selector reveals a missing member | Scope grows | Add the member in 4.2, since 4.4 freezes the API after it |
