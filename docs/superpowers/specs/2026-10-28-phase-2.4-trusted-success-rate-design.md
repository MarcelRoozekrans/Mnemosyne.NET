# Phase 2.4 Design: Trust-weighted success rate and match evidence

**Date:** 2026-10-28
**Phase:** 2.4
**Surface:** Data
**Stage:** phase (one phase, implementation-ready)

This phase builds on the [phase 2.1 evaluator contract](2026-10-23-phase-2.1-evaluator-contract-design.md) and the [phase 1.6 selector](2026-10-23-phase-1.6-selector-ranking-design.md). Decisions are marked **user** or **my call**.

## Why the phase changed

The roadmap's goal for 2.4 was "metrics computed from evaluated executions, with a minimum run count, feeding the success-rate term". Most of that already holds:
- Since phase 2.1, the counters count each run's effective verdict: a person's `Worked`, else the judge's verdict, else the agent's own.
- Since phase 1.6, the smoothing prior acts as the minimum run count.

Two gaps remain (**user**: do both):
1. **Trust.** A run that only the agent vouched for counts the same as one a judge or a person confirmed. An agent that always reports success inflates its own procedures.
2. **Evidence**, which is issue #9. A recall match carries one smoothed rate. The agent cannot tell 200 runs from 1 run plus an inherited prior.

## Goal

- **Trust-weighted rate.** The success rate weighs a judged run fully, and an agent-only run at a configurable weight.
- **Evidence.** Every recall match carries the evidence behind its rate.

## Non-goals

- **Using `ReasonletEvaluation.Score` in ranking.** Success stays binary. A graded score is a separate decision.
- **Time-decayed success rates.** Freshness already covers recency.
- **New telemetry signals.**
- **The rest of the milestone 4 API review.** This phase settles #9 only.

## Definitions

- **A judged run** is a run whose `evaluated_success` or `feedback_worked` is non-null. Its verdict came from a judge or a person.
- **An agent-only run** is any other run. Its effective success is the agent's own `agent_success`.
- **A judged success** is a judged run whose effective `success` is true.

## Approach

### Counters (my call)

Migration `0003_judged_counters.sql` adds two columns to `mnemosyne.reasonlet_metrics`: `judged_runs int NOT NULL DEFAULT 0` and `judged_successes int NOT NULL DEFAULT 0`. They are totals of record, like `runs` and `successes`, so a prune keeps them. The migration also:
- sets `schema_version` to 3, and the store's `SchemaVersion` constant becomes 3;
- adds CHECK constraints on the metrics row:
  - `0 <= judged_runs <= runs`;
  - `0 <= judged_successes <= judged_runs`;
  - `judged_successes <= successes`;
  - `successes - judged_successes <= runs - judged_runs`, so agent-only successes never exceed agent-only runs (**my call**, raised by the builder check: the first three rules alone allow a row whose agent-only successes exceed its agent-only runs).

The existing counters have no CHECKs. The new ones apply to the new columns only, so that a bug in their upkeep fails loudly.

**Backfill (my call).** The migration sets both counters from the executions still stored: `count(*) FILTER (WHERE judged)` and `count(*) FILTER (WHERE judged AND success)`, per Reasonlet. Pruned runs can no longer be judged, so they count as agent-only. That understates trust, which is the safe direction: an older procedure's rate leans on its prior slightly more. This choice is documented in the migration and the guide.

### Upgrading (user: a stop-the-world upgrade)

**The problem.** Today the store's version gate accepts any schema at or above its own. A pre-2.4 binary therefore keeps running against schema 3, and it doesn't maintain the judged counters.

**The upgrade order.** As with 0002, it is documented as stop the old instances, migrate, then start the new ones.

**The CHECKs stay.** An old instance left running fails loudly on the feedback and erase paths, which would break a CHECK, rather than corrupting data.

**Locking out old binaries later.** Migration 0003 also records a setting, `min_binary_schema`, with value 3.
- From this phase on, the store's version check also requires `min_binary_schema <= SchemaVersion`, where `SchemaVersion` is the binary's own constant. When the setting is above it, the store returns `Unavailable` with a message saying the binary is too old for the database.
- A missing setting counts as 0.
- A later migration that old binaries must not write through raises the setting, and those binaries then refuse themselves. Binaries built before 2.4 cannot read it, which is why this upgrade is still stop-the-world.

### Writers (my call)

Every statement that changes `runs` or `successes` keeps the new counters in step, in the same statement and under the same locks. The lock order stays Reasonlets, then executions, then metrics.

- **Append and remember's first run** (`ExecutionRepository.InsertSql`):
  - `judged_runs` gains 1 when the run arrives with an evaluation;
  - `judged_successes` gains 1 when that run's effective success is true.
- **Feedback** (`RecordFeedbackAsync`, then the metrics update). `LockExecutionForFeedbackAsync` must also return the run's judged state before the change, from `evaluated_success` and `feedback_worked`. The metrics update must also run when only the judged state changed, not just when `success` changed.
  - The update compares the run before and after, using both its judged state and its effective success.
  - `judged_runs` gains 1 when an agent-only run becomes judged, which happens when it gets a non-null `Worked`. It never loses one, because feedback cannot retract a verdict.
  - `judged_successes` moves by the change in "judged and successful".
  - `successes` keeps its existing raise and lose rule.

  The two counters move together whenever either changes. The spec does not prescribe whether this happens in the existing Raise and Lose statements or in one combined statement. It does require that a run going from agent-only to judged updates the judged counters even when its effective success did not change.
- **Subject erase** (`DeleteForErasureAsync`): the `removed` CTE also counts the deleted judged runs and judged successes per Reasonlet, and `subtracted` subtracts them.
- **Prune**: no change. It never touches counters.

### Ranking (user: weight 0.5, configurable)

`ReasonletRankingOptions.AgentVerdictWeight` is a `double` in [0, 1], default 0.5, validated like the other weights. The selector computes, for a metrics row:

```
agentRuns      = Runs - JudgedRuns
agentSuccesses = Successes - JudgedSuccesses
weightedRuns      = JudgedRuns + w * agentRuns
weightedSuccesses = JudgedSuccesses + w * agentSuccesses
rate = (weightedSuccesses + k * prior) / (weightedRuns + k)
```

- `w = 1` reproduces today's rate exactly. `w = 0` uses judged runs only.
- The parent prior uses the same weighting (my call). It is still `max(smoothed parent rate, 0.5)`.
- The weights in the total stay as they are.

### Evidence (user: a separate record on the match)

There is a new public record struct in Abstractions:

```csharp
public readonly record struct ReasonletEvidence(int Runs, int JudgedRuns, bool UsesParentPrior);
```

- `Runs` and `JudgedRuns` are the candidate's own counters.
- `UsesParentPrior` is true when the prior came from the parent, that is, when the parent's smoothed rate was above 0.5. Otherwise the neutral 0.5 was used.
- `Validate()` requires `0 <= JudgedRuns <= Runs`.

`ReasonletMatch` becomes `ReasonletMatch(ReasonletDefinition Reasonlet, ReasonletScore Score, ReasonletEvidence Evidence)`. Its `Validate` checks the evidence too. This breaks custom `IReasonletSelector` implementations, which must now supply evidence, so it ships as `feat!:` before 1.0.

### Metrics record (my call)

`ReasonletMetrics` gains `int JudgedRuns = 0` and `int JudgedSuccesses = 0`, appended with defaults so existing call sites still compile. `Validate()` adds four rules, matching the CHECKs:
- `JudgedRuns` is in [0, Runs];
- `JudgedSuccesses` is in [0, JudgedRuns];
- `JudgedSuccesses <= Successes`;
- `Successes - JudgedSuccesses <= Runs - JudgedRuns`.

**Stores must supply the counters (user).** The `IReasonletStore` contract docs say a store must fill in `JudgedRuns` and `JudgedSuccesses`. Zero is the valid value for "nothing judged", and a store that leaves them at zero ranks every run as agent-only.

The search query selects both counters for the candidate and its parent, and `CandidateRow` and the mapping carry them.

### Docs

`docs/concepts/ranking.md` explains the weighting, the evidence and the backfill. The PostgreSQL guide mentions migration 0003. Issue #9 is closed by this phase.

## Tests

- **Selector:**
  - `w = 1` gives exactly the phase 1.6 rate for random metrics.
  - `w = 0` ignores agent-only runs.
  - `w = 0.5` gives the hand-computed value for a mixed row.
  - The parent prior uses the weighting.
  - `UsesParentPrior` is true exactly when the parent's smoothed rate exceeds 0.5.
  - Evidence carries the candidate's own counters.
- **Options:** `AgentVerdictWeight` below 0, above 1 or NaN fails validation.
- **Records:**
  - `ReasonletMetrics` validation covers each of the three new rules.
  - `ReasonletEvidence` validation.
  - `ReasonletMatch` validates its evidence.
- **Store** (against pgvector):
  - A judged append, an agent-only append, and a remember with and without a judge each move the counters correctly.
  - Feedback that turns an agent-only run into a judged one keeps the same effective success but adds a judged run.
  - Feedback that flips a judged verdict moves `judged_successes`.
  - A subject erase subtracts the judged counts.
  - Prune leaves them.
  - Every existing invariant helper recomputes the judged counters from the executions and agrees.
  - The CHECKs reject an impossible row.
- **Version gate:** a database whose `min_binary_schema` is above the binary's `SchemaVersion` makes the store return `Unavailable`. A missing setting passes.
- **Migration:** a database at schema 2 with judged, agent-only and feedback-judged runs is upgraded, and the backfill matches the executions. Its version string reads 3.
- **End to end:** an agent-only success and a judged failure on two otherwise equal procedures rank the judged one by its weighted rate as computed.
- **AOT:** the smoke still passes, and its recall asserts that the evidence is present.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| A writer path misses the new counters | Wrong rates, then a CHECK violation at runtime | Every invariant helper recomputes the judged counters, and the CHECKs fail loudly in tests |
| Feedback's agent-only to judged transition without a change in effective success is missed | Under-counted trust | A dedicated test for exactly that case |
| The default 0.5 changes rankings for existing hosts on upgrade | Procedures with only agent-reported success drop relative to judged ones | Intended; documented in the release notes and ranking docs, and `AgentVerdictWeight = 1` restores the old behaviour |
| The breaking `ReasonletMatch` change | Custom selectors stop compiling | `feat!:` before 1.0, and the docs show the new member |
