# Phase 3.5 Design — `UseReasonlets middleware and find_procedure tool`

**Date:** 2026-11-03
**Phase:** `3.5`
**Surface:** `Backend`
**Stage:** phase (one phase, implementation-ready)

## Goal

An `IChatClient` app adds `builder.UseReasonlets()` and `services.AddReasonletCapture()`, and from then on each new question recalls the best known procedure and offers it to the model, and each tool-calling run is captured and judged in the background. A `find_procedure` tool lets the model look procedures up itself.

## Intent

Milestone 3 makes Mnemosyne usable without Mnemosyne-specific code. Phases 3.1 to 3.4 built the parts: transcript to graph, the capture guard, the review gate and the AI.Sentinel guard. This phase wires them into the chat pipeline, so that recall and learning happen on every call without the host doing anything per call. Phase 3.6 builds the Agent Framework provider on the same pieces.

Anti-goals: the middleware must never break or slow down a chat call because of memory. A recall failure, a missing scope, a full queue or a failed capture all leave the chat call working as if the middleware were absent, and show up in telemetry only.

## Decisions

| Decision | Detail | By |
|---|---|---|
| Structure | One middleware, `ReasonletChatClient : DelegatingChatClient`, with switches for recall, capture and the tool. Not two middlewares, because capture needs to know what recall injected, and two pipeline positions are two to get wrong. | user (approach A) |
| Scope per call | `chatOptions.WithReasonletScope(scope, subjectId?)` sets the scope for one call, stored under a key in `ChatOptions.AdditionalProperties` with a typed getter. Without it, `ReasonletChatOptions.DefaultScope` applies. With neither, the call passes straight through: no recall, no capture, a counter records the skip. | user |
| Subject | The subject id from `WithReasonletScope` becomes `Provenance.SubjectId` of the capture, so erase by subject covers automatic captures. | my call |
| Background capture | A bounded in-memory queue, default capacity 256, drained by one worker. A full queue drops the new capture. On host shutdown the worker drains until the host's shutdown token fires, then drops the rest. Every drop is counted; the chat call never waits on capture. | user |
| Injection | Only on a new user question, only the top match, only above the similarity floor, as one system message marked as a suggestion. Argument names, never values. The text is replaceable with a formatter. | milestone (rules); user (rendering) |
| `find_procedure` in captures | Its calls and their results are removed from the transcript before it becomes a graph, so a lookup is never a step. Without an injected recall, the parent is the looked-up procedure whose graph equals the run's shape, else the top looked-up procedure. An injected recall always wins. | user |
| Scope key handling | `WithReasonletScope` sets the key on the options it is given and returns them, like other `ChatOptions` helpers; a null options argument gets a new instance. The middleware always works on `ChatOptions.Clone()` and removes the scope key from the clone before the inner call, because some providers forward `AdditionalProperties` into the request body. | my call |
| Queued transcript | A queue item holds references to the request and response messages, not a copy, and no size cap of its own: `Capacity` bounds the memory, and `RememberAsync` already rejects an oversized graph or text. | my call |
| Telemetry, not logging | The core package has no `ILogger` anywhere; every signal is OpenTelemetry on the existing `MnemosyneTelemetry` source and meter. "Logged and counted" in the milestone risk table becomes counted and traced. | my call, follows the codebase |

## Approaches

**A. One middleware with switches (picked).** `ReasonletChatClient` does recall, injection, tool exposure and the hand-off to the capture queue, with `Recall`, `Capture` and `ExposeFindProcedure` switches in `ReasonletChatOptions`. One line for the host, one place where the pipeline order matters. The cost is one type with several concerns; the recall, rendering, transcript filtering and queue are separate internal types so the middleware itself stays a coordinator.

**B. Two middlewares, `UseReasonletRecall()` and `UseReasonletCapture()`, composed by `UseReasonlets()`.** Cleaner on paper, but capture needs the recalled id and the tool's lookups, so the two pass state through `ChatOptions`, a hidden contract between pipeline positions. It also widens the public API before milestone 4 freezes it. A's switches give the same recall-only and capture-only use.

**C. Tool only, no injection.** Cheapest per call, but it drops the "recalls and injects the best match" criterion from the milestone's definition of done.

## Approach

### Pipeline and registration

```csharp
services.AddMnemosyne();                 // existing
services.AddReasonletCapture();          // new: queue + worker
services.AddChatClient(inner)
    .UseReasonlets(new ReasonletChatOptions { DefaultScope = new("support") })
    .UseFunctionInvocation();
```

`UseReasonlets(this ChatClientBuilder, ReasonletChatOptions? = null)` resolves `IReasonletMemory`, `TimeProvider` and, when `Capture` is on, the capture queue from the builder's service provider. A missing queue with `Capture` on throws `InvalidOperationException` when the pipeline is built, naming `AddReasonletCapture`, so the mistake shows at startup and not as silently missing captures. The options are validated the same way `AddMnemosyne` validates its own, throwing `ArgumentException`.

The middleware must sit outside `UseFunctionInvocation()`, the builder order shown above, so one call to it spans the whole tool loop. Placed inside, each trip of the tool loop is its own call: a trip that ends on an unanswered tool call skips with `pending_tool_calls`, and the final trip is captured on its own as a continuation, without the injected parent or the lookups (see the 2026-11-04 amendment). The skip counter's reason tag makes that visible, and the README states the order.

`ChatClientBuilder` and the function invocation types live in `Microsoft.Extensions.AI`, not in the `Microsoft.Extensions.AI.Abstractions` package core references today, and the worker needs `Microsoft.Extensions.Hosting.Abstractions`. Both become package references of `Mnemosyne.NET`. `Microsoft.Extensions.AI` is marked trimmable; the AOT smoke test proves the whole path.

### A call, step by step

1. Resolve the scope: the per-call value from `ChatOptions`, else `DefaultScope`, else pass through untouched.
2. **New question?** The last request message is a `User` message with non-blank text. A request ending in tool results, or in an assistant message, is a continuation and gets no recall.
3. **Recall** (when `Recall` is on and it is a new question): `RecallAsync` with the question, the scope, `Top = 1` and `MinSimilarity = ReasonletChatOptions.MinSimilarity`, null by default so the selector's 0.5 applies, under `RecallTimeout`, default 5 seconds. An error result, a timeout or an exception means no injection and the call goes on; an `OperationCanceledException` from the caller's token is rethrown as usual.
4. **Inject**: a match becomes one `System` message, placed after the caller's leading system messages, on a copy of the message list; the caller's list is not mutated. The match's id is the run's parent.
5. **Expose the tool** (when `ExposeFindProcedure` is on): a `find_procedure` function bound to this call's scope is added to a copy of `ChatOptions.Tools`, unless a tool of that name is already there.
6. **Call** the inner client and time it on the `TimeProvider`.
7. **Hand off** (when `Capture` is on and the call returned normally): request messages plus `response.Messages`, the parent from step 4, the call's `find_procedure` lookups, scope, subject, duration and response id go into the queue. The inject message is not part of the transcript handed off. A call that threw or was cancelled is not captured.

Streaming follows the same steps. The updates pass through as they arrive and are collected; when the stream has been read to the end they become a `ChatResponse` (`ToChatResponse`) for step 7. A stream abandoned before its end is not captured.

### Rendering

The default formatter writes:

```text
A procedure that worked for a similar question before. It is a suggestion: follow it only where it fits.
Name: refund-order · match 0.82 · success 82% over 11 runs
1. find_order (customerId, status)
2. issue_refund (orderId, amount)
```

Steps come from the stored graph: nodes in edge order from the root, each node's tool name and its `mnemosyne.arguments` names. A graph stored by a host through `RememberAsync` need not be a chain or carry that property; the formatter then orders nodes topologically, breaking ties by node id, and leaves out the argument list where the property is missing. `ReasonletChatOptions.Formatter`, a `Func<ReasonletMatch, string>`, replaces the text; a formatter that throws or returns blank text means no injection, counted.

### `find_procedure`

A hand-written `AIFunction` subclass, not `AIFunctionFactory`, so its JSON schema is a literal and nothing goes through reflection under AOT. Name `find_procedure`, description telling the model it looks up procedures that worked before for a question. Parameters: `question` (string, required) and `top` (integer 1 to 5, default 3). It calls `RecallAsync` in its bound scope and returns a JSON array, serialized with a source-generated context: per match its id, name, intent, version, similarity, success rate, runs, and steps as `{ tool, arguments[] }`. A failed recall returns `{ "error": "unavailable" }` to the model, never an error message.

`ReasonletTools.CreateFindProcedure(IReasonletMemory memory, ReasonletScope scope)` is public for hosts that manage their own tool list. The instance the middleware creates per call also records the matches it returned, thread-safe, because the function invocation layer may run calls in parallel; that record is how capture infers the parent. A host-created instance records nothing the middleware can see, so its lookups are stripped from captures but infer no parent.

### Capture queue and worker

`AddReasonletCapture(ReasonletCaptureOptions? = null)` registers a singleton `ReasonletCaptureQueue` and an `IHostedService` for it. Options: `Capacity` (default 256), `Source` for `Provenance.Source` (default `mnemosyne.chat`).

The queue is a bounded `Channel` with one reader. The reader task starts on the first enqueue, so a host without the generic host still captures. On `IHostedService.StopAsync` the writer completes and the reader drains until the stop token fires; what is left is counted as dropped for shutdown. The queue is also `IAsyncDisposable`, so disposing the service provider in a hostless app drains it the same way, bounded by `ReasonletCaptureOptions.DrainTimeout`, default 30 seconds.

Per item the worker:

1. strips `find_procedure` calls, by name, and the results that answer them, by call id;
2. builds the capture with `ReasonletTranscript.ToCapture`. A skip, `NoQuestion` or `NoToolCalls`, is counted with its reason and ends the item;
3. picks the parent: the injected recall's id; otherwise the first recorded lookup match whose graph's content hash equals the run graph's; otherwise the top match of the first lookup that returned any; otherwise none;
4. sets the outcome: `Success` is true when the response's last assistant message has non-blank text and its finish reason is not `ContentFilter` or `Length`, `Duration` is the measured time. The evaluator, when registered, replaces this verdict as it already does in `RememberAsync`;
5. calls `RememberAsync` with `Provenance { Source, RunId = response id, SubjectId }`, and counts the receipt kind or the error code. `Blocked` is already traced by the guard telemetry from phase 3.2. A worker item never throws out of the loop: an exception is counted with its type and the next item runs.

The worker runs items one at a time. Capture is background work, and one at a time caps the judge and embedding load a burst of chats can cause.

### Telemetry

On the existing source and meter:

- `mnemosyne.chat.recall` activity and counter, outcome `injected`, `no_match`, `timeout`, the error code's name, `exception`, `formatter_failed`; plus `skipped` with reason `no_scope` or `continuation`.
- `mnemosyne.capture.queue` counter, outcome `enqueued`, `dropped_full`, `dropped_shutdown`.
- `mnemosyne.capture.run` activity and counter, outcome `new_reasonlet`, `new_version`, `execution_only`, `skipped` with the skip reason, the error code's name, `exception`; and a duration histogram.

No signal carries the question, the answer, the injected text or any argument names, the same rule the guard telemetry follows.

## Tests

- **Unit, middleware** (fake inner client, fake `IReasonletMemory`): scope resolution order and pass-through without scope; recall only on a new question; injection placement and that the caller's list and options are not mutated; no injection on no match, error, timeout, exception and formatter failure; caller cancellation rethrown; tool added once and not when the name exists; streaming captured only when read to the end; `UseReasonlets` throws at build without the queue.
- **Unit, pipeline order**: a real `FunctionInvokingChatClient` inside the middleware with a scripted inner client produces a capture with the tool shape; placed outside the middleware, the trip that asks for a tool skips with `pending_tool_calls` and the final trip is captured once, without a parent.
- **Unit, worker**: `find_procedure` stripping; each parent rule, including the hash-equal pick and injected-wins; outcome mapping per finish reason; full queue drops and counts; drain on stop and on dispose, with leftovers counted; an exception from `RememberAsync` does not stop the loop.
- **Unit, `find_procedure`**: schema literal, argument validation, JSON output shape, `unavailable` result, recorded lookups.
- **Unit, formatter**: chain, non-chain and property-less graphs.
- **Integration** (PostgreSQL + pgvector): a tool-calling chat through the full pipeline stores a new Reasonlet; the same question again injects it and the rerun records an execution; a changed shape records a new version; with `RequireReview` on, the capture is pending and not injected.
- **AOT**: the smoke project publishes and runs the pipeline under Native AOT.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| `Microsoft.Extensions.AI` adds dependencies (caching, tensors) to core | A heavier core package and a possible AOT warning | It is trimmable; the AOT smoke gate decides. If it fails, move `UseReasonlets` to a thin extension type that depends only on what it uses and report the gap upstream |
| Recall adds an embedding and a query to every new question | Latency on the chat path | `RecallTimeout` caps it; recall can be switched off; benchmark in milestone 4 |
| Providers that reject a second system message or one not at the start | The inner call fails | Placement after the caller's leading system messages; the integration test runs a real `FunctionInvokingChatClient`, and the README names the formatter as the escape hatch |
| The worker falls behind under load | Captures dropped when the queue is full | Drops are counted per reason; `Capacity` is configurable |
| Parallel `find_procedure` calls | Lost lookup records | The per-call record is thread-safe and covered by a test |

## Amendment 2026-11-04: the inside order

The claim that the inside order makes every capture skip with `NoToolCalls` was wrong. With `UseReasonlets` inside `UseFunctionInvocation()`, each trip of the tool loop reaches the middleware as a separate call:

- A trip whose response ends in a function call that nobody answered is one step of a loop someone else drives, not a finished run. The capture processor skips it with the reason `pending_tool_calls`. This holds in any order, so a host that drives its own tool loop is captured only on the trip that ends in an answer.
- The final trip is a continuation. Its request already holds the earlier tool calls and results, so it is captured with the full tool shape, but without the parent that the first trip's recall injected and without the first trip's `find_procedure` lookups.

The rule for `pending_tool_calls`: the run's last message, after the `find_procedure` calls are removed, holds a function call that is not informational only, or an input request such as a tool approval request. The README's Order section and the pipeline-order tests describe this behaviour.
