# Phase 5.1 Design — Variant selection

**Date:** 2026-11-07
**Phase:** 5.1
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)
**Status:** approved 2026-11-07

## Goal

A host opts in to variant selection and recall returns one variant per lineage, the best one by the default ranking, so sibling versions of one procedure stop crowding out other procedures. Selection is deterministic. Exploration comes in phase 5.2.

## Approach

`VariantSelector` is a public sealed class that implements `IReasonletSelector` and wraps another one (the milestone's approach 1; see the [milestone design](2026-11-07-milestone-5-design.md)). It has one public constructor taking the inner selector. `RankAsync` does four things:

1. Calls the inner selector with the same candidates and `Top` raised to the candidate count (at least 1), so the inner cut-off and ordering apply to every variant.
2. Walks the ranked matches best first and keeps the first match of each `LineageId`.
3. Takes the first `query.Top` of those. Their order is the inner order, so ties stay deterministic.
4. Returns the inner selector's error unchanged when it fails. Cancellation throws, as the port says.

This is the test-only `LineageVariantSelector` made public, with its `MaxTop = 50` workaround removed. Because the inner selector scores every variant, the default policy is "best default score wins in its lineage"; a new version with a parent prior competes on the prior already.

`AddMnemosyneVariantSelection(this IServiceCollection)` decorates the registered `IReasonletSelector`. It must run after `AddMnemosyne` and throws `InvalidOperationException` when no selector is registered. It wraps whatever is registered, so a host's own selector is grouped too. A second call is a no-op, detected through a marker singleton. `AddMnemosyne` and `ReasonletSelector` do not change.

Telemetry: the selector tags `Activity.Current`, the `mnemosyne.recall` activity the facade has open while it ranks, with `mnemosyne.recall.variant.lineages` (the lineages returned) and `mnemosyne.recall.variant.dropped` (the variants left out because a better sibling won). Counts only. The tags are set through a null-conditional call, so no listener means no cost. The constants live next to the other recall tags.

The test-only `LineageVariantSelector` and its tests are removed, and the real selector gets the tests. The sentence in `docs/concepts/variants.md` that points to the test class is reworded to point to the real selector; the full docs rewrite is phase 5.3.

## Decisions

| Decision | Detail | By |
|---|---|---|
| Opt-in through a service extension, not an option on `MnemosyneOptions` | It wraps a registered selector, so it composes with a custom one and needs no change to the 1.0 options type | my call |
| No options class yet | Nothing in 5.1 is configurable. Phase 5.2 adds `VariantSelectionOptions` and an overload | my call |
| Grouping uses the inner score | One policy, no duplicated comparator, and the inner cut-off still applies | my call |

## Tests

- Unit: one variant per lineage; the best by the inner score wins; `Top` applies after grouping; the cut-off drops a lineage whose variants are all below it; an empty candidate list; two lineages interleaved; ties are stable; inner failure passes through; cancellation throws; a null argument throws.
- Registration: after `AddMnemosyne` the resolved selector groups; a custom selector is wrapped; before `AddMnemosyne` it throws; a second call is a no-op.
- Telemetry: with an `ActivityListener`, the recall activity carries both tags with the right counts, and no tag carries content.
- Surface: a test that references every new public type, for the phase 5.2 guard.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| `Activity.Current` is not the recall activity when a host calls the selector directly | Tags land on another activity | The selector tags only when `Activity.Current` is a `mnemosyne.recall` activity |
| Grouping drops a good match from an unrelated procedure that shares a lineage | Fewer results | Lineages are per scope and follow `ParentId`; documented under Limits in the variants page |
