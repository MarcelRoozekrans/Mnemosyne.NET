# Phase 4.7 Design — 1.0.0 release

**Date:** 2026-11-06
**Phase:** 4.7
**Surface:** Infra
**Stage:** phase (one phase, implementation-ready)
**Status:** approved 2026-11-06

**Builds on:** Phase 4.4 — the `PublicAPI.Shipped.txt` baselines and the CI step that asserts every baseline is non-empty. Phases 4.1 to 4.6 are merged before the release PR is merged.

## Goal

Mnemosyne.NET 1.0.0 is on nuget.org, cut by release-please and published by the existing `publish-nuget` job, and `EnablePackageValidation` against baseline 1.0.0 then guards every later release. Nobody tags by hand.

## Why

The milestone definition of done ends on "1.0.0 is on NuGet, released by release-please". Two things stand in the way. First, `release-please-config.json` has `bump-minor-pre-major` and the manifest is at 0.7.0, so the breaking changes of 4.2 and 4.4 would propose 0.8.0, not 1.0.0. Second, 4.4 deferred package validation to this phase, because the baseline it needs is 1.0.0 itself, which cannot be restored before it exists.

## Approaches considered

| Decision | Choice | Rejected |
|---|---|---|
| Trigger | **A `Release-As: 1.0.0` footer** in the squash commit of the final phase PR. One-off, and it leaves the config alone. By the user. | `release-as` in the config (stays set after the release and pins every later release unless a follow-up removes it); dropping `bump-minor-pre-major` (implicit, rides on the breaking markers surviving the squash). |
| Package validation | **Two steps.** Step A ships 1.0.0. Step B, after 1.0.0 is on nuget.org, a small PR enables `EnablePackageValidation` with `PackageValidationBaselineVersion` 1.0.0 and shows it failing on a deliberately breaking change. The phase completes after step B. By the user. | Enabling it in the release PR guarded by an MSBuild condition (the condition silently skips forever if never removed); deferring to milestone 5 (the definition of done lists it). |
| Tagging | **Never by hand.** release-please makes the tag and the GitHub release; the release's `published` event starts `ci.yml`; `publish-nuget` packs and pushes the tag. Existing design, unchanged. | Any manual `git tag`. |

## Approach

**Step A, the release.**
1. **Verify the trigger before the last PR.** Run release-please in dry-run against a scratch branch or read its action output on a PR: with a `Release-As: 1.0.0` footer on a commit after 0.7.0, the release PR must propose 1.0.0. Record how it was verified in the phase PR. If the squash-merge message setting of the repository drops the PR body, find the setting (`gh api repos/{owner}/{repo}` fields `squash_merge_commit_title` and `squash_merge_commit_message`) and put the footer where it survives; an unproven footer is a blocker, not an assumption.
2. **Final phase PR.** The phase's own PR is the last functional PR before the release. Its squash commit has the conventional subject (for example `chore: prepare 1.0.0`), a body, and the footer `Release-As: 1.0.0` as its last paragraph. Commitlint must pass on it.
3. **Pre-release checklist**, as a short task list in the PR and the plan: every package README states the 1.0 status and links the docsite; `PackageProjectUrl`, `RepositoryUrl`, license and `PackageReadmeFile` are set on every packable project (the pack rehearsal already asserts one package per source project); the docsite is deployed from main; `CHANGELOG.md` is left to release-please; the `GitVersion.yml` comment that calls 0.x deliberate is updated to say the first tag line is now stable.
4. **Merge order.** Marcel merges PR #62 and the phase PRs 4.1 to 4.6 first. Any open 0.8.0 release PR is not merged; once the footer lands, release-please rewrites it to 1.0.0. Marcel then merges that release PR. The `published` event runs `publish-nuget`, which refuses a prerelease and pushes exactly the tag's version.
5. **Verify the release.** `gh release view v1.0.0`, the six packages on nuget.org at 1.0.0 (query the flat container index), and a fresh consumer project restoring and building against them from nuget.org.

**Step B, the guard.** After 1.0.0 is on nuget.org: in `Directory.Build.targets`, conditioned on `IsPackable`, set `EnablePackageValidation` to true and `PackageValidationBaselineVersion` to 1.0.0. The `pack-validate` job already packs every package, so validation runs there. Prove it by hand on a throwaway branch: a deliberately breaking public change fails the pack with a package validation error, and the unchanged tree passes. Then land the real change. A baseline version that is not yet on nuget.org fails the restore, which is why this is a separate PR after the release.

**After 1.0.** `bump-minor-pre-major` has no effect from 1.0.0, so it stays. Mnemosyne follows SemVer from here: the analyzers and package validation hold the line, and `compatibility.md` states the policy.

## Files / Modules Touched

- Step A: the final phase PR's commit message and body; package READMEs where they lack the 1.0 note; `GitVersion.yml` comment. No functional change.
- Step B: `Directory.Build.targets`, `docs/concepts/compatibility.md` (a line saying package validation guards releases from 1.0.0).
- No change to `release-please.yml`, `ci.yml` or the config unless the dry run in step A.1 shows the trigger does not work, in which case the fix is chosen with the user.

## Tests

- Dry run of the trigger (A.1) before the final PR.
- Pack rehearsal and AOT gate green on the final PR.
- Post-release: the release exists, the six packages are at 1.0.0 on nuget.org, a clean consumer builds.
- Step B: breaking change fails, unchanged tree passes.

## Anti-goals

- **A hand-made tag or a manual NuGet push.** If the pipeline fails, fix the pipeline.
- **Merging for Marcel.** The agent prepares and verifies; Marcel merges the PRs and the release PR.

## Open Questions

- None. The squash-merge message setting is checked in the plan's first task, not assumed.
