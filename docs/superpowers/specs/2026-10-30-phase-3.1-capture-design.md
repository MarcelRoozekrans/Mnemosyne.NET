# Phase 3.1 Design: Capture

**Date:** 2026-10-30
**Phase:** 3.1
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)

The first phase of milestone 3. It builds on the [milestone 3 design](2026-10-30-milestone-3-design.md), whose "Graph content" decision fixes what a captured graph holds: the tools called, in order, with argument names but not values. Decisions are marked **user** (chosen by the user in the brainstorm) or **my call**.

## Goal

A chat transcript of `Microsoft.Extensions.AI` messages becomes a `ReasonletCapture`. Its graph is the tool shape of the last question's run. `RememberAsync` then stores it as a new Reasonlet, a new version or an execution of the recalled one.

## Intent

Phases 3.5 (the `UseReasonlets()` middleware) and 3.6 (the Agent Framework provider) both have to turn a run into a capture. This phase is the single shared path, so that both produce identical graphs for the same procedure. That matters because `RememberAsync` tells an execution from a new version by the SHA-256 of the graph's canonical form (`ReasonletPostgreSqlStore.cs:252`). If two runs of the same procedure produce different bytes, every rerun becomes a new version, and lineage fills with near-duplicates. That is the failure the milestone's graph-content decision exists to prevent.

## Goals

- One deterministic builder from `IEnumerable<ChatMessage>` to `ReasonletCapture`. Two runs with the same tool shape produce byte-identical canonical graphs, whatever the argument values, call ids, retries or the order of parallel calls.
- A transcript with nothing to capture yields a reason, never an empty capture.
- Against PostgreSQL, a same-shape rerun with the recalled Reasonlet as `ParentId` is stored as an execution, and a different shape as a new version.

## Non-goals

- **Calling `RememberAsync`** (**user**). The builder only builds. Storing stays a separate call, so that the 3.2 redaction hook can sit between building and storing.
- **Redaction.** Phase 3.2. The builder copies the question and answer text as they are.
- **A replaceable mapping port** (**user**, approach 1 over an injectable `IReasonletTranscriptMapper`). If two apps mapped the same procedure differently, hash matching would break. A port can be added before the milestone 4 API freeze if a real need appears.
- **Multi-question captures** (**user**). A capture covers only the last question. Phase 3.6 captures each turn of a thread as it ends.
- **Docsite pages.** Phase 3.7 covers every integration. This phase ships XML docs and a short section in the core package README.
- **Argument values, call counts or timings in the graph.** Values are excluded by the milestone decision. Counts are lost by collapsing, below.

## Approaches

| Approach | Trade-off | Outcome |
|---|---|---|
| 1. Pure static builder `ReasonletTranscript.ToCapture(messages, details)` returning `Result<ReasonletCapture, TranscriptSkipReason>` | Deterministic, no DI, exhaustively testable; not replaceable, but `RememberAsync` stays open to custom builders | **Chosen (user)** |
| 2. Injectable `IReasonletTranscriptMapper` port registered by `AddMnemosyne` | Replaceable per app, but adds public surface and lets apps diverge on graph shape, which breaks hash matching | Rejected |
| 3. Extension method `messages.ToReasonletCapture(details)` | Same logic as 1, more discoverable, but it extends a general M.E.AI type in every app that references core | Rejected |
| Capture-and-remember in one call on `IReasonletMemory` | Easiest to call, but it fixes the API before the 3.2 hook needs to slot in between | Rejected (**user**, scope question) |

## Public API (my call, within approach 1)

All of it lives in the core `Mnemosyne.NET` package, namespace `Mnemosyne.NET`. The package already references `Microsoft.Extensions.AI.Abstractions`; `Mnemosyne.NET.Abstractions` gains no M.E.AI dependency.

```csharp
public static class ReasonletTranscript
{
    public static Result<ReasonletCapture, TranscriptSkipReason> ToCapture(
        IEnumerable<ChatMessage> messages, TranscriptCaptureDetails details);

    // Exposed separately so tests, docs and later phases can see the shape alone.
    public static Result<ReasonletGraph, TranscriptSkipReason> ToGraph(IEnumerable<ChatMessage> messages);
}

public sealed record TranscriptCaptureDetails   // init-only, like the other records
{
    public required ReasonletScope Scope { get; init; }
    public required ReasonletProvenance Provenance { get; init; }
    public required ReasonletOutcome Outcome { get; init; }
    public ReasonletId? ParentId { get; init; }
    public string? Intent { get; init; }
    public string? Name { get; init; }
}

public enum TranscriptSkipReason   // numbered from 1; 0 stays undefined, as in MnemosyneErrorCode
{
    NoQuestion = 1,    // no user message with non-blank text
    NoToolCalls = 2,   // the last question's run has no successful tool call
}
```

- **The skip is not a `MnemosyneError`** (**user** chose "result with a reason"; the type is my call). "Nothing to capture" is not a failure of any input invariant, and filing it under `Validation` would blur the error codes the facade documents. Phase 3.5 counts skips by reason, and needs to tell "the middleware sits inside `UseFunctionInvocation()`" (`NoToolCalls` on every call) apart from a real error.
- **Null arguments** (`messages`, `details`, a null element in `messages`) throw `ArgumentNullException`. They are programming errors, not transcript content. This matches the facade, which validates records but never accepts null records.
- **No validation of the result.** The builder does not run `ReasonletCapture.Validate()`. `RememberAsync` validates every capture, and returns `Validation` for a graph that breaks a limit, such as more than 500 steps or a tool name over 256 code points. The builder documents this. Duplicating the checks would let the two drift.

## Transcript rules

### Which part of the transcript (user: last question onward)

1. The **question** is the last message with `Role == ChatRole.User` whose `Text` is not blank. `Question` is that `Text`. No such message gives `NoQuestion`.
2. The **run** is every message after the question.
3. The **answer** is the `Text` of the last `ChatRole.Assistant` message in the run whose `Text` is not blank, or null when there is none. A null answer means the evaluator does not judge, and the agent's verdict counts, as `RememberAsync` already documents.
4. Earlier turns are context and contribute nothing.

### Which calls count (user: failed calls left out)

- A **call** is a `FunctionCallContent` in a `ChatRole.Assistant` message of the run.
- **Pairing is by position** (my call, from the final review). Contents are read in message order. A `FunctionResultContent` decides the earliest undecided call before it with the same `CallId`. A result with no such call, such as one before its call or a second result for a decided call, is ignored. This keeps providers that reuse ids across rounds, such as `"0"` and `"call_0"`, from pairing a result with the wrong call.
- A call is **successful** when its result's `Exception` is null.
- Calls with no result are dropped. So are calls whose result carries an exception. This also covers calls marked `InformationalOnly`, which never get a local result.
- When several results follow one call, the first one counts (**my call**; this does not happen with `FunctionInvokingChatClient`).
- **A retry takes the failed call's place** (**user**, from the final review). A successful call with the same step key as an earlier failed call that has not been retried yet joins that failed call's assistant message before the sort. It also retires every failed call with that key up to its own message. Without this rule, a failure inside a parallel batch that is retried in the next turn would give `B, A` instead of the clean `A, B`, and fork a new version.
- A run with no successful call gives `NoToolCalls`.

### Graph shape

- **Step key.** Each successful call becomes a step keyed by its tool name (`FunctionCallContent.Name`) and the set of its argument names. The argument names are the keys of `Arguments`; null arguments mean an empty set. The names are sorted ordinally. Values are never read.
- **Parallel calls (my call).** Steps from one assistant message are sorted by tool name, then by their sorted argument names compared element by element (ordinal, a shorter prefix first). The order the model lists them in carries no meaning, so it must not reach the hash. Steps keep message order across messages.
- **Collapsing (user).** After sorting, consecutive steps with equal keys merge into one. This applies across message boundaries too, so paging through three pages in three turns is one step. A 2-page and a 3-page run are the same version.
- **Nodes (my call).** Steps are numbered from 1 in order. Each becomes `ReasonletNode { Id = "step-<n>", Type = "tool", Tool = <name>, Properties = { "arguments": [<sorted names>] } }`. `Name` stays null. `mnemosyne.arguments` is always present. The key is namespaced, because the graph schema reserves plain keys for later schema versions; it, as an empty array when the call has no arguments, so the form never depends on an optional member. Position-based ids are required because call ids differ on every run.
- **Edges (my call).** `step-n → step-n+1`, unconditional, no properties. The graph is a linear chain. One step means no edges.
- **Graph.** `SchemaVersion = ReasonletGraph.CurrentSchemaVersion`, no graph properties. This matches the shape the samples and `getting-started.md` already write by hand (`Type = "tool"`, `Tool = "orders.get"`). The only difference is the `mnemosyne.arguments` property, so hand-written graphs without it hash differently from captured ones. That is acceptable: a hand-written procedure is not a captured one's parent unless the caller makes it so, and then it becomes a new version, which is correct.

## Tests

- **Unit, shape.**
  - The question, answer and run boundaries above, including an empty transcript, no user message, a blank user text, and a trailing user message with no run.
  - Failed and unanswered calls are dropped.
  - Duplicate call ids.
  - Null and empty arguments.
  - Parallel calls listed in any order give one graph.
  - Collapse within one message and across messages.
  - Non-consecutive repeats stay separate (A, B, A gives three steps).
  - The same tool with different argument-name sets stays separate.
- **Unit, determinism.** Two transcripts that differ only in argument values, call ids, message ids, retries and parallel order produce equal `ComputeContentHash()` values. A transcript that differs in tool order, tool name or an argument name produces a different hash.
- **Unit, capture.** `details` fields reach the capture unchanged, and the answer is carried as-is. `ToString` of the capture still redacts the answer; this is existing behaviour, asserted again here.
- **Integration (PostgreSQL + pgvector).**
  - A captured transcript with no parent is a `NewReasonlet`.
  - A same-shape rerun with different argument values and that Reasonlet as `ParentId` is `ExecutionOnly`.
  - A rerun with one more tool is `NewVersion`.
- **AOT.** The smoke project calls `ToCapture` on a small transcript, so trimming warnings surface in the CI gate.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| A provider fills `FunctionResultContent.Exception` inconsistently, putting an error only in `Result` | A failed call counts as successful and enters the graph | Follow `FunctionInvokingChatClient`'s contract, which sets `Exception` on failure; document the rule; the evaluator still judges the run |
| Collapsing hides a real difference between procedures, such as "retry until done" versus "call once" | Two procedures share one version | Accepted (**user**): the milestone prefers fewer near-duplicates; ranking by judged success separates good runs from bad within a version |
| Sorting parallel calls hides a real dependency between calls listed in one message | None in practice | Calls in one message are issued together and cannot depend on each other's results |
| The `mnemosyne.arguments` property makes captured graphs differ from the hand-written graphs in the docs | A doc reader expects a hand-written parent to match a capture | Note the captured shape in the README section; phase 3.7 documents it fully |
