# Phase 3.3 Design: Human review gate

**Date:** 2026-10-30
**Phase:** 3.3
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)

The third phase of milestone 3. It builds on the [milestone 3 design](2026-10-30-milestone-3-design.md), whose "Review gate" decision fixes the outline: opt-in and off by default; when on, a new Reasonlet or a new version is stored as `ReasonletStatus.PendingReview` and stays out of recall until approved; an execution of an approved version needs no review. Decisions are marked **user** (chosen by the user in the brainstorm), **milestone** (fixed by the milestone design) or **my call**.

## Goal

With `MnemosyneOptions.RequireReview` on, every captured procedure that is new, or a new version, is stored pending and is not recalled. A reviewer lists what is pending in a scope, approves it into recall, or rejects it, which deletes it.

## Intent

Phase 3.5 makes capture automatic: every tool-calling run in an `IChatClient` pipeline may become a stored procedure that later steers other runs, for other users in the same scope. Some hosts want a person to sign off before a procedure can do that, for quality or for oversight. The redaction hook of phase 3.2 catches content that must never be stored. The review gate covers what is allowed but not yet trusted.

The gate must cost nothing to hosts that do not want it, so off-the-shelf use stays one line (**milestone**). A host that turns it on must be able to build a review screen on the facade alone, with no access to the store (**user**).

## Goals

- With the gate on, no new Reasonlet and no new version can be recalled before a reviewer approves it, and there is no moment when it can be.
- A reviewer can list a scope's pending Reasonlets with everything needed to judge them, and approve or reject each.
- A rejected Reasonlet's content is gone, not hidden (**user**).
- With the gate off, behaviour is exactly as today.

## Non-goals

- **Who reviewed, and why.** No reviewer identity or comment is stored or emitted. Recording a person's name is personal data the host already has in its own audit trail, and the milestone dropped the audit table (**my call**).
- **A `Rejected` status.** Reject deletes (**user**). A tombstone would keep the content that was often the reason for rejecting, and would not stop the same shape being captured again, since a capture without a parent is never deduplicated.
- **Per-capture or per-scope switches.** One global option (**my call**). A host that needs scopes treated differently runs two facades. It can be added later without breaking anything.
- **Review of executions.** An `ExecutionOnly` capture stores no new procedure (**milestone**).
- **Notifications.** No event per pending capture; a host polls the list call (**user**, chose the list call alone over list plus event).
- **A review UI or docsite guide.** Phase 3.7 covers the integration guides. This phase updates only the reference docs listed below.
- **Erase and retention changes.** Both already treat `PendingReview` like `Active`.

## Approaches

| Approach | Trade-off | Outcome |
|---|---|---|
| 1. Facade passes a "review required" flag on `ReasonletStoreEntry`; the store gives new Reasonlets and new versions `PendingReview` inside its existing atomic remember. Approve, reject and list go on `IReasonletStore` and `IReasonletMemory`. | One store port and one facade, as today. A breaking change for third-party stores, acceptable before the milestone 4 API freeze; PostgreSQL is the only store. | **Chosen (user)** |
| 2. The flag and status as in 1, but approve, reject and list go on a new `IReasonletReviewStore` port and `IReasonletReview` facade. | Stores without review stay valid, and turning the gate on with one fails at startup. More DI wiring and two more types to document. | Rejected (**user**) |
| 3. Facade stores as `Active`, then flips the status to pending after the receipt. | The store needs no flag, but the Reasonlet is recallable between the two writes, which breaks the first goal. | Rejected |
| 4. The switch on the store's options (`MnemosynePostgreSqlOptions`). | Every store re-implements the policy, and the off-the-shelf switch lives in the wrong package. | Rejected |

The facade cannot set the status itself, because only the store knows, inside its transaction, whether a capture is a new Reasonlet, a new version or an execution of the parent. So the facade passes the policy and the store applies it to what it decides.

## Decided behaviour

### The switch (**milestone** for opt-in, **my call** for the shape)

`MnemosyneOptions.RequireReview`, a `bool`, default `false`. `RememberAsync` copies it onto the store entry. Turning it on leaves existing `Active` Reasonlets active. Turning it off leaves existing pending Reasonlets pending until approved or rejected, and stores new captures as `Active`.

### Remember with the gate on

| Capture | Stored as | Receipt `Status` |
|---|---|---|
| No `ParentId` | new Reasonlet, `PendingReview` | `PendingReview` |
| `ParentId`, graph equal to the parent's | execution on the parent; the parent's status is unchanged | the parent's status, as today |
| `ParentId`, graph different | new version, `PendingReview`, whatever the parent's status | `PendingReview` |

Pending Reasonlets are excluded from `SearchAsync` and from nothing else (**my call**). `GetAsync`, `RecordExecutionAsync` and `RecordFeedbackAsync` work on a pending Reasonlet and its runs exactly as on an active one, and need no change.

A capture whose parent is pending is allowed (**my call**). Recall never returns a pending Reasonlet, so only a host that keeps the id from a receipt can do this. Its runs then count towards the pending Reasonlet's metrics, which is useful evidence for the reviewer. The parent's status never changes from a remember.

`ReasonletStoreEntry` gains `bool ReviewRequired = false` as its last positional parameter, so existing callers compile. The flag is policy, not a status, so a store cannot be asked to store a new version as `Active` while the gate is on.

### Approve (**my call**)

`ApproveAsync(scope, id)` sets a `PendingReview` Reasonlet to `Active`. It is recallable from the next query on. Approving an `Active` Reasonlet succeeds and changes nothing, so a retried approve is harmless. Errors: `Validation` for a `default` scope or id, `NotFound` when the id does not exist in the scope, `Unavailable` when the store fails.

A version can be approved while its parent is still pending. Its parent's metrics still feed ranking inheritance, as today: inheritance reads metrics, not status.

### Reject (**user** for delete, **my call** for the rest)

`RejectAsync(scope, id)` deletes a `PendingReview` Reasonlet with its executions, their feedback and its metrics, the way an erase deletes them. It answers:

- `Conflict` when the Reasonlet is `Active`. Removing a live procedure is erase's job, and a reject that raced an approve must not delete what the other reviewer just approved.
- `Conflict` when another Reasonlet has it as `ParentId`. The schema's `ON DELETE SET NULL (parent_id)` would otherwise orphan those versions silently, and one of them may be approved. The reviewer rejects or approves the versions below first. The error's message says which of the two conflicts it is, without content.
- `NotFound`, `Validation` and `Unavailable` as for approve.

Reject locks the row `FOR UPDATE` before it checks status and children. A remember that is adding a version below it holds the parent `FOR NO KEY UPDATE`, which conflicts, so the two serialize: a reject that runs second sees the new child and answers `Conflict`; a remember that runs second finds no parent and answers `NotFound`, as after an erase.

Because a Reasonlet with children cannot be rejected, a reject only ever deletes a leaf. It deletes it the way an erase deletes a leaf, in the same order as `LockForErasureAsync` and the erase path that follows it in `ReasonletPostgreSqlStore`: the Reasonlet row first, then its runs, then what cascades from them. Erase locks deepest first, so taking one leaf row is consistent with that order (**my call**). A deadlock or serialization failure maps to `Conflict` through `PostgresErrors`, as it does today.

Rejecting the highest version of a lineage frees its version label. The next new version is numbered from the rows that remain, so it can reuse the label, as it already can after an erase (**my call**). Ids are never reused, and a version label was never an identity.

### List pending (**user** for the call, **my call** for the shape)

```csharp
ValueTask<Result<IReadOnlyList<ReasonletReview>, MnemosyneError>> ListPendingAsync(
    ReasonletScope scope, int limit, ReasonletId? after, CancellationToken ct);

public sealed record ReasonletReview(ReasonletDefinition Definition, ReasonletMetrics Metrics);
```

Returns up to `limit` `PendingReview` Reasonlets in the scope, ordered by id. Ids are version 7 GUIDs, so this is creation order. `after` is the last id of the previous page, and `null` starts at the beginning. A `default` `after` answers `Validation`, like a `default` id elsewhere. `limit` is 1 to 100; anything else answers `Validation`.

Ids are made by the client with `Guid.CreateVersion7`, so they are not strictly monotonic across nodes, or within one millisecond. A Reasonlet that is stored while a reviewer is paging can land behind the cursor, and that pass misses it. The list is a work queue, not a feed: the contract says so, and a review screen starts again from `null` to see new items (**my call**). Ordering by `created_at` would not help. It is the database's `now()`, the start of the inserting transaction, so a transaction that started earlier can still commit after a page was read. Each item carries the definition and the Reasonlet's own metrics (**user**):
- The definition has the name, intent, version, graph, provenance, parent and creation time.
- The metrics are runs, successes, judged runs and judged successes, and the last run. They come from the metrics row that already exists, so a review screen can show a track record, such as "ran 12 times, 10 judged successes", next to the shape.

A Reasonlet without a metrics row gets zero counts and `LastExecutedAt` equal to its creation time, the fallback `ReasonletMetrics` already documents. The embedding is not returned. An empty list is a success. `ReasonletReview` is a new record in `Mnemosyne.NET.Abstractions` with a `Validate()` that nests both parts, like the other records.

A partial index, `(scope, id) WHERE status = 2`, in migration `0004_review.sql`, keeps the list cheap however many active Reasonlets a scope holds.

### Ports

`IReasonletStore` and `IReasonletMemory` both gain `ApproveAsync`, `RejectAsync` and `ListPendingAsync` with the signatures above. Approve and reject return `UnitResult<MnemosyneError>`. The facade validates its arguments and delegates; there is no guard, extractor, embedder or judge on these paths. Cancellation throws, as on every other method.

### Telemetry (**my call**)

The store runs each through `StoreTelemetry.RunAsync` as operations `approve`, `reject` and `list_pending`, so they get the shared activity, outcome, operation counter and duration like every other store operation. Approve and reject tag `mnemosyne.reasonlet.id`. List tags `mnemosyne.list.limit` before it runs and `mnemosyne.list.returned` after. A successful remember also tags `mnemosyne.reasonlet.status` (`active` or `pending_review`), so pending captures are visible in traces. No signal carries a name, intent, graph or provenance, per `MnemosyneTelemetry`'s rule.

## Tests

- **Unit, facade:** the flag follows `RequireReview`; approve, reject and list validate arguments and delegate; the receipt's status comes through.
- **Unit, options and entry:** the default is off; `ReviewRequired` defaults to `false`.
- **Integration (PostgreSQL):**
  - gate on: a new Reasonlet and a new version are pending, absent from `RecallAsync`, and present in `ListPendingAsync`; an execution against an active parent leaves it active;
  - gate off: as today;
  - approve makes it recallable; approving twice succeeds;
  - reject deletes the Reasonlet, its runs, feedback and metrics; rejecting an active one or one with a version below answers `Conflict` and deletes nothing;
  - `NotFound` for an id in another scope, for approve and reject;
  - list pages with `after` and `limit`, validates `limit` and a `default` `after`, and carries each item's metrics, including runs recorded against the pending Reasonlet and zero counts when there are none;
  - a reject racing a remember that adds a version below it ends in one of the two serialized outcomes above, never an orphan;
  - the migration applies on a database at `0003`.
- **Unit, telemetry:** the operations, tags and outcomes, and a canary string in the capture appears in no signal.
- **AOT smoke:** the gate path runs under Native AOT.
- **Regression:** the full existing suite passes, with fakes updated for the new port members.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Retention prunes a pending Reasonlet nobody reviewed | A backlog quietly disappears | Intended: unreviewed and unused is idle. Documented in the data-lifecycle guide beside the gate. |
| A third-party `IReasonletStore` breaks on the new members | Compile errors for that store | Acceptable before 1.0; called out in the `feat` commit and release notes. |
| A reviewer approves a version and then rejects its pending parent | Conflict, because the parent has a child | The error says so; the reviewer decides. Erase stays available for removing the parent anyway. |
| A busy scope's pending list grows without limit while the gate is on | Slow list, large review queue | The partial index keeps the query cheap; paging keeps each call bounded. |
