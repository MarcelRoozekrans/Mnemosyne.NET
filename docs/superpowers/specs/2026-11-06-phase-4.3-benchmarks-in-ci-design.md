# Phase 4.3 Design — Benchmarks in CI

**Date:** 2026-11-06
**Phase:** 4.3
**Surface:** Infra
**Stage:** phase (one phase, implementation-ready)
**Status:** approved 2026-11-06

**Builds on:** Phase 4.2 — `ReasonletCandidate` and `ReasonletMatch` as init-only records with `required ReasonletId LineageId`, and the PostgreSQL search that resolves the lineage in a second query after the nearest-neighbour select.

## Goal

A BenchmarkDotNet suite for ranking, search and middleware overhead runs in CI on every change to the code, and publishes its table where a reviewer sees it, without ever failing a build on a number.

## Why

The milestone asks for measured, repeatable numbers before 1.0, and 4.2 adds a lineage query to every recall whose cost nobody has measured. Shared CI runners are noisy, so a pass or fail threshold would be flaky or useless. A report that is visible on each pull request and kept as an artifact is the part that holds up; a gate can follow once a stable threshold exists.

## Approaches considered

| Mode | Trade-off | Chosen |
|---|---|---|
| **Report only.** Run on pull requests that touch code and on demand; publish the table to the job summary and an artifact; never fail on numbers. | Cannot block a regression, but is never flaky, and costs nothing to maintain. | **Yes**, by the user |
| Report plus an allocation gate. | Allocations are deterministic, but a committed baseline needs upkeep. | No |
| Report plus a relative gate against the base commit. | Doubles the run and is still noisy on shared runners. | No |

| Scope | Trade-off | Chosen |
|---|---|---|
| **Ranking, middleware, and PostgreSQL search with lineage resolution.** | Measures every cost the milestone names, plus 4.2's walk-up. The search needs a database. | **Yes**, by the user |
| Ranking and middleware only. | No database, but the lineage cost stays unmeasured. | No |
| Everything, capture and redaction too. | Wider than the milestone goal. | No |

## Approach

**Project.** `benchmarks/Mnemosyne.NET.Benchmarks`, an executable, `IsPackable` false, in the solution under a `/benchmarks/` folder so `dotnet build` of the solution keeps it compiling. It references `Mnemosyne.NET.Abstractions`, `Mnemosyne.NET` and `Mnemosyne.NET.PostgreSql`, and the BenchmarkDotNet package, pinned in `Directory.Packages.props`. It is not part of the Native AOT gate: BenchmarkDotNet is not AOT-compatible, and nothing in `src` changes for it.

**Benchmarks.** Three classes, each with `[MemoryDiagnoser]`:
- `RankingBenchmarks`: `ReasonletSelector.RankAsync` over 10, 100 and 1000 in-memory candidates with `Top` of 5, built once in `GlobalSetup` with a fixed seed and a fixed clock.
- `MiddlewareBenchmarks`: `ReasonletChatClient` over a no-op `IChatClient` with a stub `IReasonletMemory` that returns a fixed match list, against calling the no-op client directly as the baseline. The difference is the middleware overhead for a non-streaming call, with and without a recalled Reasonlet.
- `SearchBenchmarks`: `ReasonletPostgreSqlStore.SearchAsync` against 1000 stored Reasonlets at lineage depth 1 and depth 20, so the cost of 4.2's recursive query shows. Embeddings are deterministic 256-dimension vectors from a seeded generator.

**Database.** `SearchBenchmarks` reads a connection string from `MNEMOSYNE_BENCH_PG`. When it is unset, `Program` leaves the class out of the switcher and prints a note, so the project runs anywhere without Docker. The CI job starts a `pgvector/pgvector:pg17` service container, as `aot-publish` does, and creates the benchmark database.

**Workflow.** A new `.github/workflows/benchmarks.yml` runs on pull requests that change `src/**`, `benchmarks/**` or the workflow itself, and on `workflow_dispatch`. One job on `ubuntu-latest`, `contents: read` only. It runs the project in Release with the short job, the GitHub markdown exporter and the JSON exporter, appends the markdown reports to `$GITHUB_STEP_SUMMARY`, and uploads the whole results directory as an artifact. It has no pass or fail threshold: a benchmark that throws fails the job, a slow number does not. The job summary states that the runner is shared and the numbers are for comparison within one run.

**Readme.** `benchmarks/README.md` says how to run the suite locally, what each class measures, why CI reports and does not gate, and how to compare two runs.

## Tests

- Unit: `RepoConventionsTests` still passes with the new project and workflow; if it checks the workflow set, update it.
- Smoke: `dotnet run -c Release --project benchmarks/Mnemosyne.NET.Benchmarks -- --job dry --filter '*Ranking*'` finishes and prints a table, locally and in the workflow's first run.
- Regression: `dotnet build Mnemosyne.NET.slnx -c Release` and the pack job still produce one package per source project, since the benchmark project is not packable.

## Open Questions

- None. The BenchmarkDotNet version is whatever is the latest stable when the plan runs.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Shared runners make numbers noisy | Misleading comparisons | Report only, with the caveat printed in the summary; compare within one run |
| The benchmark project stops compiling when 4.4 reshapes the API | A red solution build | It is in the solution, so 4.4's build catches it in the same change |
| The 4.2 candidate and match shape differs from the plan | Setup code does not compile | The `Builds on` line names the exact members, and a guard check in 4.2's plan fails when they change |
| The search benchmark's setup is slow | A long job | 1000 Reasonlets seeded in one batch of inserts; the job has a 30 minute timeout |
