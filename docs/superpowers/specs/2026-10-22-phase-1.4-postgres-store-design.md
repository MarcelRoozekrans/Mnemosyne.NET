# Phase 1.4 Design — PostgreSQL + pgvector store

**Date:** 2026-10-22
**Phase:** 1.4
**Surface:** Data
**Stage:** phase (one phase, implementation-ready)

This design builds on these earlier decisions:
- the [phase 1.2 contract](2026-10-22-phase-1.2-abstractions-design.md), which defines `IReasonletStore`;
- the [phase 1.3 graph format](2026-10-22-phase-1.3-graph-schema-design.md), which provides the content hash;
- the [roadmap](2026-10-21-roadmap-design.md), which requires AOT and no EF Core.

Each decision below is marked **user** or **my call**.

## Goal

`Mnemosyne.NET.PostgreSql` implements `IReasonletStore` on PostgreSQL with
pgvector. It covers:
- atomic remember;
- get;
- executions and feedback;
- scoped vector search with joined metrics;
- erasure.

The schema is created by migrations that the host runs, and it is
Native-AOT-clean.

## Approach

### Data access (user)

The store is built on **ZeroAlloc.ORM** over **AdoNet.Async**. `[Query]` and
`[Command]` partial methods emit the ADO.NET code at compile time, with no
reflection.

- **Embedding:** binds as a `float[]` parameter, which Npgsql sends as a
  binary `real[]`. The SQL casts it with `@embedding::vector`. This uses the
  float arrays added upstream in ZeroAlloc.ORM #397, so it needs no text
  formatting and no Pgvector package.
- **Atomic remember:** runs in one `IAsyncDbTransaction`. ZeroAlloc.ORM
  supports transaction parameters on its generated methods.
- **Package versions:** pin **ZeroAlloc.ORM 2.7.0**, the release that
  contains #397. Its release PR, ZeroAlloc.ORM #398, must be merged and
  published before implementation starts.
- **Connection:** the store takes an `NpgsqlDataSource` from the host and
  opens one connection per operation.
  - Hosts that publish with AOT should build that data source with
    `NpgsqlSlimDataSourceBuilder` and call `EnableArrays()`. The AOT smoke
    test uses that path.
  - The store doesn't build data sources itself.

### Configuration (user: dimension fixed at setup)

`MnemosynePostgreSqlOptions` has three members:
- `required int Dimensions`, from 1 to 2,000. pgvector's `vector` holds up
  to 16,000 dimensions, but its HNSW index holds at most 2,000, so the options
  reject anything above that at setup with a clear message.
- There is no `Schema` option (**my call**, after the builder check). The
  schema is fixed as `mnemosyne`, and every SQL statement names it in full,
  for example `mnemosyne.reasonlets`. ZeroAlloc.ORM's SQL is a
  compile-time literal and migration files are static, so a configurable
  schema would mean either hand-written SQL or a pooled `search_path`, and
  neither is worth it. ZeroAlloc.ORM's own history table, `__zaorm_migrations`,
  lands in the connection's `current_schema()`, as it does for every adopter.
- `int HnswM` (default 16) and `int HnswEfConstruction` (default 64),
  pgvector's defaults, exposed so they can be tuned. They apply when the first
  `MigrateAsync` builds the index, and are recorded like the dimension.

### Migrations (user: the host runs them)

The host calls `ReasonletPostgreSqlStore.MigrateAsync(ct)` at startup. Calling
it again is harmless. It does four things, in this order:

1. Requires PostgreSQL 15 or later, whose `ON DELETE SET NULL` takes a column
   list, which the scoped self-reference needs (see Schema). It reads
   `server_version_num` before the runner, because an older server can't
   parse the migration. An older server fails with `Validation`, naming the
   version found and the minimum.
2. Runs ZeroAlloc.ORM's `MigrationRunner` with `PostgresMigrationDialect`
   over the embedded SQL files in `src/Mnemosyne.NET.PostgreSql/Migrations/`,
   scoped by source so it can share a database with other migration sources.
   These migrations create:
   - the schema and the `vector` extension (`CREATE EXTENSION IF NOT EXISTS vector`);
   - the tables;
   - a settings table.
3. Requires pgvector 0.8.0 or later, the first release with iterative index
   scans, which scoped search depends on (see Search). After the runner has
   created the extension, it reads `extversion` from `pg_extension` and
   compares it numerically. An older version fails with `Validation`, naming
   the version found and the minimum.
4. Applies the dimension and the HNSW options. Embedded SQL is static, so it
   can't contain the configured `N`, and the store finishes the job after the
   runner, under a lock on the settings table:
   - If no dimension is recorded, it alters `embedding` to `vector(N)`,
     creates the HNSW index with `m` and `ef_construction`, and records all
     three. All of this happens in one transaction.
   - If the recorded dimension differs from `N`, it fails with `Validation`,
     naming both numbers. Mixing embedding models silently would corrupt
     similarity.
   - If the recorded HNSW options differ from the configured ones, it fails
     with `Validation`, naming both pairs: the options only take effect when
     the index is built, so accepting them silently would mislead.
   - Otherwise it does nothing.

The store never migrates on its own when it is first used. Any other member
called before `MigrateAsync` fails with `Unavailable` ("schema not
migrated"), because it checks the recorded dimension once and caches it.

### Schema (my call where not stated)

Every row carries `scope`, and every query filters on it, so a lookup with
the wrong scope finds nothing and answers `NotFound`, as phase 1.2 requires.

Every foreign key carries the scope next to the id it references, against a
`UNIQUE (scope, id)` on the referenced table (**user**). No row can then point
at a row in another scope, not even one written by hand, so the store needs
no carve-outs for cross-scope links. The self-reference uses
`ON DELETE SET NULL (parent_id)`, which cuts the link and leaves `scope`
alone; that column-list form needs PostgreSQL 15 or later. The foreign keys
can't prevent a `parent_id` cycle, so the cycle guards stay.

**`reasonlets`** holds one row per Reasonlet version:

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` | Primary key, the Reasonlet's id |
| `scope` | `text` | Not null |
| `name` | `text` | Not null |
| `intent` | `text` | Not null |
| `version` | `text` | Not null, see Versions |
| `graph` | `text` | Not null. The exact `ReasonletGraphJson.Serialize` output. **`text`, not `jsonb`:** `jsonb` normalises numbers and key order, so a graph read back would no longer match its stored hash, and a caller returning a recalled graph unchanged could be given a spurious new version |
| `content_hash` | `text` | Not null, `CHECK (length(content_hash) = 64)`. `ComputeContentHash()` at insert; never recomputed from stored text |
| `parent_id` | `uuid` | Nullable. `(scope, parent_id)` is a foreign key to `reasonlets (scope, id)`, `ON DELETE SET NULL (parent_id)` |
| `status` | `smallint` | Not null. The `ReasonletStatus` number |
| `source` | `text` | Not null |
| `run_id` | `text` | Nullable |
| `subject_id` | `text` | Nullable |
| `tags` | `jsonb` | Nullable. Bound with `[Json]` |
| `created_at` | `timestamptz` | Not null |
| `embedding` | `vector` | Not null. Becomes `vector(N)` when `MigrateAsync` applies the dimension |

The table also has `UNIQUE (scope, id)`, which the scoped foreign keys
reference.

`parent_id ON DELETE SET NULL` is how issue #3's ruling gets applied
(**user**). Erasing subject A's Reasonlet keeps subject B's child versions
and cuts their lineage link.

**`reasonlet_executions`** has these columns:
- `id uuid` primary key, with `UNIQUE (scope, id)` for the feedback's key;
- `reasonlet_id uuid not null`; `(scope, reasonlet_id)` is a foreign key to
  `reasonlets (scope, id)` with `ON DELETE CASCADE`;
- `scope text not null`;
- `executed_at timestamptz`;
- `success bool`;
- `duration_ticks bigint`;
- `score double precision`, nullable;
- `source text not null`, `run_id text`, `subject_id text` and `tags jsonb`,
  for the provenance phase 1.2 requires on every execution.

**`reasonlet_feedback`** has these columns:
- `execution_id uuid` primary key; `(scope, execution_id)` is a foreign key
  to `reasonlet_executions (scope, id)` with `ON DELETE CASCADE`;
- `scope text not null`;
- `utility`, `correctness` and `reusability`, each `double precision`;
- `recorded_at timestamptz`.

Recording feedback for the same execution again replaces it, as an upsert
(**my call**: the latest judgement wins; history isn't needed before phase 2).

**`reasonlet_metrics`** (**user**) keeps one counter row per Reasonlet, so
search reads its metrics instead of aggregating executions:
- `reasonlet_id uuid` primary key; `(scope, reasonlet_id)` is a foreign key to
  `reasonlets (scope, id)` with `ON DELETE CASCADE`;
- `scope text not null`;
- `runs integer not null` and `successes integer not null`;
- `last_success_at timestamptz`, nullable.

Every execution insert, whether from a remember or an append, upserts the row
in the same statement and transaction: an insert for a new Reasonlet, else
`runs = runs + 1`, `successes = successes + 1` on a success, and
`last_success_at = greatest(last_success_at, executed_at)` on a success. Each
is one atomic row update, so concurrent appends never lose a count, and
`greatest` ignores nulls and keeps the latest success whatever order the
appends commit in. An erase that removes a subject's executions from a
Reasonlet it keeps recounts that Reasonlet's row from the executions left,
inside the erase's transaction (see Erasure).

**`settings`** holds `key text primary key, value text`. The `dimensions`,
`hnsw_m` and `hnsw_ef_construction` keys record what the first `MigrateAsync`
applied.

**Indexes** (**my call**: exactly the ones a query, a walk or a foreign-key
action uses):
- `(scope, status, intent)` on reasonlets, for search's filters;
- HNSW on `embedding vector_cosine_ops`;
- `(scope, id)` on reasonlets and on executions, the unique constraints the
  scoped foreign keys reference; the inserts' foreign-key checks use them;
- `(scope, parent_id)` on reasonlets: the walks down a lineage, the erase's
  search for kept children, and the self-reference's `SET NULL`, which now
  looks children up by both columns. The walks up use the primary key or
  `(scope, id)`;
- `(scope, subject_id)` on reasonlets and on executions, for erasure by
  subject;
- `(scope, reasonlet_id)` on executions, for the cascade from reasonlets, the
  erase and the metrics recount.

The feedback's and the metrics' cascades find their rows through their
primary keys.

### Versions (my call; phase 1.2 left numbering to this phase)

A lineage is derived from `parent_id` alone; no root is stored.

- A new Reasonlet is version `1.0` and has a null `parent_id`. It is the top
  of its lineage.
- A child's lineage is found from its parent, always within the scope:
  - walk up `parent_id` to the **top**, the ancestor whose `parent_id` is null,
    which is the parent itself when it has no parent;
  - the lineage is the top and its whole subtree, found by walking down
    `parent_id`.
- The child's version is `1.<k>`, where `k` is one more than the highest minor
  in the lineage, so siblings and grandchildren share one sequence: `1.1`,
  `1.2`, `1.3`.
- The store takes the next number under row locks, all taken going up the
  tree: `FOR NO KEY UPDATE` on the parent, `FOR KEY SHARE` on each ancestor
  between the parent and the top, bottom-up and in one statement, and
  `FOR NO KEY UPDATE` on the top. That is how concurrent children never
  collide:
  - the top's `FOR NO KEY UPDATE` serializes every new version in the
    lineage, because two of them conflict;
  - the path locks block a `DELETE` of any ancestor, and an erase must delete
    an ancestor to cut a link, so the path to the top, and with it the
    lineage, cannot change before the transaction commits;
  - a transaction only ever waits for a row above every row it holds, so two
    remembers cannot deadlock. A remember and an erase can, when the erase's
    lock walk raced a change to the lineage, and that deadlock answers
    `Conflict`.
  - `FOR NO KEY UPDATE` rather than `FOR UPDATE` (**my call**): it still
    conflicts with another remember's lock and with an erase's `FOR UPDATE`,
    but it lets `FOR KEY SHARE` through, so an append's lock and the
    foreign-key checks of executions and children no longer wait for a
    remember in the same lineage.
- **Walks.** The walk up returns the `(id, parent_id)` links with `UNION` and
  carries no path or depth, and the store follows them from the parent in
  C#; a link that leads back to a Reasonlet already on the path is a cycle,
  which throws `InvalidOperationException`. The walk down returns the highest
  well-formed minor, computed in SQL as `split_part(version, '.', 2)`, read as
  `numeric`, and one malformed version if any, which throws
  `FormatException`; C# adds one with checked arithmetic, so a minor past
  `int.MaxValue` throws `OverflowException`. Each recursive step is an index
  probe in a `LATERAL` subquery that `LIMIT 1` or `OFFSET 0` keeps from being
  flattened, because without table statistics the planner otherwise hashes
  the whole scope at every step, which is quadratic in depth. Measured at
  depth 4,000, a remember fell from about 4 s to about 24 ms.
- **Erasure.** When a Reasonlet is erased, `ON DELETE SET NULL` cuts its
  children's `parent_id`, so each orphan becomes the top of its own lineage:
  its subtree. Version strings never change, and a surviving subtree keeps its
  numbering. For example, with R `1.0`, P `1.1` under R and G `1.2` under P,
  erasing R leaves P's lineage as P and G. P's next child is `1.3`, never a
  second `1.2`. A stored root column could not give this, because SET NULL
  would also cut G's link to R and make G a top of its own while its parent is
  still P.
- The major stays 1 until variant selection (milestone 5) gives it a meaning.

### RememberAsync (atomic, per phase 1.2)

A null entry throws `ArgumentNullException` before anything else, the
migration check included. The store then calls `entry.Validate()`; a failure
returns `Validation`, and so does an embedding whose length isn't the
configured dimension, or whose norm is zero or overflows: pgvector's cosine
distance is NaN for those, not an error. Then, in one transaction at
**READ COMMITTED**, named explicitly so a server default can't change it
(**my call**). The row locks on the parent and the lineage's top do the
serializing; nothing relies on serializable snapshots:

1. **No `ParentId`:** insert a new Reasonlet at version `1.0`, insert an
   execution from the capture's outcome and provenance with its metrics row,
   and return the receipt with kind `NewReasonlet` and status `Active`.
2. **`ParentId` set:**
   - Lock the parent row in its scope with `SELECT … FOR NO KEY UPDATE`. If it
     is missing, or exists only in another scope, return `NotFound`.
   - If the capture's `ComputeContentHash()` equals the parent's
     `content_hash`, insert an execution on the parent and return
     `ExecutionOnly`, with the parent's id and version.
   - Otherwise:
     - find the path to the lineage's top by walking up `parent_id` in the
       scope;
     - lock the ancestors between the parent and the top `FOR KEY SHARE`, in
       one statement that locks them in path order, bottom-up:
       `SELECT … FROM unnest(@ids) WITH ORDINALITY u (id, ord) JOIN reasonlets r
       … ORDER BY u.ord FOR KEY SHARE OF r`. The plan's `LockRows` step sits
       above the ordering by `ord`, an explicit sort or a nested loop driven
       by the ordinality scan, so each row is locked as it comes out in path
       order. Fewer rows than ancestors means one vanished: `Conflict`. Then
       lock the top `FOR NO KEY UPDATE`. When the parent is the top, the top
       lock is a re-lock. Everything is in the scope;
     - read the highest minor in the top's subtree, walking down `parent_id`
       in the scope, and take the next version;
     - insert the child (`parent_id`) and its execution, and return
       `NewVersion`.
3. **Errors:**
   - A parent erased before the lock returns `NotFound`, because the locked
     select finds no row.
   - An ancestor or the top erased between the walk and its lock returns
     `Conflict`. The erase cut the path, so the walk's top and subtree no
     longer describe the lineage.
   - A `parent_id` cycle, which only hand-written SQL can create, throws
     `InvalidOperationException`.
   - A deadlock (`40P01`) with a concurrent erase that locked the rows in
     another order returns `Conflict`. A foreign-key violation (`23503`)
     would too, but the remember holds a lock on every row its inserts
     reference, so none can happen.
   - Connection errors return `Unavailable`.
   - Cancellation throws.

Every success inserts exactly one execution, so a receipt always carries an
`ExecutionId`.

### Search

```sql
SELECT r.id, r.scope, r.name, r.intent, r.version, r.graph, r.parent_id, r.status,
       r.source, r.run_id, r.subject_id, r.tags, r.created_at,
       greatest(0, 1 - (r.embedding <=> @embedding::vector)) AS similarity,
       coalesce(m.runs, 0), coalesce(m.successes, 0), m.last_success_at
FROM reasonlets r
LEFT JOIN reasonlet_metrics m ON m.reasonlet_id = r.id AND m.scope = r.scope
WHERE r.scope = @scope AND r.status = 1 AND (@intent::text IS NULL OR r.intent = @intent)
ORDER BY r.embedding <=> @embedding::vector
LIMIT @limit
```

- The query selects explicit columns and never `r.*`, because Npgsql can't
  read a bare `vector` column without the pgvector plugin, and search never
  needs the embedding back.
- Only `Active` (1) Reasonlets are returned, and similarity is clamped to
  `[0, 1]`, as phase 1.2 requires.
- The metrics come from the counter row (see Schema). Every remember
  inserts an execution, so a Reasonlet without a row can't happen, but the
  join is a `LEFT JOIN` anyway and a missing row reads as `(0, 0, null)`.
- An embedding whose length isn't the configured dimension, that holds a
  non-finite value, or whose norm is zero or overflows returns `Validation`
  before the query runs.
- `limit` ranges from 1 to 200 (**my call**: the selector over-fetches, and
  200 bounds the cost); outside that range returns `Validation`.
- **Iterative scans (needs pgvector 0.8.0 or later).** An HNSW index scan
  collects about `hnsw.ef_search` nearest rows (default 40) across the whole
  table, and the `scope`, `status` and `intent` filters apply only after
  that. On a shared table, a scope with a small share of the rows would get
  fewer results than `limit`, or none, and a `limit` above about 40 would be
  silently capped. So search runs in one READ COMMITTED transaction that
  first sets, with `SET LOCAL`:
  - `hnsw.iterative_scan = strict_order`, so the scan keeps going until it
    has enough rows that pass the filters. `strict_order` rather than
    `relaxed_order`, because it keeps the results sorted exactly by distance;
    HNSW recall is approximate either way;
  - `hnsw.ef_search = max(limit, 40)`. `SET` takes no bind parameter, so the
    value is an integer that the limit check already bounded, written with
    the invariant culture, as the dimension DDL is;
  - `jit = off`: the statement is short, and JIT compilation can cost more
    than it saves once a large table pushes the estimate past
    `jit_above_cost`.

  `hnsw.max_scan_tuples` stays at its default (20,000), which bounds the work
  for a very selective scope. The flip side is that a very small scope in a
  very large table can still come back with fewer rows than `limit`; raising
  it is a milestone 4 benchmark topic.
  Rows at exactly equal distance come back in an unspecified order: an `r.id`
  tie-breaker in `ORDER BY` could stop the index from serving the ordering.

### Erasure (scope moved from 1.5; issue #3's ruling)

The phase 1.2 port already requires `EraseAsync`, and issue #3 says it ships
in this phase, so erasure moves from 1.5 to 1.4. Phase 1.5 keeps audit events
and retention, and the roadmap gets updated to match (**my call**).

- **By scope:** delete every Reasonlet in the scope with its executions and
  feedback. The executions are deleted explicitly, before the Reasonlets, so
  they can be counted; their feedback and the metrics rows cascade.
- **By subject:**
  - delete that subject's Reasonlets in the scope. This cuts other subjects'
    children through `SET NULL`. Every execution and feedback on the deleted
    Reasonlets, including other subjects' runs of them, goes with them
    (**user**). A run record only means something attached to its procedure,
    so issue #3's rule reads: other subjects' Reasonlets survive, and run
    records follow their procedure;
  - then delete that subject's executions on Reasonlets that are kept, and
    recount those Reasonlets' metrics rows from the executions left.

  Both steps run in one transaction.
- `ReasonletErasureResult` counts the Reasonlets deleted and every execution
  removed. The executions are deleted explicitly, with `DELETE … RETURNING`
  in a CTE, before the Reasonlets, so none is left to cascade uncounted. A cut
  lineage link is not a removal.
- **Order and locks (my call).** The transaction first runs
  `SET LOCAL jit = off`: on a large scope the lock statement's estimate passes
  `jit_above_cost`, and compiling cost more than the statement saved. Measured
  through the store on a 25,000-row erase out of a 50,000-row scope, the
  median fell from 554 ms to 283 ms. Then these statements, in order:
  - lock what the erase changes, `FOR UPDATE`: the Reasonlets it deletes and
    their kept children in the scope, whose `parent_id` it cuts. The rows are
    locked deepest first, by their depth below the top of their lineage in
    the scope, then by id. A remember's path locks go bottom-up, so the erase
    waits behind a remember instead of deadlocking with it, and two erases
    lock overlapping rows in one order. Each depth is computed once, in
    linear time however deep the lineage: a walk up with `UNION` finds the
    tops above the targets, and a walk down from those tops numbers the rows,
    each step an index probe in a `LATERAL` subquery (see Versions). A
    per-row walk up with a `CYCLE` path array was cubic in depth and ran a
    2,000-deep chain out of temp space. A top is a row whose parent is null;
    the scoped foreign key keeps every parent in its child's scope. A
    hand-written `parent_id` cycle ends the walk up, and rows on or below a
    cycle, which no walk down reaches, lock at depth 0. The statement returns
    the ids to delete, and the later statements use those ids rather than a
    fresh snapshot, so a Reasonlet remembered meanwhile is not deleted
    unlocked;
  - lock in id order, then delete with `DELETE … RETURNING`, the executions
    to remove: those of the locked Reasonlets and the subject's executions on
    kept Reasonlets. A kept Reasonlet of the subject itself can only have been
    remembered after the locks were taken, so its executions stay with it.
    The statement also returns the kept Reasonlets that lost executions;
  - when there are any, lock their metrics rows `FOR UPDATE` in id order, then
    recount them from their executions in a second statement. Two statements
    on purpose: an `UPDATE` that waits for a row lock re-checks only that row
    with its old snapshot, so a recount that waited for a concurrent append
    would overwrite the append's increment with a total that missed it. Once
    the rows are held, an append waits for the erase instead, and the
    recount's fresh snapshot sees every execution committed before it;
  - delete the locked Reasonlets. No execution is left to cascade, so the
    counts are exact; their metrics rows cascade, and
    `ON DELETE SET NULL (parent_id)` cuts the kept children.

  The locks go Reasonlets, then executions, then metrics rows, each in a
  fixed order. The final delete's cascades touch the kept children the erase
  holds and the metrics rows of the Reasonlets it deletes. A remember or an
  append locks a metrics row only after locking its Reasonlet, which the
  erase holds, and another erase recounts it only when both erases remove the
  same executions, so they already queued at the execution step. A deadlock
  that still happens, with a remember that raced the lock walk, answers
  `Conflict`.
- **Concurrent remembers (user ruling).** Erasure covers what exists when it
  takes its locks. A Reasonlet the subject remembers while the erase runs is
  not erased by it, and keeps its execution.
- **Corrupt data.** The scoped foreign keys rule out a cross-scope parent
  link and an execution in another scope than its Reasonlet's. Only a
  `parent_id` cycle remains possible through hand-written SQL; its rows are
  still locked and erased, as above.

### Errors

The PostgreSQL error code maps to `MnemosyneError` like this:

| PostgreSQL code | `MnemosyneError` |
|---|---|
| `40001` (serialization failure; can't happen at READ COMMITTED, mapped as a safety net) | `Conflict` |
| `40P01` (deadlock) | `Conflict` |
| `23503` (foreign-key violation), from a concurrent erase | `Conflict` |
| `55P03` (lock not available), from a host's `lock_timeout` | `Conflict` |
| Connection failure (`08*`), operator intervention (`57P*`) | `Unavailable` |
| Insufficient resources (`53*`: disk full, out of memory, too many connections) | `Unavailable` |
| Query canceled or statement timeout (`57014`) from the server's side | `Unavailable` |
| Read-only transaction (`25006`), such as a connection to a standby | `Unavailable` |
| `NpgsqlException` with no `SqlState` (I/O failure, client timeout) | `Unavailable` |

Cancellation through the caller's token surfaces from Npgsql as
`OperationCanceledException`, not as `57014`, so it still throws.

**Executions and feedback.** `AppendExecutionAsync` is one scoped statement
that locks the Reasonlet `FOR KEY SHARE`, inserts the execution and upserts
the metrics row. It takes the Reasonlet's lock first, in the order an erase
takes its locks: left to the foreign-key check, that lock would come at the
end of the statement, after the metrics row, and an append could deadlock
with an erase of its Reasonlet. So an append that waits for an erase finds
the Reasonlet gone and answers `NotFound`, never `23503`.
`AppendFeedbackAsync` is one scoped upsert; feedback whose execution a
concurrent erase deletes while the upsert waits answers `Conflict`, from the
foreign-key check's `23503`.

Anything else is a bug and propagates as an exception. Doing that is the
house rule: exceptions are reserved for bugs and cancellation. Corrupt stored
data is treated the same way: a `parent_id` cycle, which only hand-written SQL
can create, throws `InvalidOperationException`, and so does a stored graph that
no longer reads.

### DI

`services.AddMnemosynePostgreSql(MnemosynePostgreSqlOptions options)` registers
`IReasonletStore` as `ReasonletPostgreSqlStore`, a singleton. The `NpgsqlDataSource`
comes from the host's container. AOT-safe options validation happens in the
constructor, so there are no reflection-based validators. The options object is
passed directly rather than through `Action<>`, because its members are
`required` init members.

## Tests

Integration tests run against real PostgreSQL with pgvector, one container
per test class, and each test gets a fresh scope:
- **Remember:**
  - all three branches;
  - the receipt's kind, version and execution;
  - the parent missing, and the parent in another scope (both `NotFound`);
  - an equal graph matched by hash, including one re-serialized after
    reading back;
  - an embedding of the wrong length, or with a zero or overflowing norm,
    returns `Validation`;
  - 20 parallel children of one parent, of two parents and of parents at
    every depth of one lineage all get distinct versions with no gaps;
  - a 4,000-deep lineage gets its next version in well under two seconds;
  - a `parent_id` cycle throws rather than loops.
- **Races, forced deterministically:** a test holds a lock or a delete open in
  its own transaction, waits until the store blocks on it (seen in
  `pg_stat_activity`), and then commits or closes a deadlock:
  - a top or a middle ancestor erased while the remember waits: `Conflict`;
  - a deadlock with another transaction: `Conflict` carrying `40P01`, for a
    remember and for an erase;
  - the ancestors are locked in path order: while the batch waits for a
    middle ancestor, the one below it is locked and the one above is not;
  - an append to a parent that a waiting remember holds completes at once;
  - an append that waits for an erase of its Reasonlet: `NotFound`;
  - feedback that waits for an erase of its execution: `Conflict` carrying
    `23503`;
  - an erase waits behind a remember that holds a child, without deadlock;
  - a Reasonlet the subject remembers while its erase waits survives;
  - a metrics recount that waits for a concurrent append counts it;
  - two erases with overlapping rows, or overlapping executions, both
    succeed, ten rounds each, with no retry.
- **Get:** a round-trip of every field, including the exact graph text and
  tags; another scope returns `NotFound`.
- **Executions, feedback and metrics:**
  - append;
  - feedback upsert;
  - feedback on an execution in another scope returns `NotFound`;
  - the metrics rows equal an aggregate of the executions through remember,
    execution-only remember, append and a subject erase;
  - 50 concurrent appends to one Reasonlet lose no count.
- **Search:**
  - ordering by distance, with similarity clamped;
  - `PendingReview` rows excluded;
  - other scopes never returned;
  - the intent filter;
  - metrics read from the counter row, and a missing row read as no runs;
  - a wrong embedding length, a non-finite value, a zero or overflowing norm
    and a limit out of range all return `Validation`;
  - a minority scope gets its limit through the HNSW index.
- **Erasure:**
  - by scope;
  - by subject, where another subject's children survive with a null parent;
  - counts are correct;
  - a 1,000-deep lineage erases in linear time, and rows on a cycle still go.
- **Migrations:**
  - running twice is harmless, and concurrent first runs apply the dimension
    once;
  - a dimension mismatch, and an HNSW options mismatch, fail with both values;
  - a server older than PostgreSQL 15, and a pgvector older than 0.8.0,
    fail with the version found and the minimum;
  - the catalog has exactly the specified constraints and indexes, and the
    foreign keys refuse a row that points into another scope;
  - calls before `MigrateAsync` return `Unavailable`, and null arguments
    throw before that check.
- **Unit tests:** the version helpers, the server version check, the error
  mapper over its SQL state codes, and options validation.
- **AOT:** the publish stays clean, and the runtime smoke passes in CI.

Coverage stays at 100%, the repo's Codecov gate.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| A filtered HNSW scan returns fewer rows than `limit` for a scope with a small share of the table | Silent recall loss in search | Iterative scans with `strict_order` and `ef_search = max(limit, 40)`; this needs pgvector 0.8.0 or later, which `MigrateAsync` checks; a test forces the index path on a skewed table |
| The HNSW index can't be built for more than 2,000 dimensions | Large-model embeddings unsupported | Reject at setup with a clear message; `halfvec` (up to 4,000) is a later option |
| Lineage-wide version locking serializes concurrent children of one lineage | Lower throughput for one hot procedure | New versions in one lineage queue on the top's `FOR NO KEY UPDATE`, and each takes one lock statement for all its ancestors; appends and feedback never wait for them. The parallel tests check correctness, and the milestone 4 benchmark measures throughput |
| A small scope in a huge table hits `hnsw.max_scan_tuples` | Search returns fewer rows than `limit` | Documented in the README; raising the cap is a milestone 4 benchmark topic |
| Erasure deletes rows, but storage keeps them until vacuum, and WAL, replicas and backups keep them for their own retention | GDPR erasure is incomplete at rest | Documented in the README with autovacuum and backup rotation |
| The Docker-tier tests are Linux-only | Windows CI doesn't exercise the store | The tiering and conventions test make the gap explicit, the same as Rag.NET |
| Npgsql's slim data source needs `EnableArrays()` for `float[]` | AOT hosts hit a runtime error | Documented in options and the README; the AOT smoke uses the slim builder |
