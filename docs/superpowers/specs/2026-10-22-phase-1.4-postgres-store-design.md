# Phase 1.4 Design — PostgreSQL + pgvector store

**Date:** 2026-10-22
**Phase:** 1.4
**Surface:** Data
**Stage:** phase (one phase, implementation-ready)

This design builds on these earlier decisions:
- the [phase 1.2 contract](2026-10-22-phase-1.2-abstractions-design.md), which defines `IReasonletStore`;
- the [phase 1.3 graph format](2026-10-22-phase-1.3-graph-schema-design.md), which provides the content hash;
- the [roadmap](2026-10-21-roadmap-design.md), which requires AOT and no EF Core.

Each decision below is marked **user** or **my call**.

## Goal

`Mnemosyne.NET.PostgreSql` implements `IReasonletStore` on PostgreSQL with
pgvector. It covers:
- atomic remember;
- get;
- executions and feedback;
- scoped vector search with joined metrics;
- erasure.

The schema is created by migrations that the host runs, and it is
Native-AOT-clean.

## Approach

### Data access (user)

The store is built on **ZeroAlloc.ORM** over **AdoNet.Async**. `[Query]` and
`[Command]` partial methods emit the ADO.NET code at compile time, with no
reflection.

- **Embedding:** binds as a `float[]` parameter, which Npgsql sends as a
  binary `real[]`. The SQL casts it with `@embedding::vector`. This uses the
  float arrays added upstream in ZeroAlloc.ORM #397, so it needs no text
  formatting and no Pgvector package.
- **Atomic remember:** runs in one `IAsyncDbTransaction`. ZeroAlloc.ORM
  supports transaction parameters on its generated methods.
- **Package versions:** pin **ZeroAlloc.ORM 2.7.0**, the release that
  contains #397. Its release PR, ZeroAlloc.ORM #398, must be merged and
  published before implementation starts.
- **Connection:** the store takes an `NpgsqlDataSource` from the host and
  opens one connection per operation.
  - Hosts that publish with AOT should build that data source with
    `NpgsqlSlimDataSourceBuilder` and call `EnableArrays()`. The AOT smoke
    test uses that path.
  - The store doesn't build data sources itself.

### Configuration (user: dimension fixed at setup)

`MnemosynePostgreSqlOptions` has three members:
- `required int Dimensions`, from 1 to 16,000, the pgvector limit for
  `vector`. HNSW indexes at most 2,000 dimensions, so values above that are
  rejected at setup with a clear message.
- There is no `Schema` option (**my call**, after the builder check). The
  schema is fixed as `mnemosyne`, and every SQL statement names it in full,
  for example `mnemosyne.reasonlets`. ZeroAlloc.ORM's SQL is a
  compile-time literal and migration files are static, so a configurable
  schema would mean either hand-written SQL or a pooled `search_path`, and
  neither is worth it. ZeroAlloc.ORM's own history table, `__zaorm_migrations`,
  lands in the connection's `current_schema()`, as it does for every adopter.
- `int HnswM` (default 16) and `int HnswEfConstruction` (default 64),
  pgvector's defaults, exposed so they can be tuned.

### Migrations (user: the host runs them)

The host calls `ReasonletPostgreSqlStore.MigrateAsync(ct)` at startup. Calling
it again is harmless. It does two things:

1. Runs ZeroAlloc.ORM's `MigrationRunner` with `PostgresMigrationDialect`
   over the embedded SQL files in `src/Mnemosyne.NET.PostgreSql/Migrations/`,
   scoped by source so it can share a database with other migration sources.
   These migrations create:
   - the schema and the `vector` extension (`CREATE EXTENSION IF NOT EXISTS vector`);
   - the tables;
   - a settings table.
2. Applies the dimension. Embedded SQL is static, so it can't contain the
   configured `N`, and the store finishes the job after the runner:
   - If no dimension is recorded, it alters `embedding` to `vector(N)`,
     creates the HNSW index, and records `N`. All of this happens in one
     transaction.
   - If the recorded dimension equals `N`, it does nothing.
   - If they differ, it fails with `Validation`, naming both numbers. Mixing
     embedding models silently would corrupt similarity.

The store never migrates on its own when it is first used. Any other member
called before `MigrateAsync` fails with `Unavailable` ("schema not
migrated"), because it checks the recorded dimension once and caches it.

### Schema (my call where not stated)

Every row carries `scope`, and every query filters on it, so a lookup with
the wrong scope finds nothing and answers `NotFound`, as phase 1.2 requires.

**`reasonlets`** holds one row per Reasonlet version:

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` | Primary key, the Reasonlet's id |
| `scope` | `text` | Not null |
| `name` | `text` | Not null |
| `intent` | `text` | Not null |
| `version` | `text` | Not null, see Versions |
| `graph` | `text` | Not null. The exact `ReasonletGraphJson.Serialize` output. **`text`, not `jsonb`:** `jsonb` normalises numbers and key order, so a graph read back would no longer match its stored hash, and a caller returning a recalled graph unchanged could be given a spurious new version |
| `content_hash` | `char(64)` | Not null. `ComputeContentHash()` at insert; never recomputed from stored text |
| `parent_id` | `uuid` | Nullable. Foreign key to `reasonlets.id`, `ON DELETE SET NULL` |
| `root_id` | `uuid` | Nullable. Foreign key to `reasonlets.id`, `ON DELETE SET NULL` (see Versions) |
| `status` | `smallint` | Not null. The `ReasonletStatus` number |
| `source` | `text` | Not null |
| `run_id` | `text` | Nullable |
| `subject_id` | `text` | Nullable |
| `tags` | `jsonb` | Nullable. Bound with `[Json]` |
| `created_at` | `timestamptz` | Not null |
| `embedding` | `vector` | Not null. Becomes `vector(N)` when `MigrateAsync` applies the dimension |

`parent_id ON DELETE SET NULL` is how issue #3's ruling gets applied
(**user**). Erasing subject A's Reasonlet keeps subject B's child versions
and cuts their lineage link.

**`reasonlet_executions`** has these columns:
- `id uuid` primary key;
- `reasonlet_id uuid not null`, a foreign key with `ON DELETE CASCADE`;
- `scope text not null`;
- `executed_at timestamptz`;
- `success bool`;
- `duration_ticks bigint`;
- `score double precision`, nullable;
- `source text not null`, `run_id text`, `subject_id text` and `tags jsonb`,
  for the provenance phase 1.2 requires on every execution.

**`reasonlet_feedback`** has these columns:
- `execution_id uuid` primary key, a foreign key with `ON DELETE CASCADE`;
- `scope text not null`;
- `utility`, `correctness` and `reusability`, each `double precision`;
- `recorded_at timestamptz`.

Recording feedback for the same execution again replaces it, as an upsert
(**my call**: the latest judgement wins; history isn't needed before phase 2).

**`settings`** holds `key text primary key, value text`. The `dimensions` key
records the applied dimension.

**Indexes:**
- `(scope, status, intent)`;
- HNSW on `embedding vector_cosine_ops`;
- `(scope, parent_id)`;
- `(scope, content_hash)`;
- `(scope, subject_id)` on reasonlets and on executions;
- `(reasonlet_id)` on executions.

### Versions (my call; phase 1.2 left numbering to this phase)

A lineage is a root and every Reasonlet descended from it.

- A new Reasonlet is version `1.0` and has a null `root_id`, which means it is
  its own root.
- A child gets `root_id = coalesce(parent.root_id, parent.id)`. Its version is
  `1.<k>`, where `k` is one more than the highest minor already in the
  lineage, so siblings and grandchildren share one sequence: `1.1`, `1.2`,
  `1.3`.
- The store takes the next number while holding `FOR UPDATE` on the root
  row, so concurrent children never collide.
- If a root is erased, `ON DELETE SET NULL` makes each orphan the root of its
  own lineage. Existing version strings stay as they are. The next child of an
  orphan continues from the highest minor in its new lineage.
- The major stays 1 until variant selection (milestone 5) gives it a meaning.

### RememberAsync (atomic, per phase 1.2)

The store first calls `entry.Validate()`; a failure returns `Validation`. Then,
in one transaction at the default **READ COMMITTED** isolation level (**my
call**). The `FOR UPDATE` row locks on the parent and the root do the
serializing; nothing relies on serializable snapshots:

1. **No `ParentId`:** insert a new Reasonlet at version `1.0`, insert an
   execution from the capture's outcome and provenance, and return the
   receipt with kind `NewReasonlet` and status `Active`.
2. **`ParentId` set:**
   - Lock the parent row in its scope with `SELECT … FOR UPDATE`. If it is
     missing, or exists only in another scope, return `NotFound`.
   - If the capture's `ComputeContentHash()` equals the parent's
     `content_hash`, insert an execution on the parent and return
     `ExecutionOnly`, with the parent's id and version.
   - Otherwise, lock the root, take the next version, insert the child
     (`parent_id`, `root_id`) and its execution, and return `NewVersion`.
3. **Errors:**
   - A parent erased before the lock returns `NotFound`, because the locked
     select finds no row.
   - A foreign-key violation (`23503`) or deadlock (`40P01`) from a
     concurrent erase returns `Conflict`. That means the insert raced a
     delete after the read, or an erase locked the rows in another order.
   - Connection errors return `Unavailable`.
   - Cancellation throws.

Every success inserts exactly one execution, so a receipt always carries an
`ExecutionId`.

### Search

```sql
SELECT r.id, r.scope, r.name, r.intent, r.version, r.graph, r.parent_id, r.status,
       r.source, r.run_id, r.subject_id, r.tags, r.created_at,
       greatest(0, 1 - (r.embedding <=> @embedding::vector)) AS similarity,
       m.runs, m.successes, m.last_success_at
FROM reasonlets r
LEFT JOIN LATERAL (SELECT count(*) runs, count(*) FILTER (WHERE success) successes,
                          max(executed_at) FILTER (WHERE success) last_success_at
                   FROM reasonlet_executions e WHERE e.reasonlet_id = r.id) m ON true
WHERE r.scope = @scope AND r.status = 1 AND (@intent IS NULL OR r.intent = @intent)
ORDER BY r.embedding <=> @embedding::vector
LIMIT @limit
```

- The query selects explicit columns and never `r.*`, because Npgsql can't
  read a bare `vector` column without the pgvector plugin, and search never
  needs the embedding back.
- Only `Active` (1) Reasonlets are returned, and similarity is clamped to
  `[0, 1]`, as phase 1.2 requires.
- An embedding whose length isn't the configured dimension returns
  `Validation` before the query runs.
- `limit` ranges from 1 to 200 (**my call**: the selector over-fetches, and
  200 bounds the cost); outside that range returns `Validation`.
- `hnsw.ef_search` is left at its default; tuning is a milestone 4
  benchmark topic.

### Erasure (scope moved from 1.5; issue #3's ruling)

The phase 1.2 port already requires `EraseAsync`, and issue #3 says it ships
in this phase, so erasure moves from 1.5 to 1.4. Phase 1.5 keeps audit events
and retention, and the roadmap gets updated to match (**my call**).

- **By scope:** delete every Reasonlet in the scope. Executions and feedback
  cascade.
- **By subject:**
  - delete that subject's Reasonlets in the scope. This cuts other subjects'
    children through `SET NULL`. Every execution and feedback on the deleted
    Reasonlets, including other subjects' runs of them, cascades with them
    (**user**). A run record only means something attached to its procedure,
    so issue #3's rule reads: other subjects' Reasonlets survive, and run
    records follow their procedure;
  - then delete that subject's executions on Reasonlets that are kept.

  Both steps run in one transaction.
- `ReasonletErasureResult` counts the Reasonlets deleted and every execution
  removed, whether by cascade or directly. Executions are counted before the
  delete inside the same transaction, or with `DELETE … RETURNING` in a CTE.
  A cut lineage link is not a removal.

### Errors

The PostgreSQL error code maps to `MnemosyneError` like this:

| PostgreSQL code | `MnemosyneError` |
|---|---|
| `40001` (serialization failure; can't happen at READ COMMITTED, mapped as a safety net) | `Conflict` |
| `40P01` (deadlock) | `Conflict` |
| `23503` (foreign-key violation), from a concurrent erase | `Conflict` |
| Connection failure or timeout (`08*`, `57P*`, `NpgsqlException` with no `SqlState`) | `Unavailable` |

Anything else is a bug and propagates as an exception. Doing that is the
house rule: exceptions are reserved for bugs and cancellation.

### DI

`services.AddMnemosynePostgreSql(Action<MnemosynePostgreSqlOptions>)` registers
`IReasonletStore` as `ReasonletPostgreSqlStore`, a singleton. The `NpgsqlDataSource`
comes from the host's container. AOT-safe options validation happens in the
constructor, so there are no reflection-based validators.

## Tests

Integration tests run against real PostgreSQL with pgvector, one container
per test class, and each test gets a fresh scope:
- **Remember:**
  - all three branches;
  - the receipt's kind, version and execution;
  - the parent missing, and the parent in another scope (both `NotFound`);
  - an equal graph matched by hash, including one re-serialized after
    reading back;
  - 20 parallel children of one parent all get distinct versions with no gaps
    in the minor sequence.
- **Get:** a round-trip of every field, including the exact graph text and
  tags; another scope returns `NotFound`.
- **Executions and feedback:**
  - append;
  - feedback upsert;
  - feedback on an execution in another scope returns `NotFound`.
- **Search:**
  - nearest-first ordering, with similarity clamped;
  - `PendingReview` rows excluded;
  - other scopes never returned;
  - the intent filter;
  - metrics joined correctly: runs, successes, last success;
  - a wrong embedding length and a limit out of range both return `Validation`.
- **Erasure:**
  - by scope;
  - by subject, where another subject's children survive with a null parent;
  - counts are correct.
- **Migrations:**
  - running twice is harmless;
  - a dimension mismatch fails with both numbers;
  - calls before `MigrateAsync` return `Unavailable`.
- **Errors:** the error mapper is unit-tested over the SQL state codes. A
  real race is too timing-dependent to force reliably in an integration test,
  so it isn't attempted.
- **Unit tests:** the version helper, the error mapper, and options
  validation.
- **AOT:** the publish stays clean, and the runtime smoke passes in CI.

Coverage stays at 100%, the repo's Codecov gate.

## Open Questions

None. Before implementation, ZeroAlloc.ORM #398 (release 2.7.0) must be
merged and published to NuGet. A builder check raised four questions:
- schema configurability, settled as a fixed schema;
- isolation and the trigger for `Conflict`, settled as READ COMMITTED with
  row locks;
- executions on erased Reasonlets, settled by the user as cascade;
- the package version, settled as 2.7.0.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The HNSW index can't be built for more than 2,000 dimensions | Large-model embeddings unsupported | Reject at setup with a clear message; `halfvec` (up to 4,000) is a later option |
| Lineage-wide version locking serializes concurrent children of one lineage | Lower throughput for one hot procedure | It only locks one row per lineage; the parallel test measures correctness, and the milestone 4 benchmark measures throughput |
| The Docker-tier tests are Linux-only | Windows CI doesn't exercise the store | The tiering and conventions test make the gap explicit, the same as Rag.NET |
| Npgsql's slim data source needs `EnableArrays()` for `float[]` | AOT hosts hit a runtime error | Documented in options and the README; the AOT smoke uses the slim builder |
