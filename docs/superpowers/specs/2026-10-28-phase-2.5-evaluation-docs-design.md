# Phase 2.5 Design: Evaluation docs and sample

**Date:** 2026-10-28
**Phase:** 2.5
**Surface:** Docs
**Stage:** phase (one phase, implementation-ready)

The last phase of milestone 2. It closes the criterion "Docs and a sample cover evaluation". Every milestone ends with a docs-and-samples phase covering what it shipped (**user**, from the roadmap). Decisions marked **user** were chosen by the user in the brainstorm; everything else is **my call**.

## Intent

Milestone 2 made ranking's success rate come from judged runs. The docsite already explains pieces of that: the Minos and chat-model guides, judged versus agent-only runs and match evidence in `concepts/ranking.md`, the evaluate activity in `guides/telemetry.md`, and a paragraph in getting-started. What it lacks:

1. **One place that tells the whole story.** Who gives a verdict, in which order, what each call returns, how feedback changes a verdict, what happens when the judge is down. Today a reader assembles that from four pages.
2. **A way to write your own judge.** `IReasonletEvaluator` is a public port with a precise contract (error codes, validation, cancellation, privacy) that no page explains.
3. **A sample where evaluation happens.** The only sample registers no evaluator, so every run in it is agent-only. Nobody can see judging move a ranking.

## Goals

- A reader can run a sample, with only Docker and the .NET 10 SDK and no API key, that shows a judged procedure outranking an agent-only one, an evaluator overruling the agent, and a person's feedback overruling both, and prints the evidence behind each match.
- A reader can write and register their own `IReasonletEvaluator` from one guide page.
- A reader understands the evaluation loop end to end from one concept page, linking out for the ranking maths and the shipped judges.

## Non-goals

- **A sample that calls a real model** (**user** chose the offline sample over a chat-model or a combined one). The Minos and chat-model guides already show registration of the shipped judges.
- **Changing the StoreAndRecall sample** (**user** chose a new sample over extending it). Its walkthrough and the worked example in `ranking.md` stay as they are.
- **Library code changes.** This phase is docs and a sample. If writing them exposes a defect or a misleading API in `src/`, fix it in this phase per the review-loop rule, but do not add features.
- **An API reference.** Milestone 4.

## Anti-goals

- **Duplicating the ranking maths.** The formula, prior and weights live in `concepts/ranking.md`. The new pages link there; they do not restate formulas that can drift.
- **A sample whose printed numbers disagree with the docs.** The sample checks its own output and exits 1 on a mismatch, and CI runs it, exactly like StoreAndRecall.
- **A toy evaluator that teaches a wrong contract.** The sample's evaluator is the worked example for the custom-evaluator guide, so it must follow the contract fully: `Unavailable` for a backend failure, no question or answer text in an error, a result that passes `ReasonletEvaluation.Validate`, honour cancellation.

## Constraints

- .NET 10, central package management, the repo's analyzers and `-warnaserror` settings apply to samples as they do now (`samples/Directory.Build.props`).
- Docusaurus with an autogenerated sidebar: a new page needs only a file in the right folder, plus `sidebar_position` front matter.
- The docs' house style: short sentences, plain words, tables for settings and fields, code blocks that compile against the shipped API.
- Commit messages: conventional, no nested parentheses in bodies, footer lines at most 100 characters.

## Approach

### 1. The sample: `samples/Mnemosyne.Samples.Evaluation` (**user**: offline judge plus feedback)

A console app in the same shape as StoreAndRecall: same `compose.yaml` pattern but a different host port, so both samples' databases can run side by side (my call), same connection-string environment variable convention (its own name, `MNEMOSYNE_SAMPLE_PG` reused is fine since CI gives it its own database), same offline `HashingEmbeddingGenerator` (copy it, or share it through a linked file; builder's call), same `Require` / `SampleFailure` helpers, same fresh scope erased at the end.

It registers a small rule-based evaluator defined in the sample, for example `ChecklistEvaluator`: it judges a run as working when the answer meets a simple, visible rule tied to the procedure (for example, a refund answer must name a refund id and say the customer was notified). The rule is deliberately simple. `ReasonletEvaluation` is only `Success`, `Score` and a judge id, `Evaluator`; it carries no reason, because a reason could quote the answer and is never stored. So the *sample's walkthrough code*, not the evaluator, prints the rule once up front and says which act's answer meets it, and the reader can see why each verdict came out. The evaluator itself never logs or prints the question or the answer (my call, after the builder check).

The walkthrough, in three acts, each printing what happened and checking it:

1. **Judged beats agent-only.** Two procedures for similar questions. One has more runs, all agent-only (recorded without an answer, so the evaluator is not asked). The other has fewer runs, each recorded with an answer the evaluator judges a success. Recall shows the judged one first despite fewer runs, and prints each match's `ReasonletEvidence` (runs, judged runs) next to its score. The point: `AgentVerdictWeight` 0.5 counts self-graded runs for less.
2. **The evaluator overrules the agent.** A run the agent reports as a success, recorded with an answer that fails the rule. The receipt says `Source = Evaluator`, `Success = false`, and the sample prints it.
3. **A person overrules both.** `RecordFeedbackAsync` with `Worked` on one run (for example, a person confirms the run the evaluator failed actually worked, or reports a judged success as a failure; builder picks the one that moves the ranking most visibly). Recall again and show the ranking or the rate change.

Act 1 only works when the judged procedure's run count is more than half the agent-only one's, given `AgentVerdictWeight` 0.5 and equal success; pick counts with a clear margin (my call, after the builder check).

The exact procedures, counts and questions are the builder's call, under two rules: every act must produce a visible, explained change; and the final ranking and totals must be deterministic within a run (freshness 1.000, as in StoreAndRecall) so the sample can check them and the docs can publish them.

### 2. CI

Add a step to `.github/workflows/ci.yml` next to the store-and-recall one: create a database of its own, `mnemosyne_evaluation_sample` (my call), run the sample in Release, fail the job on a non-zero exit. It gates publish the same way and for the same reason: a release must not ship docs whose sample fails. Add the project to `Mnemosyne.NET.slnx` wherever StoreAndRecall sits.

### 3. `docs/concepts/evaluation.md` (**user**: concept page plus custom guide)

The loop end to end:

- Why evaluate: the agent grades its own work.
- The three verdicts and their order: a human's `Worked` from feedback, then an evaluator's verdict, then the agent's `Success`. Link to `ranking.md#success-rate` and `#judged-and-agent-only-runs` for how they weigh.
- When the evaluator is asked: a registered `IReasonletEvaluator`, and a run recorded with a question and an answer, on both remember and `RecordExecutionAsync`. The answer is never stored.
- What comes back: `ReasonletRunReceipt` / the receipt's `Source` and `Success`, never `Feedback`.
- Feedback: `RecordFeedbackAsync`, `Worked` changes a verdict, `Worked` null keeps it (changed, not withdrawn), the three scores are stored but unused by ranking, a feedback on an agent-only run makes it judged.
- When the judge is down, too slow, or the answer is blank or too long: the agent's verdict counts and the call does not fail. An adapter bug throws `InvalidOperationException`. Link to `ranking.md#when-recall-fails` and `EvaluationTimeout`.
- Match evidence: what `JudgedRuns` of 0 means for a caller. Link to `ranking.md#the-evidence-on-each-match`.
- Choosing a judge: a short table linking Minos, the chat model, and your own.
- A pointer to the sample.

### 4. `docs/guides/custom-evaluator.md`

Writing your own `IReasonletEvaluator`, with the sample's evaluator as the worked example:

- The request: what `ReasonletEvaluationRequest` carries.
- The result: `ReasonletEvaluation` is `Success`, `Score` (0 to 1) and `Evaluator`, a short judge id, not blank and at most 100 code points. What `Validate` rejects. There is no reason field, and why: it could quote the answer. Check the exact limits against the code when writing.
- Errors: `MnemosyneErrorCode.Unavailable` for a backend failure (the agent's verdict then counts), anything else is a bug the facade throws for. Never quote the question or the answer in an error.
- Cancellation: throw `OperationCanceledException`, never return it. The facade's `EvaluationTimeout` cancels the token and stops waiting even for a judge that ignores it.
- Registration: as a singleton, like everything else the facade uses.
- Testing it: a short note on unit-testing the evaluator alone.
- Telemetry: the evaluate activity covers custom judges too; link to `guides/telemetry.md`.

## Tests

- **The sample checks itself**: expected order, totals and evidence for the final recall, and the receipt of act 2; exits 1 on a mismatch. CI runs it against pgvector.
- **The docsite builds**: `npm run build` with Docusaurus' broken-link check, so every new link resolves.
- **Code in the docs compiles**: snippets in the custom-evaluator guide come from, or match, the sample's evaluator.
- No new unit tests in `tests/`: the sample is not library code and stays out of coverage, as StoreAndRecall does.

## What's left to the builder

- The sample's procedures, questions, counts and the evaluator's rule, under the rules in Approach §1.
- Whether the embedding stand-in is copied or shared.
- Page wording, section order within each page, and `sidebar_position` values.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The offline embedding stand-in gives similarities that make the acts' point hard to see | A reader can't tell what moved the ranking | Pick questions with near-equal similarity, so success rate decides; print the score breakdown |
| Published numbers drift from the sample | Docs lie | The sample checks the exact totals it prints; the docs copy them from a real run |
| The docs restate ranking maths that later changes | Two pages disagree | Link to `ranking.md`; no formulas on the new pages |
