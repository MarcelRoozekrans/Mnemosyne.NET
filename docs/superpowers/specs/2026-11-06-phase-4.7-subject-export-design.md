# Phase 4.7 Design — Subject export

**Date:** 2026-11-06
**Phase:** 4.7
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)
**Status:** approved 2026-11-06

## Goal

A host can read everything a subject owns in a scope, page by page, through `IReasonletMemory` and `IReasonletStore`, so it can answer a GDPR access request (Art. 15) or a portability request (Art. 20) without querying PostgreSQL tables. Closes #69.

## Why

`EraseAsync` removes a subject's data, but nothing reads it. `docs/guides/data-protection.md` says so and points the deployer to SQL against the `subject_id` columns. That is a stopgap. The read path is new public API on the store port, and after 1.0.0 adding a member to `IReasonletStore` is a breaking change, so it lands before the release (Marcel, 2026-11-06, option A in STATE.md).

## Goals, non-goals, anti-goals

**Goals**
- The export set is exactly the set `EraseAsync` removes for the same scope and subject, so access, portability and erasure agree.
- Bounded memory: both reads page.
- The guide replaces its SQL stopgap with the new calls.

**Non-goals**
- No export file format. The records are plain, and the host serialises them.
- No cross-scope read. A host loops over its scopes.
- No rectification (Art. 16); the guide still says erase and capture again.
- No change to the embedding, the schema or the migrations.

**Anti-goals**
- An export that omits something an erase would delete.
- An export that exposes another subject's graph or text.

## Decided with Marcel (2026-11-06)

| Decision | Choice |
|---|---|
| Export set | The same set as erase |
| Shape | Two paged calls, `ListSubjectReasonletsAsync` and `ListSubjectRunsAsync`, each shaped like `ListPendingAsync` (option A) |

## Approaches considered

| Approach | Trade-off | Verdict |
|---|---|---|
| A. Two paged calls | Two members on the port and on the facade; the host joins runs to Reasonlets by `ReasonletId`; the cursor is a plain id | **Picked by Marcel** |
| B. One paged mixed call | One member, but a union record type and a composite cursor over two tables | Rejected |
| C. One unpaged call | Smallest API, memory unbounded for a heavy subject | Rejected |

## Approach

**The export set.** For a scope and a subject id:
- *Reasonlets:* every Reasonlet of the scope whose provenance `SubjectId` equals the subject, in any status, so `PendingReview` ones are included. Versions are Reasonlets, so they come with it.
- *Runs:* every execution of the scope whose `subject_id` is the subject, plus every execution of any Reasonlet in the first list, whatever its own subject. This mirrors `LockExecutionsForErasureAsync`: an erase follows a Reasonlet's runs with it, and also removes the subject's runs on Reasonlets that stay. A run on someone else's Reasonlet carries only its `ReasonletId`; the other owner's definition is never returned.

**Calls.** On `IReasonletStore`, with the same members on `IReasonletMemory`:

```csharp
ValueTask<Result<IReadOnlyList<ReasonletRecord>, MnemosyneError>> ListSubjectReasonletsAsync(
    ReasonletScope scope, string subjectId, int limit, ReasonletId? after, CancellationToken ct);

ValueTask<Result<IReadOnlyList<ReasonletExecutionRecord>, MnemosyneError>> ListSubjectRunsAsync(
    ReasonletScope scope, string subjectId, int limit, ExecutionId? after, CancellationToken ct);
```

Each returns up to `limit` rows (1 to 100) with an id above `after`, ordered by id, `null` to start. Ids are version 7 GUIDs, so this is creation order. An empty list is a success. Validation errors: a `default` scope, a blank subject, a limit outside 1 to 100, a `default` cursor. `Unavailable` when the store fails. The facade validates and passes through, as `ListPendingAsync` does. Ids are made by clients, so a row stored while an export pages can land behind the cursor. The remarks say the export is a snapshot of what existed when it began only if the host stops writing for the subject first, which is what the guide's erase procedure already asks.

**Records** (new, in `Mnemosyne.NET.Abstractions/Records`, my call on the names):
- `ReasonletRecord { Definition: ReasonletDefinition, Metrics: ReasonletMetrics }`. The embedding is not returned, because it is derived from the text and is not personal text itself. This is the same shape `ReasonletReview` has, kept separate because a review is a work-queue item.
- `ReasonletExecutionRecord { Id: ExecutionId, ReasonletId: ReasonletId, Scope: ReasonletScope, ExecutedAt: DateTimeOffset, Outcome: ReasonletOutcome, Evaluation: ReasonletEvaluation?, Feedback: ReasonletFeedback?, Success: bool, VerdictSource: ReasonletVerdictSource, Provenance: ReasonletProvenance }`. It reuses the input types, so a host sees what was recorded. `Outcome` is the agent's flag, duration and score. `Evaluation` is the evaluator's verdict, null when none judged. `Feedback` is the human's scores and `Worked`, null when none was recorded. `Success` is the effective success the store derived (human, else evaluator, else agent) and `VerdictSource` says which one it was. The columns come from `reasonlet_executions` and `reasonlet_feedback`. Both records have `Validate()` like their neighbours.

**Guard and review gate.** Reads go through neither. The capture guard and the review gate control what is written and what recall returns; an access request must show what is stored, including pending Reasonlets. Stated in the remarks.

**PostgreSQL.** Two queries in `ReasonletRepository` and `ExecutionRepository` (the runs query left-joins `reasonlet_feedback`), on the existing indexes `(scope, subject_id)`. The runs query is a `WHERE scope = @scope AND (subject_id = @subjectId OR reasonlet_id IN (SELECT id FROM reasonlets WHERE scope = @scope AND subject_id = @subjectId)) AND id > @after ORDER BY id LIMIT @limit`. Whether the `OR` plans well on a large table is for the builder to check with `EXPLAIN`; a `UNION` of the two index paths is the fallback. The export set is a read, so it runs at the default isolation level in one statement per page; no transaction spans pages.

## Tests

- Unit: facade validation (default scope, blank subject, limit 0 and 101, default cursor); delegation; record `Validate()`.
- Integration, PostgreSQL: an export equals what an erase removes. Seed two subjects, a Reasonlet owned by A with a run by B, and a run by A on a Reasonlet owned by B; export A, erase A, and assert the exported ids are exactly the deleted ones. Paging: several pages reach the end without a repeat or a gap. Pending Reasonlets are included. Another scope's rows and another subject's rows are absent. A subject with nothing returns an empty success.
- The Native AOT gate must stay green; the records are plain types with no reflection.
- Codecov targets 100% patch coverage, so every new branch has a test.

## Open Questions

None that block planning. Builder to confirm: the `OR` query plan, and that `ExecutionId` is ordered like a version 7 GUID, as the cursor relies on.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The export and erase sets drift apart later | An access request misses data an erase deletes | The integration test asserts export equals erase, so a change to either fails it |
| The `OR` over two indexes plans badly | A slow export for a subject in a large scope | `EXPLAIN` in the plan; fall back to a `UNION` of the two index paths |
| Third-party `IReasonletStore` implementations stop compiling | Breaking for them | Acceptable before 1.0.0; the release notes of 1.0.0 name it |
| Hosts export a record captured without a subject id | Their access answer is incomplete | The guide keeps the warning that such a record is not found by subject |
