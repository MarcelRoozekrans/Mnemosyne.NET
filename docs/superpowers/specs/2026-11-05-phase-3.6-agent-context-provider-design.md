# Phase 3.6 Design — `Agent Framework AIContextProvider`

**Date:** 2026-11-05
**Phase:** `3.6`
**Surface:** `Backend`
**Stage:** phase (one phase, implementation-ready)

## Goal

A Microsoft Agent Framework agent gets the recall and capture that `UseReasonlets` gives an `IChatClient`. The host adds a `ReasonletContextProvider` from the new `Mnemosyne.NET.AgentFramework` package to the agent's `AIContextProviders`. From then on, each agent run recalls the best known procedure for the user's message and offers it to the model. Each run's tool loop is captured and judged in the background. Thalos.NET and Daedalus.NET are the first hosts.

## Intent

`UseReasonlets` cannot serve Agent Framework agents. `ChatClientAgent` wraps its chat client in its own tool loop, so middleware on that client sits inside the loop. Inside the loop it sees single model calls and captures nothing useful. Thalos also attaches memory to agents through `IAgentContextProviderSource.CreateProvider(AgentDefinition)`, which expects an `AIContextProvider`. An `AIContextProvider` runs once around a whole agent run: before the run it adds instructions and tools, and after the run it sees the run's full tool loop.

**What one procedure is.** One agent run, from the user's message to the final answer, is one procedure. Thalos and Daedalus were checked on 2026-11-05:
- One user turn is one `RunStreamingAsync` call.
- No tool needs approval, and no agent asks for clarification in the middle of a task.
- Multi-step work runs in Thalos's own workflow engine, with a fresh session per node.
- Thalos creates a fresh Agent Framework session every turn, so the session's `StateBag` does not carry anything to the next turn.

Joining several runs into one procedure would solve a problem these hosts do not have, and in Thalos it could not work.

**Goals**
- Recall, injection, `find_procedure` and background capture for any `AIAgent` that runs `AIContextProvider`s, with no Mnemosyne-specific code per run.
- Procedures shared per agent by default.
- A small public capture API in the core package, which `UseReasonlets` and the provider both use.
- Inherited issues closed in this phase:
  - #45: a parentless capture of a stored shape creates a duplicate;
  - #47: intent text reaches other users through `find_procedure`;
  - #46: settled by keeping the bypass internal and documenting the rule.

**Non-goals**
- **Procedures across several runs.** Tool approvals and clarifying questions in the middle of a task are not joined into one capture. This is documented as a limit until a host uses them.
- **The Thalos adapter and the Daedalus wiring.** They are PRs in those repos after release, per the milestone design.
- **Microsoft.Agents.AI.Workflows.** Neither host uses it.

**Anti-goals**
- **Memory never breaks or slows an agent run.** A recall failure, a missing scope, a full queue or a failed capture leaves the run working as if the provider were absent, and shows only in telemetry. This matches 3.5.
- **No suggestion lands in a session's saved history.** Thalos saves `AIContext.Messages` into the session's history, so the suggestion goes in `Instructions`, which apply to the current run only.
- **One user's text never reaches another user of the scope.** This rules out the extracted intent in `find_procedure` output, which is #47.

## Facts this design rests on

These were checked against Agent Framework 1.27.0 with a throwaway console probe on 2026-11-05. The probe used a fake chat client making one tool call, attached to a `ChatClientAgent` with one provider.

- `AIContextProvider` is in `Microsoft.Agents.AI.Abstractions`, namespace `Microsoft.Agents.AI`. Its surface is the same in 1.24 and 1.27.
- **The run-end hook sees the whole tool loop.** `StoreAIContextAsync(InvokedContext)` gets `ResponseMessages` with the assistant tool call, the tool result and the final answer, for both `RunAsync` and `RunStreamingAsync`.
- **The request side holds only the new input.** `RequestMessages` holds only the run's new external messages; the history and provider messages are filtered out by the default filters.
- **The suggestion reaches every model call of the run.** `AIContext.Instructions` from `ProvideAIContextAsync` reached both inner model calls, so the suggestion holds across the whole tool loop.
- **One provider instance serves every session of an agent.** The docs say a provider must keep no per-session state in fields.
- **Both hooks get the same session object.** `InvokingContext.Session` and `InvokedContext.Session` are the same reference. When the caller passes no session, `ChatClientAgent` creates one, so neither hook saw a null session. The type still allows null.
- **An abandoned stream never reaches the run-end hook.** When the consumer stops reading a `RunStreamingAsync` early, `InvokedCoreAsync` never runs, so a partial tool loop is never captured.
- **A failed run reaches it with the exception set.** A run whose chat client throws reaches `InvokedCoreAsync` with `InvokeException` set, and the base implementation does not call `StoreAIContextAsync`.
- **AOT.** Neither assembly carries `RequiresUnreferencedCode` or `RequiresDynamicCode`. Both are built AOT-compatible and trimmable, and both target net8.0, net9.0, net10.0, netstandard2.0 and net472.
- Agent Framework 1.24.0 depends on `Microsoft.Extensions.AI.Abstractions` 10.10.1. The repo uses 10.11.0, so the dependency range is fine.

## Decisions

| Decision | Detail | By |
|---|---|---|
| Unit of capture | One agent run is one capture. Runs that end on a pending tool call or an approval request are skipped with skip reason `pending_tool_calls`, like 3.5, not joined to the next run. | user |
| Default scope | Per agent. Everyone using the same agent shares its procedures, because procedures are tool shapes and the tools belong to the agent. | user |
| Scope resolution | `ReasonletAgentOptions.ScopeResolver`, of type `Func<AIAgent, AgentSession?, ReasonletAgentScope?>`, returns the scope and an optional subject id per run, or null to skip the run. The default resolver uses `agent.Name` as the scope, with no subject. A null or empty name skips the run with reason `no_scope`. `agent.Id` is not a fallback: Thalos rebuilds agents per revision, and a generated id would scatter one agent's procedures over many scopes. | user (per agent); my call (Name, not Id) |
| Subject | Agent Framework has no owner concept, so the default subject is null. A host that knows the owner returns it from the resolver, and it becomes `Provenance.SubjectId`, so erasing a subject covers automatic captures. Thalos keeps its session id in the `StateBag` under `thalos.session_id`, and the Thalos adapter will map it to the session's owner. | my call |
| Public capture API | Approach A, below. The core package gets a public way to hand a finished run to the capture queue, and a public type for the `find_procedure` tool's lookups. `UseReasonlets` moves onto the same API. | user |
| Recall question | The text of the last user message in `RequestMessages`. A run with no user text in its request is not recalled for: skip reason `continuation`, the same name as in 3.5. | my call |
| Injection | The top match above the similarity floor, rendered by `ReasonletPromptFormatter`, or by the `Formatter` in the options, is returned as `AIContext.Instructions`. Never as `Messages`, which Thalos saves into history. | my call (Instructions) |
| `find_procedure` | With `ExposeFindProcedure` on (off by default, like 3.5), each run gets its own tool instance, added through `AIContext.Tools` for that run only. Its lookups feed parent inference as in 3.5. | my call (mirrors 3.5) |
| Correlating the two hooks | The injected parent and the run's tool instance must reach `StoreAIContextAsync` without instance fields that runs share. The provider keys per-run state on the `AgentSession` with a `ConditionalWeakTable`, which the probe showed is the same reference in both hooks. A new run on the session replaces any state left by an abandoned stream. With a null session, which the type allows but `ChatClientAgent` never passes, the run is captured without an injected parent and without lookups, and is counted (amended 2026-11-05, see the amendments at the end). This assumes one run at a time per session, as Thalos enforces. | my call |
| Pending calls | The rule from 3.5, unchanged. A run ends pending when its last response message carries a `FunctionCallContent` with no matching `FunctionResultContent`, or an `InputRequestContent` approval request. Such a run is skipped as `pending_tool_calls`. `TryCapture` decides this when the run is handed over, so `ReasonletRun` has no field for it. | 3.5 rule |
| Source | `ReasonletRun` has an optional `Source`. Null means `ReasonletCaptureOptions.Source`, so `UseReasonlets` keeps `mnemosyne.chat` or the host's setting. The provider sets `ReasonletAgentOptions.Source`, default `mnemosyne.agent`. Both paths share one queue and one processor, and the processor writes the run's source into the provenance. | my call |
| Target framework | net10.0 only, like every package in the repo. Thalos targets net10.0. Daedalus also targets net8.0, but its agent projects consume Thalos, which is net10.0 only, so net8.0 gains nothing here. | my call |
| Renamed agents | With the default resolver, renaming an agent starts a new scope, and its procedures stay under the old name. This is accepted and documented. A host that renames agents returns a stable scope from its resolver. | my call |
| #45 duplicates | `RememberAsync` without a `ParentId` first looks up a Reasonlet in the scope with the same content hash, and records an execution against it. See its own section below. | user (in the store) |
| #47 intent | `find_procedure` no longer returns `intent`. Recall still matches on it. A match still returns id, name, version, similarity, success rate, runs and steps. | user |
| #46 judge bypass | Stays internal. The documented rule stands: a judge or guard uses a client without `UseReasonlets`. The provider sits on the agent, not the chat client, so judge calls never reach it. The issue is closed with a comment linking the guide. | user |
| Both layers on one agent | `UseReasonlets` on the agent's chat client together with this provider is not supported. The middleware would sit inside `ChatClientAgent`'s tool loop anyway. The README says to use the provider for agents. Nothing detects the combination. | my call |
| Package version | `Mnemosyne.NET.AgentFramework` references `Microsoft.Agents.AI.Abstractions` 1.24.0, the lowest version with the needed surface, so hosts on 1.24 to 1.27 can all use it. Renovate is told not to raise this floor. | my call |
| Telemetry | The provider uses the same instruments as the middleware, `mnemosyne.chat.recall` and the capture counters. Captures carry `Provenance.Source = "mnemosyne.agent"`, so the two paths stay apart. Each recall activity has a `mnemosyne.integration` tag, `chat` or `agent`. | my call |

## Approaches

**A. A small public capture API in the core package (picked).** The core exposes a public way to hand a finished run to the capture queue, and a `find_procedure` tool that reports its lookups. The provider is a thin layer over it, and `UseReasonlets` uses the same API, so the two stay in step. The cost is new public API before the milestone 4 freeze. The milestone design says integrations are meant to push on the API first, and other hosts can build their own integrations on it.

**B. `InternalsVisibleTo` from the core to the new package.** Adds no public API. But a host whose core and provider packages differ in version fails at runtime with a missing member, not at build time. Thalos and Daedalus update packages separately. Rejected.

**Dropped: no new package, `UseReasonlets` on the agent's chat client.** `ChatClientAgent` adds its own tool loop around that client, so the middleware would capture single model calls. It also does not fit `IAgentContextProviderSource`.

## Public API

**Core package, `Mnemosyne.NET`.** The names are the builder's to refine; the shape is decided.

- `ReasonletRun`: a public record of one finished run, to hand to capture.
  - Required: `Scope` and `Messages` (the request plus the response messages, without the injected suggestion).
  - Optional: `SubjectId`, `InjectedParent`, `Lookups` (the matches each `find_procedure` call returned, in call order), `Duration`, `RunId`, `FinishReason` and `Source`.
  - It does not take "ends with a pending call". The queue decides that itself when the run is handed over, as 3.5 does now.
- `IReasonletCaptureSink`, registered by `AddReasonletCapture`: `bool TryCapture(ReasonletRun run)`.
  - Returns false when the queue is full or shut down.
  - Counted as today; it never throws for those cases.
  - `ReasonletCaptureQueue` implements it, and the internal `ReasonletCaptureItem` becomes `ReasonletRun` or is built from it.
- `ReasonletTools.CreateFindProcedure` returns a public `FindProcedureFunction` (or a narrow public subtype of `AIFunction`) with an `IReadOnlyList<IReadOnlyList<ReasonletMatch>> Lookups` property. It is the same thread-safe record 3.5 keeps internally. Hosts that create their own instance can then pass its lookups along.
- `ReasonletSuggestions`: a public recall step (amended 2026-11-05, Marcel's choice during planning).
  - Why: the middleware's recall enforces a hard timeout, abandons a slow memory call through the internal `ReasonletMemory.Abandon`, and counts on internal instruments. A provider in another package cannot reuse any of that.
  - `RecallAsync(memory, scope, question, options, integration, ct)` returns a `ReasonletSuggestion(Id, Text)` or null. It does the timeout, the abandon, the formatting and the counting.
  - `CountSkipped(reason, integration)` counts the `no_scope` and `continuation` skips.
  - The options carry `MinSimilarity`, `RecallTimeout`, `Formatter` and `TimeProvider`.
  - The integration value, `chat` or `agent`, becomes the `mnemosyne.integration` tag.
- `ReasonletChatClient` calls `ReasonletSuggestions` and `IReasonletCaptureSink`, and its behaviour does not change.

**New package, `Mnemosyne.NET.AgentFramework`.**

- `ReasonletContextProvider : AIContextProvider`.
  - Overrides `ProvideAIContextAsync` and `StoreAIContextAsync`.
  - Is built from an `IServiceProvider` and a `ReasonletAgentOptions`.
  - Resolves `IReasonletMemory` and `IReasonletCaptureSink` lazily on the first run, as 3.5 does, so a memory that depends on the agent's own chat client does not deadlock construction.
  - Keeps the default message filters.
  - Uses no `StateBag` keys, so `StateKeys` stays empty and adds nothing to the key collision check.
- `ReasonletAgentOptions` mirrors `ReasonletChatOptions`:
  - `ScopeResolver`, `Recall` (default on), `Capture` (default on), `ExposeFindProcedure` (default off), `MinSimilarity`, `RecallTimeout` (default 5 seconds) and `Formatter`;
  - plus `Validate()`, following the core's pattern.
- `ReasonletAgentScope`: a public record of `ReasonletScope Scope` and `string? SubjectId`.
- No container registration of the provider itself. Options are per agent, and Thalos builds one provider per agent in `CreateProvider(AgentDefinition)`, so a container singleton would force every agent onto one set of options. Hosts call `new ReasonletContextProvider(services, options)` once per agent, and one instance then serves all that agent's sessions. The host still calls `AddMnemosyne` and `AddReasonletCapture`. Without the memory, or with capture on and no `AddReasonletCapture`, the first run counts the error and goes on. It does not throw at construction, because Thalos builds agents lazily, where a throw would break the agent.
- `find_procedure` name collisions follow 3.5. The tool is not added when the agent already has a tool of that name. Capture removes calls by the name `find_procedure`, so a host tool of that name is removed from captures too. The README states this.

## Run flow

**Before the run (`ProvideAIContextAsync`):**
1. Resolve the scope through `ScopeResolver`. Null means a skip with reason `no_scope`: return an empty `AIContext`, and capture nothing later.
2. If `Recall` is on and the request has user text, call `RecallAsync` with that text, the scope, `Top = 1` and the floor, under `RecallTimeout`. A hit becomes `Instructions`, and its id is kept as the run's injected parent. A miss, a timeout, an error or an exception means no instructions. The caller's own cancellation is rethrown.
3. If `ExposeFindProcedure` is on, create a `find_procedure` for the scope and return it in `Tools`.
4. Store the per-run state, made of scope, subject, injected parent, tool instance and start time, against the session.

**After the run (`StoreAIContextAsync`):**
1. The base `InvokedCoreAsync` already skips failed runs.
2. Take the per-run state. Without it (null session), use the scope from the resolver and no parent.
3. If `Capture` is on, call `TryCapture` with the request messages, the response messages, the parent, the lookups, the duration and the response id where Agent Framework exposes one. A false return or an exception is counted, never thrown.
4. Remove the per-run state.

**The capture itself** is unchanged from 3.5: removing `find_procedure` steps, the pending-call check, parent inference from lookups, naming after the tool shape, the guard, the review gate and the judge. All of it runs in the existing processor.

## #45: parentless captures of a known shape

`ReasonletPostgreSqlStore.RememberAsync` (`src/Mnemosyne.NET.PostgreSql/ReasonletPostgreSqlStore.cs`, the `ParentId is null` branch near line 240) gets a lookup before it inserts:

- **Lookup.** Find a Reasonlet in the scope with the same `content_hash`. Prefer an `Active` one over a `PendingReview` one, then the newest. These are the only two statuses: a reject deletes the row, so a shape a reviewer rejected has no row to match and comes back as a new one.
- **On a match**, record an execution against it, exactly like the parent-hash-equal branch, and return `ReasonletCaptureKind.ExecutionOnly`.
- **Otherwise**, insert a new Reasonlet as today.
- **Concurrency.** Two concurrent parentless captures of one new shape must not both insert. Take a transaction-scoped advisory lock keyed on scope and hash before the lookup. My call, and the builder may use an equivalent.
- **No unique index.** One hash can legitimately sit on several rows: versions in different lineages, and duplicates stored before this change. So the lock is the only guard against new duplicates. A plain index on `(scope, content_hash)` in migration `0005` keeps the lookup from scanning the scope. My call.
- With a `ParentId`, nothing changes: the parent-hash-equal branch still records an execution against the named parent.
- **Other stores.** The PostgreSQL store is the only `IReasonletStore` the repo ships. The `IReasonletStore.RememberAsync` docs gain the rule, so custom stores know to follow it. The test fakes in `tests/Mnemosyne.NET.Tests/Core/Fakes.cs` and `tests/Mnemosyne.NET.AotSmoke/Program.cs` follow it only where a test depends on it.
- **Test changes.** `UseReasonletsTests.WithReviewGatePendingCaptureIsNotInjected` changes from two pending rows to one pending row with two executions. A new store test covers repeat, concurrency, preference order and the rejected case.

## Tests

- **Unit, provider** (fake memory, fake sink, a real `ChatClientAgent` over a fake chat client, as in the probe):
  - recall on user text, and none on a run without it;
  - the suggestion in `Instructions`, never in `Messages`;
  - no injection on no match, timeout, error or exception;
  - the caller's cancellation rethrown;
  - `find_procedure` added per run only when switched on;
  - the hand-off carries request and response messages with the tool loop, and the injected parent;
  - a failed run is not captured;
  - a null scope and a null session behave as specified;
  - concurrent runs on different sessions keep their own state;
  - streaming runs are captured once;
  - an abandoned stream is not captured, and the next run on that session gets fresh state;
  - the provider's source reaches the provenance, and `UseReasonlets` keeps its own.
- **Unit, core:**
  - `TryCapture` on a full or disposed queue returns false and counts;
  - `UseReasonlets` still behaves the same over the sink (the existing tests stay green);
  - the `find_procedure` JSON has no `intent`.
- **Integration (PostgreSQL + pgvector):**
  - an agent run end to end becomes a Reasonlet;
  - a second run of the same question recalls it, injects it, and records an execution against it;
  - two agents get two scopes;
  - the #45 store tests.
- **AOT:** the smoke app builds an agent with the provider, publishes with no warnings and runs.

## Open Questions

None blocking. `AIContextProvider` has no response id, so the run id stays null unless `ResponseMessages` carries a `MessageId`; the builder checks this. It is not a design question.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Agent Framework changes the provider hooks before 1.0 of our API | The provider breaks on a host upgrade | The floor is 1.24, the surface was the same through 1.27, and CI builds against the floor. Renovate PRs for the test-only reference show breaks early. |
| `ConditionalWeakTable` per session misses concurrent runs on one session | A run is captured with the wrong parent | Thalos runs one turn per session at a time. The limit is documented, and the second run's capture falls back to no parent. |
| Making the capture API public freezes a shape too early | A breaking change in milestone 4 | That is the point of pushing before the freeze. Keep the surface to the record, the sink, the lookups and the recall step. |
| The #45 lock adds contention on hot shapes | Slower captures | Captures are in the background, and the lock is per scope and hash, held for one short transaction. |
| Per-agent sharing leaks text other than intent | Cross-user leak | Names are tool shapes (3.5), steps hold argument names only, and #47 removes intent. The README states what a scope's users can see. |

## Amendments (2026-11-05)

Recorded after implementation, so the spec matches the code as built.

- **Name of the capture record.** The public record of one finished run is `ReasonletCaptureRun`, not `ReasonletRun`. `ReasonletRun` already exists in `Mnemosyne.NET.Abstractions` as the execution record, and the same name in two namespaces breaks the build for hosts that import both. Every `ReasonletRun` above that means the capture record reads `ReasonletCaptureRun`.
- **Two public counting entry points.** The Agent Framework package is another assembly and core grants it no `InternalsVisibleTo`, so core exposes the counters it needs: `ReasonletSuggestions.CountFailed(Exception, string integration)` counts a recall that could not run, as outcome `exception` on `mnemosyne.chat.recalls`, and `ReasonletCaptures.CountFailed(Exception)` counts a failed hand-off on `mnemosyne.capture.queue`. The chat middleware uses the same two.
- **Null session.** In the table row "Correlating the two hooks", "and is counted" is replaced by this. With a null session the end hook has no stored state, so it asks the scope resolver again. A run with no scope, or whose resolver throws, counts nothing at that point, because the start of the run already counted it as `no_scope` or `exception`. A run with a scope is captured without a parent and without lookups, and the queue's normal counters apply.
- **Test location.** The agent tests live in `tests/Mnemosyne.NET.Tests/AgentFramework`, with `InternalsVisibleTo` from the new package, and not in a new test project.
