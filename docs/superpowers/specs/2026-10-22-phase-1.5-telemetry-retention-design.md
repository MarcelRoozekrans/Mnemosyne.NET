# Phase 1.5 Design — Telemetry and retention

**Date:** 2026-10-22
**Phase:** 1.5
**Surface:** Data
**Stage:** phase (one phase, implementation-ready)

This design builds on the [phase 1.4 store](2026-10-22-phase-1.4-postgres-store-design.md)
and on the roadmap amendment of 2026-10-22: telemetry, not compliance (**user**).
Decisions are marked **user** or **my call**.

## Goal

Two things, both in the PostgreSQL store:

- **Telemetry.** Every store operation emits OpenTelemetry signals into the
  host's own pipeline, so an operator can see what Mnemosyne did and how it
  performed.
- **Retention.** A host-run `PruneAsync` keeps the store bounded. It deletes
  old run records and Reasonlets that are no longer used.

## Approach

### Telemetry (user: OpenTelemetry signals, no audit table)

**Names** (**my call**):
- One `ActivitySource` and one `Meter`, both named `Mnemosyne.NET`.
- The names are public constants on `MnemosyneTelemetry` in Abstractions:
  `ActivitySourceName` and `MeterName`.
- A host enables them with `.AddSource(MnemosyneTelemetry.ActivitySourceName)`
  and `.AddMeter(MnemosyneTelemetry.MeterName)`.
- There is no separate SDK-wiring package. A single name per signal can't be
  mis-wired the way Rag.NET's two meters could.

**Activities.** There is one activity per store operation:

| Activity | Tags |
|---|---|
| `mnemosyne.migrate` | |
| `mnemosyne.remember` | `mnemosyne.capture_kind`; and on success, `mnemosyne.reasonlet.id` and `mnemosyne.reasonlet.version` |
| `mnemosyne.get` | |
| `mnemosyne.execution.append` | |
| `mnemosyne.feedback.append` | |
| `mnemosyne.search` | `mnemosyne.search.limit`, `mnemosyne.search.returned`, `mnemosyne.search.top_similarity` |
| `mnemosyne.erase` | `mnemosyne.erase.by` (`scope` or `subject`), `mnemosyne.erased.reasonlets`, `mnemosyne.erased.executions` |
| `mnemosyne.prune` | `mnemosyne.pruned.reasonlets`, `mnemosyne.pruned.executions` |

Every activity also gets these:
- On a failure result: `error.type` set to the `MnemosyneErrorCode` name, and
  `ActivityStatusCode.Error`.
- When an exception propagates: the exception recorded as an activity event,
  and status Error.

**Metrics:**

| Instrument | Type | Tags |
|---|---|---|
| `mnemosyne.operations` | counter | `mnemosyne.operation`, `mnemosyne.outcome` (`ok` or the error code) |
| `mnemosyne.operation.duration` | histogram, in seconds | `mnemosyne.operation` |
| `mnemosyne.reasonlets.remembered` | counter | `mnemosyne.capture_kind` |
| `mnemosyne.search.returned` | histogram | none |
| `mnemosyne.erased.reasonlets`, `mnemosyne.erased.executions` | counters | none |
| `mnemosyne.pruned.reasonlets`, `mnemosyne.pruned.executions` | counters | none |

**Privacy** (**my call**). No signal carries user data:
- no question text, intent, name, graph, tags, scope, subject or run id;
- ids and versions are opaque, so they are allowed.

Scope often names a tenant and subject names a person, and telemetry
pipelines are exported, sampled and kept elsewhere. So they stay out. An
operator who needs tenant breakdowns can add them in their own wrapper.

**Recall telemetry.** The tag for which Reasonlet a recall chose, with its
score, belongs to the facade in phase 1.6. That phase adds it to the
`mnemosyne.recall` activity, using the names fixed here. Phase 1.5 only
instruments the store.

**Cost.** Activities are created only when a listener is attached
(`ActivitySource.StartActivity` returns null otherwise). Metrics go through
`Meter` instruments, which are cheap when nothing listens. The store stays
AOT-clean, because `System.Diagnostics.DiagnosticSource` is in-box.

### Retention (user: old runs and unused Reasonlets, host-run PruneAsync)

**Contract.** These are additions to Abstractions. The API is pre-1.0, so
adding a port member is allowed:

```csharp
public sealed record ReasonletRetention
{
    public ReasonletScope? Scope { get; init; }            // null: every scope
    public TimeSpan? ExecutionsOlderThan { get; init; }     // null: keep all runs
    public TimeSpan? ReasonletsUnusedFor { get; init; }     // null: keep all Reasonlets
    public UnitResult<MnemosyneError> Validate();
}

public sealed record ReasonletPruneResult
{
    public required int Reasonlets { get; init; }
    public required int Executions { get; init; }
}

// IReasonletStore gains:
ValueTask<Result<ReasonletPruneResult, MnemosyneError>> PruneAsync(ReasonletRetention retention, CancellationToken ct);
```

`Validate()` rejects three things:
- a policy with both windows null, since it would do nothing;
- a window that isn't positive;
- an invalid scope.

The facade, `IReasonletMemory`, doesn't expose pruning. Pruning is
administration, not memory use (**my call**).

**Old run records.**
- Delete executions whose `executed_at` is earlier than now minus
  `ExecutionsOlderThan`. Their feedback cascades.
- The metrics counters keep their totals, because a pruned run still
  happened.
- This makes the counters the source of truth for totals, so the erase recount
  from phase 1.4 has to change (see "Erase and metrics" below).

**Unused Reasonlets.**
- "Used" means **executed**, not recalled (**my call**). Recall is the hot
  path, and recording it would add a write to every search.
- `reasonlet_metrics` gains a `last_executed_at timestamptz not null` column,
  set by every execution insert. It is null-free, because every Reasonlet has
  at least the execution its remember created.
- **Use is judged per lineage** (**user**). A Reasonlet is used when it or
  any of its descendants has a `last_executed_at` or a `created_at` at or after
  the cutoff. So a superseded version stays as long as a later version is run
  or remembered. A lineage's history goes only once the whole subtree is idle.
- It follows that an unused Reasonlet's descendants are all unused too.
  Pruning deletes whole idle subtrees: no kept child ever loses its parent, and
  no parent link is cut by pruning. Ancestors stay if another branch below them
  is still in use.
- `PendingReview` Reasonlets follow the same rule as `Active` ones. A capture
  left unreviewed for the whole window is stale (**my call**).
- A deleted Reasonlet's runs and metrics go with it. The deleted runs are
  counted in `ReasonletPruneResult.Executions`.

**Cutoff.** A prune reads `now()` once, in its first statement, and uses that
cutoff for every batch (**my call**). A long prune therefore has a fixed
target and ends: rows that become idle while it runs wait for the next prune.

**Batches** (**my call**). No transaction deletes more than 1,000 rows, an
internal constant.
- **Run records:** each batch deletes up to 1,000 executions older than the
  cutoff, across every scope the policy covers.
- **Idle subtrees:** each batch picks idle subtree roots in `(scope, id)`
  order and deletes them deepest-first.
  - A subtree whose rows exceed the bound has its executions deleted first, in
    batches of their own, before its Reasonlets go. All of those runs are
    older than the cutoff, because the subtree is idle, so this is ordinary run
    pruning and keeps the counters.
  - One batch never splits a subtree's Reasonlets from each other: a subtree
    with more than 1,000 Reasonlets is deleted bottom-up over several
    batches, leaves first. Each batch leaves a smaller idle subtree, never a
    child without its parent.
- Run-record pruning happens before Reasonlet pruning, so runs aren't counted
  twice.

**Locks and the re-check** (**my call**). Erase can delete whatever it
selected, because `subject_id` never changes. Prune can't, because an append or
a remember can make a subtree used again between the select and the lock. So
each Reasonlet batch:
1. locks the candidate Reasonlets deepest-first, `FOR UPDATE`;
2. then locks their `reasonlet_metrics` rows, in the same order that appends
   use;
3. then re-evaluates "idle" in a fresh statement, which under READ COMMITTED
   sees every commit that landed before the locks, including new children;
4. and deletes only the subtrees that are still idle. Ones that became used
   are skipped and not counted.

An append or remember that arrives after the locks waits, then gets `NotFound`
as it would after an erase. Pruning only locks rows inside idle subtrees, plus
their metrics. It never locks a kept ancestor, because deleting a child doesn't
lock the parent row it references. So it takes no lock that phase 1.4's
writers take in a different order.

**Failures** (**my call**).
- A batch that hits a deadlock or serialization failure (`40P01`, `40001`) is
  retried in-process up to three times before the prune gives up with
  `Conflict`. Any other failure ends the prune at once.
- On failure, the earlier batches stay committed and the result carries no
  counts. The prune is safe to run again: a retry deletes only what is still
  older than its new cutoff.
- The telemetry still reports what was deleted: the `mnemosyne.pruned.*`
  counters and activity tags count every committed batch, including on the
  failure path. Operators' totals stay exact.

**Erase and metrics** (my call: fixes a conflict that retention creates).
- Phase 1.4's subject erase recomputes a kept Reasonlet's metrics from its
  remaining executions. Once runs can be pruned, that undercounts.
- Erase instead **subtracts** what it removes: `runs` and `successes` go down
  by the removed rows.
- Order within the erase transaction:
  1. after the Reasonlet locks, the executions to delete are locked in id
     order, and their ids kept;
  2. then the metrics rows of the kept Reasonlets that lose runs are locked in
     id order. That is Reasonlets, then executions, then metrics: the same
     order as phase 1.4 and as the final delete's cascades, so two overlapping
     erases cannot deadlock;
  3. one statement then deletes exactly the locked executions and subtracts
     them from those metrics rows. Its snapshot is taken after the metrics
     lock, so the timestamp recompute sees every append that committed before.
     The erase covers what existed when it took its locks, as phase 1.4's
     erase already promises.
- A timestamp is recomputed when the removed latest value is at or after the
  stored one. The new value is the latest of the remaining runs, or the stored
  value when no qualifying run remains.
  - That covers two cases: no run remains at all, or runs remain but none is a
    success while pruned successes once existed.
  - The kept value is documented as "possibly older".
  - For `last_executed_at`, this keeps the column non-null. A null would read
    as "never used" to the retention rule.
  - Ties need no special case. A remaining run with the same timestamp
    recomputes to the same value.
- **What erasure leaves behind.** Counts of runs that were pruned before the
  erase stay in `runs` and `successes`, because nothing can identify them any
  more. They are bare integers with no link to a person, so they are anonymous
  aggregates, not personal data. The README's erasure section says this, next
  to its at-rest note.

**Where the delete time comes from.** The database clock, `now()`, as with
every other timestamp in the store.

## Tests

- **Telemetry.**
  - Each operation produces exactly one activity with the right name and tags.
  - Failures set `error.type` and status Error.
  - Exceptions are recorded.
  - Every counter and histogram records the right value and tags.
  - No signal ever contains the scope, subject, question, intent, name, graph
    or tags. One test captures everything a full workflow emits and scans it
    for sentinel strings planted in each of those fields.
- **Retention.**
  - Each window works alone, and both work together.
  - Scope-limited versus every scope.
  - Counters survive run pruning.
  - A superseded version stays while a later version is run or remembered
    inside the window. A fully idle lineage goes whole. An ancestor stays when
    one branch below it is in use and another is idle.
  - `PendingReview` Reasonlets are pruned like `Active` ones.
  - Batching: more than 1,000 executions, and a subtree of more than 1,000
    Reasonlets, prune completely.
  - The re-check: a Reasonlet that is executed, or gets a new child, between
    the candidate select and the lock survives and isn't counted.
  - A retried prune deletes only what is still idle.
  - Telemetry counts committed batches even when a later batch fails.
  - A `Validation` result for each invalid policy.
- **Erase and metrics.** Prune old runs, then subject-erase. The counters
  equal the pruned history plus the remaining runs, minus the erased runs.
- **AOT.** The smoke run adds `PruneAsync`, and it runs with an
  `ActivityListener` attached so the instrumentation runs under AOT.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| `last_success_at` can't be restored once the runs that set it are pruned | The freshness ranking in phase 1.6 sees an older success than reality, or keeps a stale one | Documented. Phase 1.6 uses `last_executed_at` for freshness where that fits better |
| A prune across every scope on a huge store takes long | Contention while it runs | Batches of 1,000 rows, one transaction each. The host schedules it off-peak. The milestone 4 benchmark measures it |
| Telemetry tag names are hard to change after 1.0 | Breaking dashboards | Names are fixed now, follow OpenTelemetry style, and go through the milestone 4 API review |
