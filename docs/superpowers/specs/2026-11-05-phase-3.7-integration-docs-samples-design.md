# Phase 3.7 Design — `Integration docs and samples`

**Date:** 2026-11-05
**Phase:** `3.7`
**Surface:** `Docs`
**Stage:** phase (one phase, implementation-ready)

## Goal

A developer who wants to add Mnemosyne to a chat pipeline or an Agent Framework agent finds a guide for it on the docsite and a sample they can run offline. This closes the last milestone 3 criterion, "Docs and samples cover every integration".

## Intent

Phases 3.1 to 3.6 shipped capture, the redaction hook, the review gate, the AI.Sentinel adapter, `UseReasonlets` with `find_procedure`, and the Agent Framework provider. The docsite does not describe most of it:
- Nothing on the docsite explains capture, the redaction hook or the review gate.
- `UseReasonlets` and `find_procedure` appear only inside the chat-evaluator guide.
- The Sentinel adapter and the Agent Framework provider exist only as package READMEs.
- The two samples, store-and-recall and evaluation, cover milestones 1 and 2. Nothing runnable shows the integrations.

The existing samples set the standard: no key, no model, Docker plus the .NET 10 SDK, a self-check that exits 1 on a difference, and a CI step that gates `publish-nuget`. The new samples keep it. The integrations need a chat model, so a scripted stand-in replaces it, the way `HashingEmbeddingGenerator` replaces the embedding model.

**Goals**
- Three new guides under `docs/guides`, one per integration path.
- Two new samples that run offline, check their own output, and gate releases in CI.
- A way into the guides from `getting-started.md`, and the samples page updated.
- Package READMEs link to the guides, so each fact has one home.

**Non-goals**
- **Real-model samples.** The guides show how to swap in a real model, as the samples page does for embeddings. No sample needs a key.
- **Public API changes.** If writing the docs exposes a wrong or missing API, it is filed as an issue, not changed here.
- **The Thalos adapter and the Daedalus wiring.** They are PRs in those repos, per the milestone design.
- **A benchmarks or 1.0 docs pass.** That is milestone 4.

**Anti-goals**
- **A sample that passes while the docs are wrong.** Every number and outcome a guide quotes from a sample must be one the sample checks.
- **Sample code that drifts from the packages.** Samples reference the projects, as the existing two do, so a breaking change fails the build.

## Approaches

**How the new samples get a chat model.** Chosen: a scripted `IChatClient` (offline, deterministic, self-checking, CI-gated). Rejected: a real model only, since CI cannot run it and the docs would drift. Rejected: both, since it doubles the surface for little gain. The user chose this on 2026-11-05.

**How many samples.** Chosen: two, a chat pipeline sample and an Agent Framework sample. Rejected: one, which leaves the Agent Framework guide without a runnable example. Rejected: three, which splits capture, redaction and review into its own project at the cost of another project and CI step. The user chose this on 2026-11-05.

**Redaction in the chat sample.** Chosen: the real `Mnemosyne.NET.Sentinel` adapter with `AddAISentinel`, blocking a capture that carries a credit card number. Rejected: a hand-written `ICaptureGuard`, which would leave the adapter package without a runnable example. The user chose this on 2026-11-05.

## The pieces

### The guides

Three new files under `docs/guides`, in the style of the existing guides (concrete code first, then behaviour, then limits). The guides are the home of the facts. The package READMEs keep their reference tables and link to the guide for the walkthrough.

1. **`chat-pipeline.md` — `UseReasonlets` and `find_procedure`.**
   - Setup in the order a host does it: store, `AddMnemosyne`, `AddReasonletCapture`, `UseReasonlets` on the client.
   - What a call does: recall, injection, the skip reasons, the background capture.
   - `find_procedure`: when to expose it, what it returns, what it never shows.
   - The rule for judges and guards that call a chat model (a client without `UseReasonlets`), linking to `chat-evaluator.md`.
   - Limits as 3.5 left them.
2. **`capture-and-review.md` — capture, redaction and the review gate.**
   - How a transcript becomes a tool-shape graph, and the three outcomes: new Reasonlet, new version, execution of the recalled one.
   - The capture guard: `ICaptureGuard`, the verdicts, `Blocked` and `Unavailable`, `GuardTimeout`.
   - The Sentinel adapter: registration, `BlockAtSeverity`, what is scanned, the known gap with a throwing detector (AI.Sentinel#550).
   - The review gate: `RequireReview`, `PendingReview`, `ApproveAsync` and `RejectAsync`, what recall does meanwhile.
3. **`agent-framework.md` — `ReasonletContextProvider`.**
   - Setup, scope and subject, what a run does, `find_procedure` on an agent, limits, and why not to combine it with `UseReasonlets`.
   - A short "provider or middleware" section: the provider for agents, `UseReasonlets` for plain chat clients.

`getting-started.md` gains a "Pick an integration" section after the store-and-recall walkthrough: three short entries, each linking to its guide. `docs/index.md` lists the same three pages where it lists the packages.

The existing guides are not rewritten. Where they already own a fact, such as `telemetry.md` for the instruments, the new guides link to it.

### The shared fake chat client

`samples/Shared/ScriptedChatClient.cs`, next to `HashingEmbeddingGenerator`, linked into each sample project the same way.
- An `IChatClient` that returns a scripted answer per call. It can emit tool calls and then a final answer, so a run has a tool shape to capture.
- It can answer a judge call with a scripted verdict, if a sample needs the chat evaluator. Whether a sample needs it is the builder's call.
- Its doc comment says what the stand-in is not, as the hashing generator's does.
- It has unit tests in `tests/Mnemosyne.NET.Tests/Samples`, because the samples' self-checks depend on its behaviour, as they do for the hashing generator.

### Sample 1: `Mnemosyne.Samples.ChatPipeline`

A console app with a Docker compose file and a README, like the existing two.
1. Wires up the PostgreSQL store, the hashing embedder, `AddMnemosyne` with `RequireReview` on, `AddAISentinel`, `AddMnemosyneSentinel`, `AddReasonletCapture`, and a scripted client with `UseReasonlets`.
2. **Act 1.** A first question runs a tool loop through the pipeline. The capture is stored as `PendingReview` and recall does not return it yet.
3. **Act 2.** The sample approves it with `ApproveAsync`. The same question is asked again, the pipeline injects the recalled procedure, and the sample shows that the scripted client received it.
4. **Act 3.** A question that carries a credit card number is blocked. The sample shows the `Blocked` outcome and that nothing was stored.
5. Checks every outcome and exits with code 1 if one differs. Erases its scope at the end.

It uses a database of its own, with 256 dimensions, as the other two do. The self-check does not wait on the background worker with a fixed sleep. The queue's drain is internal and closes the queue, so it cannot run between acts in one host. The default (my call, open to the builder) is a bounded poll of the store for the expected state.

### Sample 2: `Mnemosyne.Samples.AgentFramework`

A console app with a compose file and a README.
1. Wires up the same store and embedder, `AddMnemosyne` and `AddReasonletCapture`, and builds a `ChatClientAgent` with a `ReasonletContextProvider` over the scripted client.
2. **Run 1.** The agent solves a question through a tool loop. The provider recalls nothing, and the run is captured.
3. **Run 2.** A similar question. The provider recalls the procedure from run 1 and adds it to the run's instructions. The sample shows it in the scripted client's received instructions, and shows that the run was recorded as an execution of the recalled Reasonlet.
4. Checks every outcome and exits with code 1 if one differs. Erases its scope at the end.

If the sample needs a new version of the chat sample's helpers, the helper goes in `samples/Shared`, not in a package.

### CI

Two new steps in the existing job that runs the samples, each with a database of its own, as the evaluation sample has. Both gate `publish-nuget` through `aot-publish`, like the first two. The solution file lists the new projects.

### The samples page

`docs/samples.md` gets two new sections in the format of the existing two: what it does, how to run it, the output with the numbers the sample checks, and what is a stand-in. The scripted client gets its own "is a stand-in" paragraph with the swap to a real model through Microsoft.Extensions.AI.

## Constraints

- **Native AOT and trim.** The samples are not packed and not in the AOT gate. The packages stay as they are.
- **The Sentinel dependency.** The chat sample references AI.Sentinel 4.x through central package management, at the version already pinned. The sample relies on the PII detector's severity for a credit card number (Critical). The test for that is the sample's own self-check.
- **No public API change.** A needed change is an issue.
- **Docsite build.** The site builds with the new pages. The sidebar autogenerates from `docs/guides`, so each page needs a `sidebar_position` consistent with the existing guides.
- **Style.** The docs follow the repository's existing prose rules, and the `anti-slop` skill applies to every page and README before it is committed.

## Tests

- **Unit:** `ScriptedChatClient`, covering its scripts, tool calls, cancellation and its reported shape.
- **Samples as tests:** each sample's self-check is the assertion for its guide's numbers. CI runs both on every pull request to `main`.
- **Docs:** the docsite builds without broken links. Every code snippet that a guide quotes from a sample is the sample's code, or is marked as a sketch.
- **Regression:** the existing unit, PostgreSQL and AOT checks stay green. The two existing samples run unchanged.

## What is left to the builder

- Exact page titles, `sidebar_position` values and section order within each guide.
- The scripts of the fake client and the questions the samples ask.
- How long the bounded poll waits and what state it polls for.
- Whether the chat sample needs the chat evaluator and a scripted judge. The default is no: the samples show recall, capture, redaction and review, and evaluation already has its sample.
- The port numbers of the new compose files, which must not collide with 5432 and 5433.

## Open Questions

None that block the plan.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The credit card block depends on AI.Sentinel's detector severity | A detector change fails CI, and the guide's claim is wrong | The sample's self-check is the assertion. The guide names the detector and the severity, and says the sample checks them. |
| The background capture makes the self-check flaky | A sample that fails on a slow runner blocks releases | The self-check waits with a bounded poll, never a fixed sleep. Both new samples run several times locally before the first push. |
| The guides repeat facts from the READMEs and the existing guides | Two homes for a fact drift | The guides own the walkthrough. READMEs and `telemetry.md` keep their reference tables and are linked, not copied. |
| The docs expose an API wart | Pressure to change the API in a docs phase | File an issue per the project's rule. Milestone 4 owns the API freeze. |
| Two more databases and two more CI steps lengthen the sample job | Slower pull requests | Each sample is small. The steps share the job's PostgreSQL service. |
