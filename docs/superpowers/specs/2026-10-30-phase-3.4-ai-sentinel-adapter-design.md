# Phase 3.4 Design: AI.Sentinel adapter

**Date:** 2026-10-30
**Phase:** 3.4
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)

The fourth phase of milestone 3. It builds on the [milestone 3 design](2026-10-30-milestone-3-design.md) and implements the `ICaptureGuard` port from the [phase 3.2 design](2026-10-30-phase-3.2-redaction-hook-design.md). Decisions are marked **user** (chosen by the user in the brainstorm) or **my call**.

## Goal

A new package, `Mnemosyne.NET.Sentinel`, whose `SentinelCaptureGuard` runs AI.Sentinel's detection pipeline over the text a capture would store, and blocks the capture when a detection reaches a configurable severity. `AddMnemosyneSentinel()` registers it as the host's `ICaptureGuard`.

## Intent

Phase 3.2 gave `RememberAsync` a seam that asks a guard before anything is persisted, and left detection to AI.Sentinel. This phase is that adapter: the default way a host gets "sensitive text never lands in shared memory" without writing detection logic. Core Mnemosyne keeps no Sentinel dependency, per the milestone's package decision.

Persisted memory is a different risk from live chat traffic. A chat message that trips a High detector is gone after the turn; a stored question is recalled into other sessions, possibly for other subjects, until it is erased or pruned. So the guard's notion of "block" is Mnemosyne's own, stricter than Sentinel's chat defaults (**user**).

## Goals

- A capture whose question, intent or name trips an AI.Sentinel detector at or above the configured severity is blocked, and so never stored.
- One line of setup on top of the host's existing `AddAISentinel()`: `services.AddMnemosyneSentinel()`.
- A host that wants a different detector configuration for memory than for chat, such as detectors disabled or escalation settings changed, can point the guard at a named Sentinel pipeline, without Mnemosyne configuring Sentinel (**user**).
- The verdict carries only the guard's name and AI.Sentinel's detector id. The detector's `Reason` text, which can quote content, goes nowhere.
- The package passes the Native AOT gate.

## Non-goals

- **Scanning the answer** (**user**). The answer is never stored. It reaches only the judge, through the host's `IChatClient`, which the host protects with AI.Sentinel's chat middleware, as phase 3.2 documented.
- **Scanning the graph or the provenance** (**my call**). The graph holds tool names and argument names, which the application defines, not the user. Provenance holds the source, run and subject ids and host tags, which are host metadata. A host that puts user text into tags is responsible for it. This keeps detector false positives on identifiers out.
- **Configuring AI.Sentinel.** The host registers Sentinel with `AddAISentinel()` or `AddAISentinel(name, …)`. The adapter neither calls those nor exposes `SentinelOptions` in its API (**user**, pipeline question).
- **Using Sentinel's intervention engine, audit store or alerts.** The adapter calls `IDetectionPipeline.RunAsync` directly, as Thalos.NET's `SentinelContentScanner` does. A blocked capture shows up in Mnemosyne's telemetry from phase 3.2, not in Sentinel's audit log.
- **Logging.** The guard has no logger. Phase 3.2's telemetry already records the block and the detector; a log line would be the one place the reason text could leak.
- **Moving Thalos.NET.Sentinel to AI.Sentinel 4.x.** That is a PR in the Thalos.NET repo, needed before Daedalus wires both adapters into one host.

## Approaches

### Which detections block (**user**)

| Approach | Trade-off | Outcome |
|---|---|---|
| Own threshold option, default High and above | Stricter than chat, independent of how the host tunes Sentinel for chat traffic. One more knob. | **Chosen** |
| Reuse Sentinel's `OnCritical` … `OnLow` actions; block when the action is `Quarantine` (Thalos's approach) | One knob for the host, but by default only Critical blocks, which is tuned for live chat, not persisted memory | Rejected |
| Block on any non-clean detection | Strictest, drops many harmless captures on Low hits | Rejected |

### Which pipeline runs (**user**)

| Approach | Trade-off | Outcome |
|---|---|---|
| Host's default `IDetectionPipeline`, with an optional pipeline name for a keyed one | Sentinel stays configured in one place; isolation is available | **Chosen** |
| Host's default pipeline only | Simplest, but memory and chat share one detector configuration | Rejected |
| The adapter registers its own `AddAISentinel("mnemosyne", …)` | Always isolated, but duplicates Sentinel setup (embedding generator, user detectors) and ties the adapter's API to `SentinelOptions` | Rejected |

### AI.Sentinel version (**user**)

| Approach | Trade-off | Outcome |
|---|---|---|
| 4.x, the current major (4.1.1) | Current API. Forces `Microsoft.Extensions.AI.Abstractions` 10.10.1 → 10.11.0 and the other bumps below. Until Thalos.NET.Sentinel moves off 2.3.1, a host using both adapters gets one Sentinel version across two majors. | **Chosen** |
| 2.3.1, matching Thalos.NET | Coexists with Thalos today, but starts two majors behind and needs the same bump later | Rejected |

This supersedes the milestone design's "AI.Sentinel 2.x, the version Thalos.NET uses".

## Decided behaviour

### What is scanned (**user** for the fields, **my call** for the shape)

The guard builds one `SentinelContext` per capture with one `ChatRole.User` message for each of `Question`, `Intent` and `Name` that is not null or blank, in that order, and runs the pipeline once. One run keeps the cost to one pass of the semantic and LLM-escalating detectors. Separate messages keep the fields from running into each other in detectors that look at single messages; `SentinelContext.TextContent` still joins them for detectors that read the whole text.

Context fields:
- `SenderId` and `ReceiverId`: the resolved pipeline's `SentinelOptions.DefaultSenderId` and `DefaultReceiverId`, as Thalos does.
- `SessionId`: the capture's `Provenance.RunId` when it is not null or blank, otherwise a fixed `mnemosyne-capture`. AI.Sentinel's `SessionId` throws on a blank value, so the fallback covers both. It ties a block to the run in Sentinel-side telemetry; it is an id, not content.
- `History`: empty. `LlmId` and `SystemPrompt`: null.

A capture with no scannable text cannot occur: `ReasonletCapture.Validate` requires a non-blank question, and the facade validates before it calls the guard.

### Verdict (**user** for the threshold, **my call** for the details)

- No detection in `PipelineResult.Detections` has a severity at or above `BlockAtSeverity`: `CaptureVerdict.Allow(GuardName)`. The guard filters on each detection's `Severity`; `Detections` can hold entries of severity `None`, so neither its count nor `IsClean` alone decides.
- Otherwise: `CaptureVerdict.Block(GuardName, detector)`, where `detector` is the `DetectorId.Value` of the highest-severity detection at or above the threshold. Ties go to the first in pipeline order, so the verdict is deterministic.
- The detection's `Reason` is never read.

`DetectorId` values are AI.Sentinel's short ids such as `SEC-32`. A user detector registered with the host's Sentinel could carry an id longer than `EvaluationLimits.MaxEvaluatorLength` or one that is not valid UTF-16. Such a verdict fails `CaptureVerdict.Validate`, and the facade treats an invalid verdict as an adapter bug and throws. To keep a host's detector naming from breaking captures, the guard truncates the id to the limit, counted in code points as `Check.MaxLength` counts them, never splitting a surrogate pair; an id that is blank or not valid UTF-16 is replaced by `invalid-detector-id` (**my call**). Either way the capture is still blocked.

### Errors

- An exception from the pipeline propagates. Phase 3.2's facade already treats any exception, and a cancellation while the caller's token is not cancelled, as the guard being down: `Unavailable`, fail closed, with only the exception type in the detail. The adapter adds no error mapping of its own.
- The adapter never returns an error result.

### Options (**user** for the threshold and the pipeline name, **my call** for the rest)

```csharp
public sealed class SentinelCaptureGuardOptions
{
    // The lowest AI.Sentinel severity that blocks a capture. Defaults to Severity.High. Severity.None is invalid.
    public Severity BlockAtSeverity { get; init; } = Severity.High;

    // The name of a pipeline registered with AddAISentinel(name, …). Null, the default, uses the unnamed pipeline.
    public string? PipelineName { get; init; }

    // The name verdicts carry as CaptureVerdict.Guard. Same rules as MinosEvaluatorOptions.EvaluatorName. Defaults to "ai-sentinel".
    public string GuardName { get; init; } = "ai-sentinel";

    public UnitResult<MnemosyneError> Validate();
}
```

`Validate` follows `MinosEvaluatorOptions`: `Check.All` with the property name as the path. `BlockAtSeverity` must be a defined `Severity` other than `None`. `PipelineName`, when set, must not be blank.

The options take an AI.Sentinel type, `Severity`, in their public API. That is fine for an adapter package whose whole purpose is AI.Sentinel; the core packages still see none of it.

### Registration (**my call**, following `AddMnemosyneMinosEvaluator`)

```csharp
public static IServiceCollection AddMnemosyneSentinel(this IServiceCollection services, SentinelCaptureGuardOptions? options = null);
```

- Validates the options and throws `ArgumentException` on failure, as the Minos registration does.
- Registers `SentinelCaptureGuard` as the singleton `ICaptureGuard`. Its factory resolves the unkeyed `IDetectionPipeline` and `SentinelOptions`, or the keyed ones for `PipelineName`.
- The host calls `AddAISentinel()` (or the named overload) itself, in any order relative to `AddMnemosyneSentinel()`. A missing pipeline fails at the first resolution with the container's own error, as a missing `IDecisionClient` does for Minos.
- `AddMnemosyne` already resolves `ICaptureGuard` with `GetService`, so nothing in core changes.
- `SentinelCaptureGuard` is public with a public constructor taking the pipeline, the `SentinelOptions` and the guard options, so a host without DI can construct it.

### Package (**my call**)

`src/Mnemosyne.NET.Sentinel/`, shaped like `Mnemosyne.NET.Minos`: packable, `IsAotCompatible`, documentation file, `InternalsVisibleTo` the test project, a README. Root namespace `Mnemosyne.NET.Sentinel`. It references `Mnemosyne.NET.Abstractions`, `AI.Sentinel` and `Microsoft.Extensions.DependencyInjection.Abstractions`.

### Dependency bumps

AI.Sentinel 4.1.1's net10.0 dependencies are newer than the repo's pins:
- `Microsoft.Extensions.AI.Abstractions` 10.10.1 → 10.11.0, which every package uses;
- `Microsoft.Extensions.DependencyInjection.Abstractions` and `Microsoft.Extensions.DependencyInjection` 10.0.13 → 10.0.14;
- `Microsoft.Extensions.Options` 10.0.14 and `Microsoft.Extensions.AI` 10.11.0 arrive transitively; `Microsoft.Extensions.AI` is new to the repo and gets a central pin if restore asks for one.
- AI.Sentinel's exact-pinned ZeroAlloc packages (`Authorization`, `Inject`, `Mediator`, `Serialisation`, `Telemetry`, `Validation`, `ValueObjects`) do not overlap `ZeroAlloc.ORM` 2.10.0's dependencies, and `ZeroAlloc.Results` is 1.4.5 on both sides, so no conflict is expected. A restore confirms it.

The bumps go in their own `chore(deps):` commit ahead of the package, so a regression from a bump is separable from the adapter.

## Tests

- **Unit, guard:**
  - a clean result allows;
  - a detection below the threshold allows; one at it blocks; one above it blocks;
  - with several detections at or above the threshold, the verdict names the highest severity, and on a tie the first in pipeline order;
  - the context carries one user message per non-blank field among question, intent and name, in that order, and never the answer, the graph or the provenance tags;
  - the session id is the run id when set, else `mnemosyne-capture`; sender and receiver come from the resolved `SentinelOptions`;
  - a canary in the detection's `Reason` appears in no part of the verdict;
  - an over-long detector id is truncated to the limit and the verdict validates; an id that is not valid UTF-16 becomes `invalid-detector-id`;
  - a pipeline exception propagates; the caller's cancellation token reaches the pipeline.
- **Unit, options:** the defaults; each `Validate` rule.
- **Unit, DI:** the default pipeline is resolved; a named pipeline is resolved by key; invalid options throw `ArgumentException`; `AddMnemosyne` picks up the guard.
- **Unit, end to end in memory:** with the real AI.Sentinel pipeline from `AddAISentinel()` and a capture whose question carries text an official detector flags at High or above, `RememberAsync` answers `Blocked` naming that detector, and a harmless capture is stored. It uses SEC-02, `CredentialExposureDetector`: regex-based, role-agnostic and Critical, so the test needs no embedding generator or model. A fixture such as an `api_key=` assignment trips it (**my call**).
- **AOT smoke:** the guard runs under Native AOT with the real pipeline and blocks.
- **Regression:** the full existing suite passes after the dependency bumps, before the adapter lands.

No PostgreSQL integration test: the guard sits before the store, and phase 3.2's integration test already proves a blocked capture leaves no row.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| AI.Sentinel 4.1.1 is not AOT-clean | The AOT gate fails for the adapter | Check first in the plan, before the adapter is written. If it fails, the fix belongs upstream in AI.Sentinel (same author); the phase waits on that release rather than suppressing warnings. |
| A ZeroAlloc exact pin in AI.Sentinel conflicts with `ZeroAlloc.ORM` 2.10.0's | Restore fails, or a downgrade warning | Checked with the dependency bumps; an upstream release aligns the pins if needed. |
| Thalos.NET.Sentinel stays on AI.Sentinel 2.3.1 | A host using both adapters, like Daedalus, gets one Sentinel version across two majors | A Thalos.NET PR moves it to 4.x before Daedalus wires both. Tracked as an issue in Thalos.NET. |
| Semantic or LLM-escalating detectors make the guard slow | Captures time out and are dropped, fail closed | Phase 3.2's `GuardTimeout`. Every pipeline sees the same global detector pool, but a named pipeline can disable detectors for itself through `Configure<T>` and `DetectorConfiguration.Enabled`, so a host can point the guard at a named pipeline with the slow ones off. Documented in the README. |
| A false positive drops a useful procedure | Lost capture | The High default skips Low and Medium hits; telemetry names the detector, so a host can tune or use a named pipeline. |
