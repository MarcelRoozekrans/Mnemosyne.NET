# Phase 3.2 Design: Redaction hook

**Date:** 2026-10-30
**Phase:** 3.2
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)

The second phase of milestone 3. It builds on the [milestone 3 design](2026-10-30-milestone-3-design.md), whose "Flagged captures" decision fixes the outcome: a capture the hook flags is dropped, never written, and an OpenTelemetry event records that it was blocked and which detector fired, without the content. Decisions are marked **user** (chosen by the user in the brainstorm) or **my call**.

## Goal

`RememberAsync` asks an optional capture guard about every capture before doing anything else with it. A capture the guard blocks is dropped and answers a new `Blocked` error code. The telemetry records the guard and the detector, never the content.

## Intent

A capture stores the user's question as text, plus an intent and a name, in shared long-term memory that later sessions and other subjects recall. Text that was fine to send to a model in one conversation, such as a user's own email address, is not necessarily fine to keep and recall. The chat pipeline cannot decide this, because only Mnemosyne knows when something is about to be persisted. So Mnemosyne asks at that moment.

Detection is not Mnemosyne's job (**user**). Deciding what counts as sensitive belongs to AI.Sentinel, which phase 3.4 adapts as the default guard. Core Mnemosyne owns only the question-asking seam, the drop and the event. Core takes no Sentinel dependency, per the milestone's package decision, and a host without Sentinel can register its own guard or none.

## Goals

- A capture the guard blocks never reaches the intent extractor, the embedding generator, the judge or the store.
- The caller can tell a block from bad input and from an outage, by error code.
- A guard that is down never lets an unchecked capture through.
- No signal, error or exception message carries the capture's text, or the guard's own reason text.

## Non-goals

- **Detectors, patterns or any detection logic.** Phase 3.4 adapts AI.Sentinel's detectors. Core ships no guard implementation; with none registered, nothing is checked (**user**).
- **Rewriting or masking.** The guard allows or blocks. It cannot return a cleaned capture (**user**). AI.Sentinel's detectors only classify, which matches. A stored question is always what was actually asked, so its embedding and default name are unchanged.
- **Guarding `RecordExecutionAsync`** (**user**). An execution stores no text. Its question and answer go only to the judge, which is a call through the host's own `IChatClient`. The host protects that, and the intent extractor's calls, by putting AI.Sentinel's chat middleware on that client. Phase 3.7's docs can show it.
- **Several guards.** Zero or one guard is registered, like the extractor and the evaluator (**my call**). AI.Sentinel already runs many detectors behind one entry point, so composing guards in core adds nothing. A host that needs two writes a guard that calls both.
- **A quarantine or review of blocked captures.** Blocked captures are dropped, per the milestone. Phase 3.3's review gate is for allowed captures.
- **Docsite pages beyond the reference updates below.** Phase 3.7 covers the integration guides.

## Approaches

| Approach | Trade-off | Outcome |
|---|---|---|
| 1. Optional `ICaptureGuard` port injected into `ReasonletMemory`, called first in `RememberAsync` | Follows the existing extractor and evaluator pattern. Every path through `IReasonletMemory` is checked and cannot be bypassed. Touches the facade's constructor. | **Chosen (user)** |
| 2. `GuardedReasonletMemory` decorator around `IReasonletMemory`, registered by `AddMnemosyneCaptureGuard()` | Leaves the facade untouched. But a host that constructs `ReasonletMemory` directly, or registers in the wrong order, silently skips the guard, which is the wrong failure mode for a safety check. | Rejected |
| 3. Decorator around `IReasonletStore` | Runs after the extractor, the embedder and the judge have already received the text, so it breaks "check first". | Rejected |
| Guard called by the caller between `ReasonletTranscript.ToCapture` and `RememberAsync` | No facade change, but captures made by hand through `RememberAsync` go unchecked. | Rejected (**user**, placement question) |

## Decided behaviour

### Placement (**user**)

The guard runs in `RememberAsync` right after `capture.Validate()` succeeds, before the intent is resolved. It sees the capture as the caller gave it: the question, the answer, the graph, the provenance and the caller's own intent and name. It does not see the intent the extractor would derive, or the name derived from the question. Both come from the question, which the guard has already seen.

An invalid capture answers `Validation` without calling the guard, so a guard always receives a valid capture.

### Outcomes (**user** for the codes, **my call** for the details)

| Guard result | `RememberAsync` answers | Stored? | Extractor, embedder, judge called? |
|---|---|---|---|
| No guard registered | as today | as today | as today |
| Allow | continues as today | as today | as today |
| Block | `MnemosyneErrorCode.Blocked` | no | no |
| `Unavailable` result, an exception, or a timeout | `MnemosyneErrorCode.Unavailable` (fail closed, **user**) | no | no |
| Any other error code, or an invalid verdict | throws `InvalidOperationException`, as an extractor or evaluator adapter bug does | no | no |
| `OperationCanceledException` while the caller's token is cancelled | propagates | no | no |

The guard call mirrors the judge call in `ReasonletMemory.JudgeAsync`: its linked timeout source, and abandoning a guard that ignores its token. Sharing a helper between the two is the builder's call. The rules for exceptions and timeouts follow the extractor's and evaluator's (`ReasonletMemory` remarks): an exception counts as down, and so does a cancellation while the caller's token is not cancelled. The `Blocked` error's message is fixed text, and its `Detail` names the guard and the detector, never the content or the guard's reason. The `Unavailable` error's detail names only the exception type, as the extractor's does.

### Error code (**user**)

`MnemosyneErrorCode.Blocked = 5`, documented as "a capture guard blocked the capture; nothing was stored". It is a new enum member and new public API, acceptable before 1.0. `EnumNumberingTests`, both `ErrorName` switches (`RecallTelemetry`, `StoreTelemetry`) and every doc that lists the codes are updated.

### Port and verdict (**my call**)

In `Mnemosyne.NET.Abstractions`, beside `IIntentExtractor` and `IReasonletEvaluator`:

```csharp
public interface ICaptureGuard
{
    // Error codes: Unavailable when the guard's backend fails. Any other failure, and a verdict that fails
    // Validate, is an adapter bug. A guard must not quote the capture in an error.
    ValueTask<Result<CaptureVerdict, MnemosyneError>> InspectAsync(ReasonletCapture capture, CancellationToken ct);
}

public readonly record struct CaptureVerdict
{
    public static CaptureVerdict Allow(string guard);
    public static CaptureVerdict Block(string guard, string detector);

    public bool IsBlocked { get; }
    public string Guard { get; }       // names the guard, e.g. "ai-sentinel"
    public string? Detector { get; }   // the detector that fired; set exactly when blocked

    public UnitResult<MnemosyneError> Validate();
}
```

The guard receives the whole `ReasonletCapture`, not a selection of text fields, so a text field added to the capture later needs no new interface. The guard decides what to scan, and that includes `Answer`, which is never stored but would go on to the judge. Whether an answer-only hit should block is the guard's policy, not core's (**my call**, in line with detection being AI.Sentinel's job). Phase 3.4 settles it for the Sentinel adapter. The core contract documents that the answer is present and is never stored. `Guard` and `Detector` go into telemetry and errors, so they follow the same rule as `ReasonletEvaluation.Evaluator`: not blank, valid UTF-16, at most `EvaluationLimits.MaxEvaluatorLength` characters. The contract says they name the guard and the detector, and must never quote the capture. A `default(CaptureVerdict)` fails `Validate`, so an adapter that forgets to build one is caught as a bug, not read as an allow.

There is deliberately no reason text. AI.Sentinel's `DetectionResult.Reason` can quote the content, and Mnemosyne has nowhere safe to put it.

### Timeout (**my call**)

`MnemosyneOptions.GuardTimeout`, with the same range, rules and default (30 seconds) as `EvaluationTimeout`. When it expires, the facade cancels the token it passed the guard and stops waiting, even for a guard that ignores the token, and treats the guard as down. It is a separate option because a slow judge is harmless (the run is stored unjudged) while a slow guard drops captures, so hosts will tune them differently.

### Registration (**my call**)

`ReasonletMemory` gains an optional `ICaptureGuard? guard` constructor parameter. `AddMnemosyne` resolves it with `GetService`, as it does the extractor and the evaluator, so a host registers one as a singleton and nothing else. The parameter is appended after the existing optional ones, before `timeProvider`. The plan checks what that does to positional callers in tests and samples and fixes them.

### Telemetry (**my call**)

A new internal `GuardTelemetry`, shaped like `EvaluationTelemetry`, on the shared source and meter:

- a `mnemosyne.guard` activity per guard call, tagged `mnemosyne.guard` (the guard's name) and `mnemosyne.guard.blocked` (true or false) from a valid verdict, and `mnemosyne.guard.detector` when blocked;
- when blocked, a `mnemosyne.capture.blocked` event on that activity carrying the guard and the detector;
- a `mnemosyne.guard.inspections` counter tagged with the guard's name and the outcome (`allowed`, `blocked`, an error code's name or `exception`), and a `mnemosyne.guard.duration` histogram;
- the shared `mnemosyne.operations` and `mnemosyne.operation.duration` under operation `guard`.

The guard is an operation of its own (**my call**). Today the facade's `RememberAsync` has no activity; only the store emits `mnemosyne.remember`. A blocked or failed-guard capture never reaches the store, so it shows up only under operation `guard`, with no `remember` count. That is intended: the remember never happened. When there is no tracer, the guard's activity is a root activity; otherwise it nests under whatever activity the caller has open.

A failed guard call has no verdict, so its signals carry no guard name, as a failed judge call carries no evaluator name. No signal carries the question, the answer, the intent, the name, the graph or any error or exception message, per `MnemosyneTelemetry`'s rule. A blocked capture is visible in telemetry and in the returned error, and nowhere else. It is not logged, since the facade has no logger.

## Tests

- **Unit, facade:**
  - no guard, so behaviour is unchanged;
  - allow, so the capture is stored as today;
  - block, so the answer is `Blocked`, the detail names the guard and the detector, and the store, the extractor, the embedder and the judge are never called;
  - an `Unavailable` result, a thrown exception and a timeout (including a guard that ignores its token) all answer `Unavailable`, and nothing downstream is called;
  - another error code, and an invalid or default verdict, throw `InvalidOperationException`;
  - the caller's cancellation propagates;
  - an invalid capture answers `Validation` without calling the guard;
  - the guard receives the capture exactly as given, before the facade fills in an intent or a name.
- **Unit, verdict and options:** the `CaptureVerdict.Validate` rules; the `GuardTimeout` range, matching `EvaluationTimeout`'s.
- **Unit, telemetry:** the activity, the event, the counter and the histogram for allow, block, error and exception, and that no tag or event carries capture text. A canary string in the question, the answer, the intent and the name must appear in no signal and no error.
- **Unit, DI:** `AddMnemosyne` picks up a registered guard and works without one.
- **Integration (PostgreSQL):** a blocked capture through the real facade leaves no row, and an allowed one is stored.
- **AOT smoke:** the guard path runs under Native AOT. The pinned graph hash is unchanged.
- **Regression:** the full existing suite passes unchanged apart from the `Blocked` enum additions.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| A guard that is down blocks all capture | Lost procedures during an outage | Intended, fail-closed (**user**). Telemetry shows it as the `Unavailable` outcome; phase 3.5's background capture logs and counts failures. |
| A guard quotes content in `Guard` or `Detector` | User text in telemetry | The contract forbids it, the length cap limits it, and phase 3.4's adapter maps only AI.Sentinel's `DetectorId`. |
| A new constructor parameter breaks positional callers | Compile errors in tests and samples | Append it as an optional parameter and fix the callers in the same phase. |
| A new enum member breaks exhaustive switches in hosts | A host's `switch` falls to its default case | Acceptable before 1.0. Called out in the release notes through the `feat` commit. |
