# Phase 1.3 Design — Graph JSON schema v1

**Date:** 2026-10-22
**Phase:** 1.3
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)

The user skipped the design questions ("let's go"), so every decision here is
**my call** unless it is inherited. It is inherited when it comes from the
[roadmap design](2026-10-21-roadmap-design.md): "Mnemosyne owns a minimal,
versioned schema of nodes and edges … callers may add their own properties;
executing the graph stays the caller's job". It is also inherited when it
comes from the [phase 1.2 design](2026-10-22-phase-1.2-abstractions-design.md):
phase 1.3 extends `ReasonletGraph` with schema, serialization, equality and
validation without renaming `Nodes`, `Edges` or `SchemaVersion`.

## Goal

A procedure has one well-defined shape that Mnemosyne stores and compares.
That shape is a versioned JSON format with a published JSON Schema, an
AOT-safe serializer, stricter validation, and a content hash. The hash decides
whether two graphs are "the same procedure". `RememberAsync` uses that answer
to choose between "another execution" and "a new version".

## Approach

### Shape (v1)

```json
{
  "schemaVersion": 1,
  "nodes": [
    { "id": "check-endpoint", "type": "tool", "name": "Check the endpoint", "tool": "http_get" },
    { "id": "decide", "type": "decision" }
  ],
  "edges": [ { "from": "check-endpoint", "to": "decide", "condition": "status != 200" } ],
  "properties": { "daedalus.process": "azure-troubleshooting" }
}
```

- **`ReasonletNode`** keeps `Id` and `Type`, and gains three members:
  - `Name`: an optional human label.
  - `Tool`: the tool name for tool steps, optional.
  - `Properties`: optional, see Extension properties.

  `Type` is a free string. Doc comments list the well-known values `tool`,
  `retrieve`, `decision`, `agent` and `answer`, but other values are valid,
  because the schema is expected to change fast.
- **`ReasonletEdge`** keeps `From` and `To`, and gains two members:
  - `Condition`: an optional label for a branch.
  - `Properties`.
- **`ReasonletGraph`** keeps `Nodes`, `Edges` and `SchemaVersion`, and gains
  `Properties`.
- **Tool arguments are not part of the schema.** A procedure is the steps,
  not the values one run passed. Arguments often carry user data, and the
  roadmap puts redaction before capture in phase 3. A caller that wants an
  argument *template* can put it in `Properties`.
- **The positional records become init-only.** `ReasonletNode`,
  `ReasonletEdge` and `ReasonletGraph` change from positional records to
  `sealed record`s with `required` init members. This is the same rule
  phase 1.2's final review applied to records that will grow, and these
  three just gained members. It changes construction syntax only, never
  member names.

### Extension properties

- `Properties` is `IReadOnlyDictionary<string, JsonElement>?` on the graph,
  on nodes and on edges. It holds caller-defined data that Mnemosyne stores
  and returns but never interprets.
- **Keys are namespaced.** A key must be two or more non-empty segments
  separated by dots, such as `daedalus.process`. So `"."`, `"a."` and `".a"`
  are invalid. Plain-named keys stay free for later schema versions without
  colliding with caller data.
- A property value must not be an undefined `JsonElement` (`default`).
  JSON `null` is a valid value, and it is distinct from an absent key.
- A null `Properties` and an empty one are the same: both serialize as
  absent and hash the same.
- **Limits:**
  - **Size.** The **sum, over every `Properties` dictionary in the graph**
    (graph, nodes and edges), of the UTF-8 byte length of its compact JSON
    serialization must be at most 64 KiB (65,536 bytes).
  - **Count.** A single graph may have up to 500 nodes and 2,000 edges.
  - **Depth.** Property values may nest at most 32 levels deep, the same as
    the serializer's `MaxDepth`.
  - The limits are constants on a static `ReasonletGraphLimits` class.
- These limits keep a graph a procedure, not a data dump. Hitting one is a
  `Validation` error.

### Validation (extends 1.2's `Validate()`)

In order, first failure wins:
1. Everything phase 1.2 already checks.
2. `SchemaVersion` equals a supported version. Today only `1` is supported:
   a higher version gives `Validation` with "unsupported schema version",
   not a crash.
3. At least one node.
4. Node IDs are unique (ordinal comparison), reported at `Nodes[i].Id`.
5. Every edge's `From` and `To` name an existing node, reported at
   `Edges[i].From` or `Edges[i].To`.
6. An edge `Condition`, when present, is not blank. `null` means
   unconditional.
7. No duplicate edges with the same `From`, `To` and `Condition`.
8. Property keys are well formed (see Extension properties) and values are
   not undefined. Failures are reported as `Properties["k"]`,
   `Nodes[i].Properties["k"]` and so on, with the same key escaping as phase 1.2.
9. Within the limits.

Cycles are **allowed**, since a retry loop is a real procedure. Self-loops are
allowed too. These rules keep the order from phase 1.2: the first failure
wins.

### Serialization

- A source-generated `System.Text.Json` context lives inside Abstractions.
  `System.Text.Json` is in-box, so the "only ZeroAlloc.Results" package rule
  still holds.
- `ReasonletGraphJson` is a public static class with two members:
  - `string Serialize(ReasonletGraph graph)`
  - `Result<ReasonletGraph, MnemosyneError> Deserialize(string json)`
- JSON names are camelCase. Null optional members are omitted.
- `Deserialize` returns a `Validation` error for:
  - malformed JSON;
  - a missing required member;
  - an unknown top-level or node or edge member, which must go in
    `properties` instead;
  - a **duplicate member name in any JSON object**, including inside
    `properties` and nested property values;
  - a graph that fails `Validate()`.

  It never throws on bad input. `System.Text.Json` keeps the last value of a
  duplicate key and drops the rest without an error. That is the same silent
  data loss that rejecting unknown members prevents. Use .NET 10's
  `JsonSerializerOptions.AllowDuplicateProperties = false` if it covers
  dictionaries and `JsonElement`. If it doesn't, pre-scan with
  `Utf8JsonReader`.
- Unknown members are rejected rather than ignored. Silently dropping
  data would make two different stored graphs hash the same.

### Equality: content hash

- `Result<string, MnemosyneError> ReasonletGraph.ComputeContentHash()` runs
  `Validate()` first and returns its failure. An invalid graph has no
  hash, so the store never persists a hash for an invalid graph. On success
  it returns lowercase hex SHA-256 over a **canonical** serialization:
  - `schemaVersion` is included, so the same content under a later schema
    version is a different procedure. Schema bumps are rare and deliberate.
  - nodes sorted by `Id`;
  - edges sorted by `From`, then `To`, then `Condition` (null first);
  - property keys sorted, at every level, including inside nested
    `JsonElement` objects;
  - numbers written from their **raw JSON text**, so `1` and `1.0` differ.
    That is simple and stable, and writers are expected to be consistent.
    Strings are re-encoded through one writer, so escape differences such
    as `\u0041` versus `A` do not change the hash;
  - no whitespace.

  Sorting is ordinal.
- Two graphs are the same procedure **if and only if** their content hashes
  are equal. Node IDs count: the same shape with different IDs is a
  different procedure, because IDs are how edges and callers refer to steps.
- `Name` counts too, so renaming a step is a new version. `Properties`
  count as well.
- The hash is what phase 1.4 stores and indexes, so the store can decide
  "equal to parent" in SQL inside the atomic remember.
- No `Equals` override. Records holding collections still must not be
  compared with `==` (phase 1.2 rule). The hash is the comparison.

### Published schema

- `schemas/reasonlet-graph.v1.schema.json` is a JSON Schema (draft 2020-12)
  describing v1. It is committed, and the docsite in phase 1.7 links it.
- A test validates the serializer's output against it, using a JSON Schema
  library in the test project only.
- A test also checks that the schema rejects an unknown member.

## Tests

- **Round-trip:** for every valid sample graph, `Deserialize(Serialize(g))`
  succeeds and gives the same content hash.
- **Hash:**
  - Reordering nodes, edges or property keys gives the same hash.
  - Changing any node ID, name, tool, type, edge condition or property
    value gives a different hash.
  - A golden test pins the hash of one fixed graph, so an accidental change
    to canonicalization is caught.
- **Deserialize:** malformed JSON, a missing `nodes` member, an unknown
  member, `schemaVersion: 2`, a duplicate node ID and an edge to a missing
  node each give `Validation` with the right path, and none throws.
- **Limits:** 501 nodes fails, and properties of 64 KiB + 1 fails.
- **Schema conformance:** the serializer's output validates against the
  published schema.
- **AOT:** the AOT gate stays green with the source-generated context.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Canonical hashing of nested `JsonElement` property values is subtle (number formats, unicode escapes) | Equal graphs hash differently, which creates spurious versions | Canonicalize numbers from their raw text, re-serialize strings through one writer, and pin with a golden test plus reorder tests |
| Rejecting unknown members breaks a newer writer talking to an older reader | Interop across versions | `schemaVersion` gates it; a v2 adds members and bumps the version, so an old reader reports "unsupported schema version" clearly |
| Init-only conversion touches many tests | Churn in this phase | Mechanical, and `TestData` builders absorb most of it |
