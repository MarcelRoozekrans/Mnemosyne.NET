# Phase 2.1 Design: Evaluator contract and feedback API

**Date:** 2026-10-23
**Phase:** 2.1
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)

This design builds on the phase 1.4 to 1.6 store, recall and facade, and on the
[roadmap](2026-10-21-roadmap-design.md) for milestone 2: "Answer 'did it work?' without the caller hand-filling feedback, so the success-rate term in ranking is real."

Decisions are marked **user** or **my call**. The final review of the branch added four **user** decisions, U1 to U4, which this text includes: the record call returns the verdict, an unusable answer stores the run unjudged, remember embeds before it judges, and the judge has a timeout.

## Goal

The success rate behind ranking should reflect whether a run really worked:

- An **evaluator** judges each run.
- A **human's explicit verdict** overrides the evaluator.
- The **agent's own success flag** is used only when nothing better exists.

This phase adds the evaluator contract, the run data an evaluator needs, the explicit verdict on feedback, and the bookkeeping that keeps the success counters in step with whichever verdict counts.

## Non-goals

- **No evaluator implementation ships here.** The LLM-as-judge default is phase 2.2, and the Minos.NET adapter is phase 2.3.
- **No minimum-run-count weighting.** Phase 2.4 adds it to the success-rate term.
- **No docs pages or sample.** Those are phase 2.5.
- **No stored answers and no re-judging.** See the next section.

## Decisions from the brainstorm

| Question | Decision | By |
|---|---|---|
| Who decides whether a run worked? | An evaluator scores every run, and a human's explicit verdict replaces it. The agent's own flag is the fallback when no evaluator is registered. | user |
| Where does the answer come from? | The agent passes the answer when it records the run. It is judged and never stored, so a run can't be re-judged. | user |
| When is a run judged? | Inside the record call. The run and its verdict are stored together, so nothing is lost on a crash. The agent chooses whether to await. | user |
| How does feedback override? | Feedback gains an optional "worked" verdict. When given, it replaces the evaluator's verdict for that run and the counters are corrected. The three scores stay. | user |

## Approach

### Contract (Abstractions)

```csharp
public interface IReasonletEvaluator
{
    ValueTask<Result<ReasonletEvaluation, MnemosyneError>> EvaluateAsync(ReasonletEvaluationRequest request, CancellationToken ct);
}

public sealed record ReasonletEvaluationRequest
{
    public required ReasonletGraph Graph { get; init; }        // the procedure followed
    public required string Name { get; init; }
    public required string Intent { get; init; }
    public required string Question { get; init; }             // the run's question
    public required string Answer { get; init; }               // the run's answer
    public required ReasonletOutcome Outcome { get; init; }    // the agent's own view
}

public readonly record struct ReasonletEvaluation(bool Success, double Score, string Evaluator);
```

**Request shape** (**my call**). The request carries the procedure's graph, name and intent, not a `ReasonletDefinition`. During a remember there is no stored Reasonlet yet: the store decides between a new Reasonlet, a new version and an execution only after the judge has run, so no id, version or status exists. A recorded run fills these fields from the stored definition.

**Field rules:**
- `Score` is in [0, 1].
- `Evaluator` is a short, non-blank identifier of the judge, at most 100 characters, for example `llm-judge` or `minos`. It is stored and it appears in telemetry, so it must name the judge and nothing about the run (**my call**).
- An evaluator's reasoning text is not part of the contract and is never stored (**my call**). It could quote the answer, which the user decided is not kept.

**Error codes.** `Unavailable` when the judge's backend fails. Any other failure, or an invalid evaluation, is an adapter bug and throws `InvalidOperationException`, which follows the phase 1.6 extractor rule.

### Recording a run

`IReasonletMemory.RecordExecutionAsync` takes one record in place of the current parameters. This is pre-1.0, so the change is allowed, and a record lets later phases add members (**my call**).

```csharp
public sealed record ReasonletRun
{
    public required ReasonletScope Scope { get; init; }
    public required ReasonletId Id { get; init; }
    public required ReasonletOutcome Outcome { get; init; }
    public required ReasonletProvenance Provenance { get; init; }
    public string? Question { get; init; }   // with Answer, lets the evaluator judge
    public string? Answer { get; init; }
}
```

Both strings are optional, but they must be given together. When present, the question must not be blank and is capped at 32,000 code points, through `Check.MaxLength` (**my call**). The existing `ReasonletCapture.Question` gains no new cap; adding one would change existing input.

**An unusable answer stores the run unjudged (user, U2).** The answer is the agent's own output, so a bad one must not lose the run. Validation of `ReasonletRun` and `ReasonletCapture` checks only that a present answer is valid UTF-16, since a lone surrogate is a programming error, not bad agent output. An answer that is blank, or longer than 32,000 code points, passes validation, but the facade does not judge it:
- it skips the judge, so no `mnemosyne.evaluate` activity starts, and the run is stored with the agent's verdict;
- with an evaluator registered, it counts the skip once on `mnemosyne.evaluations` with outcome `skipped` and no other tag (**my call**, of the two options U2 offered). The counter needs no new activity or tag and sits beside the judge's other outcomes, so a dashboard of judge outcomes shows skips too. The tag alternative would have tagged an activity the facade does not own. The counter carries no text, so the privacy rule holds.

The answer goes to a model, so the 32,000 code point cap bounds cost and abuse. `ReasonletEvaluationRequest` keeps its own `Answer` checks, not blank and at most 32,000 code points, because the facade builds a request only from a usable answer.

`ReasonletCapture` gains the same optional `Answer`, so the run that a remember records can be judged too (**my call**). A capture already carries its question.

**Redacted `ToString`** (**my call**, from the final review). `ReasonletRun`, `ReasonletCapture` and `ReasonletEvaluationRequest` override the record's `PrintMembers`, so `ToString` prints `Answer = [redacted]` when an answer is present and `Answer = null` when it is not. Every other member prints as the compiler would print it. The privacy rule thereby extends to logging.

**The record call returns the verdict (user, U1).** `RecordExecutionAsync` returns `ValueTask<Result<ReasonletRunReceipt, MnemosyneError>>`:

```csharp
public sealed record ReasonletRunReceipt(ExecutionId Execution, ReasonletVerdictSource Source, bool Success);

public enum ReasonletVerdictSource { Agent = 1, Evaluator = 2, Feedback = 3 }
```

- `Success` is the effective success that counted at record time, and `Source` says whose verdict it is.
- `ReasonletReceipt`, the result of remember, gains trailing `ReasonletVerdictSource Source` and `bool Success` for the run it records. Every capture records a run, an `ExecutionOnly` one included, so every receipt carries them.
- `Feedback` never appears in a record or remember receipt, because feedback comes later. The enum has it so that one type names all three sources.
- The enum is numbered from 1, as every Mnemosyne enum is, and the numbering tests pin its values.
- The store derives both values, so the facade passes the store's receipt through unchanged.

**The facade's steps:**

1. Validate.
2. Judge, if an evaluator is registered, `Question` and `Answer` are present, and the answer is usable: not blank and at most 32,000 code points.
   - For a recorded run, read the Reasonlet from the store for its graph, name and intent. If it doesn't exist, the record answers `NotFound`, as today.
   - For a remember, the order is: resolve the intent and the name, embed, judge, store (**user, U3**). A remember that fails on the embedding then never pays for a judge call.
   - Call `EvaluateAsync`, honouring the cancellation rules from phase 1.6: only the caller's own cancellation propagates. Any other `OperationCanceledException` is a timeout.
   - **Timeout (user, U4).** `MnemosyneOptions.EvaluationTimeout`, a `TimeSpan` that defaults to 30 seconds, must be positive, or `Timeout.InfiniteTimeSpan` to disable it. A finite value is also capped at 4,294,967,294 milliseconds, about 49.7 days, the longest delay a `CancellationTokenSource` accepts, so a valid option can never throw at judge time (**my call**). The facade links the caller's token with a `CancellationTokenSource` that the registered `TimeProvider` cancels after the timeout, and passes the linked token to the evaluator. When the timeout fires, the judge is down: the run is stored with source `agent`, and the judge call's telemetry shows outcome `Unavailable`. The caller's own cancellation still propagates. The evaluator must honour the token; the facade does not abandon a judge that ignores it. `ReasonletMemory` takes an optional trailing `TimeProvider`, `TimeProvider.System` when null, and `AddMnemosyne` passes the registered one.
3. Pass the run to the store with its verdict:
   - **`evaluator`:** the judge answered. The verdict is the judge's success, score and name.
   - **`agent`:** no evaluator is registered, no answer was given, the answer was blank or over 32,000 code points, or the judge was `Unavailable` (including a timeout). The agent's own `Outcome.Success` counts.

**When the judge is down (my call).** The run is still stored, with source `agent`. A broken judge must not lose data or fail the agent's call. Telemetry records that judging failed, so an operator can see it. A judge that throws an exception counts as down, the same as an `Unavailable` result, which matches how phase 1.6 treats a failing generator or extractor. A judge that returns an error result with any other code, or an invalid evaluation, is an adapter bug and throws.

**Where the answer goes.** It reaches the evaluator and nothing else. It is never stored, never placed in an error, and never placed in a signal.

**Store port** (**my call**).
- `IReasonletStore.AppendExecutionAsync` gains a trailing `ReasonletEvaluation? evaluation`, and returns `ValueTask<Result<ReasonletRunReceipt, MnemosyneError>>` (**user, U1**). `ReasonletStoreEntry` gains `ReasonletEvaluation? Evaluation`, and the `ReasonletReceipt` that `RememberAsync` returns carries the source and effective success of the run it records.
- The store derives the verdict source and the effective success itself, so third-party stores apply one rule. A new run has no feedback yet, so the PostgreSQL store derives both in code, `Evaluator` with the judge's success when there is an evaluation and `Agent` with the agent's flag otherwise, which is the rule the schema's `CHECK` enforces on the row. It needs no value read back from the insert. It validates the evaluation: score in [0, 1], and a non-blank evaluator name of at most 100 characters.
- The facade strips `Answer` from the capture before it builds the entry, as it already does for intent and name. `ReasonletStoreEntry.Validate` requires `Capture.Answer` to be null, so no answer can reach any store.
- `AppendFeedbackAsync` keeps its signature. Its documented meaning gains the verdict rule.

### Explicit verdict on feedback

`ReasonletFeedback` gains `bool? Worked`, as a trailing optional member, so existing calls keep compiling.

- When `Worked` is present, it is the run's verdict, with source `feedback`.
- Recording feedback again replaces the three scores, as today.
- A later feedback with `Worked = null` keeps an earlier human verdict (**my call**). A score-only update must not silently erase a human's override. To change the verdict, record a new `Worked` value. A verdict can be changed but not retracted, and the docs say so.

### Which verdict counts

For each execution:

```
effective success = feedback.Worked ?? evaluated success ?? agent success
verdict source    = feedback | evaluator | agent
```

The store keeps all three inputs, so the effective value can always be recomputed:
- `agent_success`, the existing `success` column, renamed;
- `evaluated_success`, `evaluation_score` and `evaluator`, null unless judged;
- `feedback_worked`, the human's verdict, kept on the execution row so that one row holds every input.

`reasonlet_metrics.successes` and `last_success_at` count the effective success.

**Recording or replacing feedback.**
- If the change flips the effective success, the counters are adjusted in the same transaction.
- `successes` moves by ±1.
- `last_success_at` follows the phase 1.5 rule. A success raises it with `greatest`. When a lost success held the stored value, it is recomputed from the remaining effective successes. With none left it becomes null, so an erased or overridden run's time is never kept.

**Feedback path and missing targets** (**my call**). Feedback knows only `(scope, executionId)`. It reads the execution's Reasonlet id, then locks in order: the Reasonlet `FOR KEY SHARE`, the execution `FOR UPDATE`, then metrics. Each step is a statement of its own, so each sees commits that landed while it waited. If the execution is gone after the locks, because an erase or a prune removed it, the feedback answers `NotFound`, the same as for an execution that never existed. The XML docs that say feedback "waits for nothing" are rewritten.

**Pruned history** (**my call**). The counters are a total of record, so pruned runs stay counted. When an override removes the latest success, `last_success_at` is recomputed from the remaining effective successes. It can become null while `successes` is still above zero, which matches what erase already does.

**Lock order.** Every writer still takes locks in the order Reasonlets, then executions, then metrics. The feedback path today touches only the execution and the feedback row. It must now take the Reasonlet `FOR KEY SHARE`, then the execution `FOR UPDATE`, then the metrics row, before it adjusts the counters. The phase 1.5 erase subtraction and the prune counters must use the effective success. The erase already subtracts a removed run's success from its kept Reasonlet, and that run's success is now its effective success.

**Schema** (**my call**). A new migration, `0002_evaluation.sql`, rather than an edit to 0001. The 0.1.0 release may ship before this phase, and a released migration must not change. It:
- renames `reasonlet_executions.success` to `agent_success`;
- adds nullable `evaluated_success boolean`, `evaluation_score double precision` and `evaluator text` with `CHECK (length(evaluator) <= 100)`;
- adds `feedback_worked boolean NULL`;
- adds `success boolean NOT NULL` as the stored effective success, so that search, erase and prune read one column. Existing rows get `success = agent_success`.
- adds `CHECK (success = coalesce(feedback_worked, evaluated_success, agent_success))` and `CHECK ((evaluated_success IS NULL) = (evaluator IS NULL) AND (evaluated_success IS NULL) = (evaluation_score IS NULL))`, so the database itself enforces the rule (**my call**). The erase subtraction and the prune counters already read `success`, so they stay correct unchanged.
- records `schema_version = 2` in `mnemosyne.settings`.

**Upgrades** (**my call**).
- Version check: `EnsureMigratedAsync` also checks `schema_version`. A new binary pointed at a phase 1.7 database answers `Unavailable` "schema not migrated: call MigrateAsync", not a raw missing-column error.
- Atomicity: the migration must apply atomically. Confirm that the ZeroAlloc.ORM runner wraps each file in a transaction. If it doesn't, the file runs in its own transaction, which PostgreSQL DDL allows.
- Old instances: an old instance still running against the upgraded schema fails loudly, because its insert omits the `NOT NULL` `agent_success`. The README says to stop old instances before migrating.

### Telemetry

The facade emits a `mnemosyne.evaluate` activity around each judge call, on the shared source.

| Tag | Value |
|---|---|
| `mnemosyne.evaluator` | the judge's name |
| `mnemosyne.evaluation.success` | on success |
| `mnemosyne.evaluation.score` | on success |
| outcome and `error.type` | the phase 1.5 and 1.6 rules |

**Instruments:**
- `mnemosyne.evaluations`, a counter tagged with `mnemosyne.evaluator` and `mnemosyne.outcome`;
- `mnemosyne.evaluation.duration`, a histogram in seconds;
- `mnemosyne.operations` and `mnemosyne.operation.duration` gain operation `evaluate`.

The store's `execution.append` activity gains `mnemosyne.verdict_source`, a successful `remember` gains it for the run it records, and `feedback.append` gains it, as `feedback`, whenever the call sets `Worked`, even when the verdict stays the same, so human overrides that agree with the judge are visible too (**my call**). A failed judge call carries no `mnemosyne.evaluator` tag, because the name comes from the judge's answer.

An answer that is not judged because it is unusable starts no `mnemosyne.evaluate` activity, and with an evaluator registered counts once on `mnemosyne.evaluations` with outcome `skipped`, with no other tag, no duration and no `evaluate` operation (**my call**, U2).

The privacy rule holds: no question or answer text, and no error or exception message. `MnemosyneTelemetry`'s privacy list names the answer.

### Registration

`AddMnemosyne` resolves an optional `IIntentExtractor` today, and it now also resolves an optional `IReasonletEvaluator` with `GetService`. With no evaluator registered, behaviour is exactly as today: the agent's flag counts. It also passes the registered `TimeProvider`, which it already adds when the host has none, so the judge's timeout runs on the host's clock.

## Tests

- **Precedence.** Feedback beats the evaluator, the evaluator beats the agent, and the agent is the fallback. Cover all the combinations, and include feedback with `Worked = null`.
- **Counters:**
  - Feedback that flips the verdict moves `successes` by ±1 and keeps `last_success_at` correct, including when the lost success held it.
  - Replacing feedback twice.
  - After erase and prune, the counters still equal the effective successes.
- **Receipts.** A judged run returns `Evaluator` with the judge's success. With no evaluator, or with the judge down, the run returns `Agent` with the agent's flag. Remember returns the same pair for its run, for every capture kind.
- **Unusable answers.** A blank answer and a 32,001 code point answer each store the run, return `Agent`, never call the judge, and count one `skipped` evaluation.
- **Order.** Remember judges after it embeds, and a remember whose embedding generator is down fails without calling the judge.
- **Timeout.** An expired timeout stores the run as `Agent`, with outcome `Unavailable`; the caller's cancellation still throws; an infinite timeout sets no timer.
- **Redaction.** A sentinel answer never appears in `ToString`.
- **Judge failures:**
  - `Unavailable`, a timeout, or a missing answer stores the run with source `agent`.
  - Real cancellation propagates.
  - Other errors and invalid evaluations throw.
- **The answer never leaks.** A sentinel in the answer never appears in any stored column, error or signal.
- **Remember with an answer** stores the first run with source `evaluator`.
- **Migration 0002** upgrades a phase 1.7 database: existing runs keep their success, now as `agent_success`, and their counters are unchanged.
- **Concurrency.** Feedback racing an append, an erase and a prune on the same Reasonlet completes with no deadlock under the lock order, and the counters stay exact.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The judge adds seconds to every record call | Slower agents | The agent chooses whether to await; the judge is optional; phase 2.2 measures it |
| Answers can't be re-judged | A better judge later can't fix past verdicts | User's decision; human feedback still overrides any run |
| The stored effective `success` drifts from its inputs | Wrong ranking | One write path in the store maintains it; an invariant test checks it after every mutation kind |
| An evaluator ignores its cancellation token | The timeout cannot fire, and the record call waits for the judge | The contract says to honour the token; the option's docs say so; an adapter that wraps an SDK passes the token through |

**Note for phase 2.2.** An LLM judge's parse failures, such as a model reply that isn't the expected JSON, should map to `Unavailable`, not to an invalid evaluation. A malformed reply then falls back to the agent's verdict instead of throwing and failing the call. Phase 2.2's design picks this up.
